# OSTEP Ch 4 — The Abstraction: The Process 정리

OS의 가장 기본 추상화 = **프로세스**. "실행 중인 프로그램"을 OS가 어떻게 표현·관리하는가.

---

## 1. 프로그램 vs 프로세스

- **프로그램** = 디스크의 **정적인 실행 파일**(코드 + 데이터). 가만히 있음(passive).
- **프로세스** = 그 프로그램을 메모리에 올려 **실행 중인 인스턴스**(active) = **프로그램 + 실행 상태(state)**.
- **일대다**: 하나의 프로그램 → 여러 프로세스 (예: `./ssort`를 두 번 실행 = 프로그램 1, 프로세스 2).
- 각 프로세스는 **독립된 주소 공간**(같은 코드라도 메모리 안 섞임 — mem.c의 격리).

## 2. 프로세스의 machine state (구성 요소)

프로세스를 멈췄다 정확히 재개하려면(context switch) OS가 저장해야 할 것:

1. **주소 공간(메모리)** — 코드 / 정적 데이터 / 힙 / 스택
2. **레지스터** — 특히:
   - **PC(Program Counter)** = 다음 실행할 명령 위치("어디까지 실행했나")
   - **스택 포인터(SP)** = 스택 꼭대기
   - 범용 레지스터 = 계산 중 값
3. **I/O 정보** — 열린 파일들(파일 디스크립터, fd 0/1/2 포함)

→ 이 셋을 저장하면 프로세스를 정확히 되살릴 수 있음(context switch의 본질).

## 3. 프로세스 상태 (Running / Ready / Blocked)

```
        디스패치(스케줄됨)
   Ready ───────────────▶ Running
     ▲   ◀───────────────   │
     │     선점(타이머 IRQ)   │ I/O 시작
     │   I/O 완료           ▼
     └──────────────  Blocked
```

- **Running**: CPU에서 실행 중
- **Ready**: 돌 준비 됨, 스케줄러 간택 대기
- **Blocked(Waiting)**: 어떤 사건(주로 I/O 완료) 전엔 못 돎

**4개 전이:**
- Ready→Running: 스케줄됨 / Running→Ready: 선점(타이머 인터럽트)
- Running→Blocked: I/O 시작 / **Blocked→Ready: I/O 완료**

**시험 포인트:**
- **I/O 완료 → 바로 Running 아님, 반드시 Ready 경유.**
- **왜 Blocked를 Ready와 분리?** Blocked에 CPU 줘봤자 I/O 미완이라 할 일 없음 → CPU 낭비. 스케줄러가 Ready 중에서만 골라야 CPU 안 놀림.

## 4. PCB / 프로세스 리스트

- **PCB(Process Control Block)** = 프로세스 하나의 모든 것을 담는 구조체 (리눅스 `task_struct`, xv6 `struct proc`).
  - PID, 상태, **레지스터 문맥**(context switch 시 저장/복원), **메모리 정보**(페이지 테이블 포인터), 열린 파일, 부모 포인터 등
- **프로세스 리스트** = PCB들의 모음.
- **cpu.c의 CR3 질문 해소:** "pid로 페이지 테이블 구분?" → 아니, **PCB가 매핑을 담음.** context switch 때 OS가 다음 프로세스의 **PCB에서 페이지 테이블 주소를 CR3에 로드** + 레지스터 복원.

## 5. 프로세스 생성 5단계

1. **코드+정적 데이터를 주소 공간에 로드** (eager=한번에 / **lazy=필요할 때만**, lazy는 demand paging)
2. **런타임 스택 할당** + argc/argv 채우기
3. **힙 초기 할당** (malloc으로 성장)
4. **I/O 준비**: 기본 fd 0/1/2(stdin/stdout/stderr)
5. **진입점(main)으로 점프** → 제어권을 프로세스에 넘김 (엄밀히는 `_start`가 먼저)

## process-run.py 숙제 (스케줄링 정책 실험)

프로세스 상태 변화를 시뮬레이션. `X:Y` = 명령 X개, 각 명령이 CPU일 확률 Y%.

**핵심 발견:**
- **`5:100,5:100`**: CPU만 쓰는 2개 → CPU 100%, 10틱 (1코어라 순차).
- **`4:100,1:0`**: CPU 프로세스 후 IO 프로세스 → IO 대기 5틱 동안 **CPU idle**(돌릴 게 없음) → 11틱, 55%.
- **`1:0,4:100`** (순서 뒤집기): IO 먼저 → IO 대기 중 CPU 프로세스 **overlap** → 7틱, 86%. **순서만 바꿔도 큰 차이.**

**두 스케줄링 축:**
- **`-S` (언제 떠나나)**: `SWITCH_ON_IO`(IO 발행 시 전환, overlap 가능) vs `SWITCH_ON_END`(끝날 때까지 안 바꿈, CPU 낭비).
- **`-I` (언제 돌아오나)**: `IO_RUN_IMMEDIATE`(IO 완료 즉시 그 프로세스 실행 → IO 디바이스 계속 바쁨) vs `IO_RUN_LATER`(나중에 → IO 디바이스 놀아 낭비).
- 예: `3:0,5:100,5:100,5:100` → LATER는 31틱/CPU 68%, IMMEDIATE는 21틱/**CPU 100%**.

**교훈: IO 바운드와 CPU 바운드 작업을 끼워 넣어(interleave) IO 대기가 CPU 작업과 겹치게 하면 자원을 안 놀린다.** (MLFQ가 IO 바운드 우대하는 이유 — Ch 8 예고.)

**IO의 하드웨어 이해:** IO 중 CPU는 IO를 하지 않음. **디바이스 컨트롤러가 독립적으로** 처리하고, 끝나면 **인터럽트**로 CPU에 알림(=io_done). 그래서 CPU와 IO 디바이스가 병렬로 일해 overlap 가능. (세부는 36장 I/O Devices.)

## 헷갈렸다 푼 것

- **가상 주소 vs 물리 주소**: 두 프로세스가 같은 가상 주소를 써도 다른 물리 프레임 → 격리.
- **Blocked → Ready(바로 Running 아님).**
- **context switch 시 전체 레지스터 저장** (인터럽트는 함수 호출이 아니라 caller/callee 규약이 안 통함).
- **시뮬레이터는 타이머 선점 없음**(IO/END에만 전환) — 실제 시스템(cpu.c)과 다른 단순화.
