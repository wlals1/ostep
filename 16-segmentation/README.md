# OSTEP Ch 16 — Segmentation 정리

base/bounds(Ch15)의 **내부 단편화**를 해결. 핵심: **base/bounds 쌍을 세그먼트마다 하나씩.**

---

## 아이디어

주소 공간을 **논리적 조각(세그먼트)**으로 나눔 — 보통 **코드 / 힙 / 스택**.
각 세그먼트가 **자기 base와 bounds**를 가짐 → 물리 메모리에 **각각 독립 배치**.

**이득:** 안 쓰는 가운데 빈 공간은 **물리 메모리에 아예 안 잡음** → 내부 단편화 해결.
```
가상 16KB (코드2 + 힙2 + 스택2, 나머지 10KB 빈 공간)
→ 물리는 6KB만 사용. 세 조각이 물리 여기저기 흩어져도 됨.
```

**중요 구분:** 주소 공간 크기(가상 범위) ≠ 물리 메모리 소비(limit들의 합).
어제 실측한 VSZ 502MB vs RSS 1.25MB와 같은 원리.

## 세그먼트 판별 방법

**① 명시적(explicit)** — 가상 주소의 **상위 비트**로 표시:
```
14비트 VA (16KB 주소 공간)
 13 12 | 11 ... 0
 └─┬─┘   └──┬──┘
세그먼트    오프셋
```
- **대가**: 상위 비트를 뺏겨 **세그먼트당 크기 제한** (2비트 쓰면 세그먼트당 최대 주소공간의 1/4).

**② 암묵적(implicit)** — 접근 방식으로 판단:
- PC(명령어 인출)에서 온 주소 → 코드 / SP 기반 → 스택 / 나머지 → 힙
- **주소 비트를 안 뺏김.**

## 방향: 증가 vs 감소

스택은 **반대 방향으로 자람** → 하드웨어에 **grows-positive/negative 비트** 필요, 계산식도 다름.

**변환 절차 (3단계):**
1. **세그먼트 판별** (상위 비트)
2. **오프셋 계산**
   - 증가 세그먼트: `오프셋 = VA` (0에서부터)
   - 감소 세그먼트: `오프셋 = 주소공간크기 - VA` (**끝에서부터의 거리**)
3. **오프셋 vs limit 비교** → 통과 시 `base ± 오프셋`

| | 오프셋 | 유효 조건 | 변환 | 물리 범위 |
|--|--------|-----------|------|-----------|
| **seg0(증가)** | `VA` | `오프셋 < limit0` | `base0 + 오프셋` | `base` ~ `base+limit-1` (base **포함**) |
| **seg1(감소)** | `크기 - VA` | `오프셋 <= limit1` | `base1 - 오프셋` | `base-limit` ~ `base-1` (base **제외**) |

- **base는 감소 세그먼트의 "위쪽 경계선"** — 그 자체는 안 씀. base=32, limit=4면 물리 **28~31**.
- 왜 주소 공간 크기가 계산에 나오나 → **감소 세그먼트는 주소 공간 끝에 붙어 있어** 끝을 기준으로 오프셋을 재기 때문.

## 보호 비트와 공유

세그먼트마다 **권한 비트(read/write/execute)** 부여 → 하드웨어가 매 접근 검사.

**코드 세그먼트 공유:**
- 코드를 **읽기+실행 전용(r-x)**으로 하면 아무도 못 고침 → **여러 프로세스가 물리 한 벌을 공유** 가능.
- 예: `libc.so.6` — 시스템의 거의 모든 프로세스가 공유(pmap에서 확인한 것). 100개 프로세스 × 1.5MB → 1.5MB로 절약.
- **힙·스택은 rw-** → 각자 쓰는 데이터라 공유 불가(격리 깨짐).
- **fork의 COW와 같은 원리**: 읽기만 하면 공유 안전, 쓸 때만 갈라놓기.

## 세그먼트 정보 저장

세그먼트가 3개면 프로세스당 **base/limit/권한/방향 × 3 = 십여 개 값** → 작아서 **CPU 레지스터에 직접**, 문맥 교환 시 **PCB에 저장·복원**.

**페이징과 대비 (앞으로):**
| | 세그멘테이션 | 페이징 |
|--|--------------|--------|
| 관리 정보 | 세그먼트 3~4개 = 십여 개 | 페이지 수만큼 = **수십만~백만 항목** |
| 저장 | **CPU 레지스터** | **메모리에 테이블**, CPU엔 **CR3 포인터만** |
| 문맥 교환 | 레지스터 몇 개 | **CR3 하나만 교체** |
| 번역 비용 | 레지스터라 빠름 | 메모리 접근 필요 → **TLB 필수** |

## 한계 → 페이징으로

1. **외부 단편화(external fragmentation)** ★ 결정타
   - 세그먼트 크기가 **제각각**이라 물리에 넣고 빼다 보면 빈틈이 여기저기.
   - "총 여유는 10KB인데 연속 6KB가 없어 할당 실패" 상황.
   - 압축(compaction)으로 정리 가능하지만 **비쌈**(전부 복사).
2. **세그먼트 크기 상한** (명시적 방식에서 주소 비트를 나눠 먹어서)
3. **희소한 세그먼트**(띄엄띄엄 쓰는 큰 힙)는 여전히 낭비

→ **페이징**: 주소 공간을 **똑같은 크기(4KB) 페이지**로 자름 → 크기가 균일하니 **외부 단편화 원천 소멸**(어느 빈 프레임이든 딱 맞음).

## 숙제 (segmentation.py)

세그먼트 **2개** 모델: seg0(상위 비트 0, 코드+힙, 증가) / seg1(상위 비트 1, 스택, 감소).

```bash
./segmentation.py -s 100 -a 16 -p 64        # 문제
./segmentation.py -s 100 -a 16 -p 64 -c     # 정답
./segmentation.py -a 16 -p 32 --b0 24 --l0 4 --b1 18 --l1 5   # 직접 지정
```
(주의: 랜덤 base 생성 시 **물리 메모리 > 주소 공간 × 2** 여야 함.)

**실측 예** (주소공간 16, base0=49/limit0=4, base1=32/limit1=5):
```
VA 0,1,2,3       → seg0 유효 → PA 49,50,51,52
VA 4~7           → seg0 위반 (오프셋 ≥ 4)
VA 8,9,10        → seg1 위반 (오프셋 > 5, 가운데 빈 공간)
VA 11,12,13,14,15 → seg1 유효 → PA 27,28,29,30,31
```
| VA | 세그먼트 | 오프셋 | 결과 |
|----|----------|--------|------|
| 12 | seg1 | 16-12=4 | 4≤5 → **PA 28** |
| 8 | seg1 | 16-8=8 | 8>5 → violation |
| 1 | seg0 | 1 | 1<4 → **PA 50** |
| 7 | seg0 | 7 | 7≥4 → violation |
| 0 | seg0 | 0 | → **PA 49** |

**헷갈렸다 잡은 것:**
- 감소 세그먼트 오프셋은 **하위 비트가 아니라 `크기 - VA`**(끝에서의 거리).
- **base는 감소 세그먼트에 포함 안 됨** (base=32, limit=4 → 28~31).
- 주소 공간 크기가 공식에 나오는 건 **기준점이 끝**이라서지, 물리를 그만큼 쓴다는 뜻이 아님.
- 인자 의미: `-s` 시드(같은 시드=같은 문제), `-a` 가상 주소 공간 크기, `-p` 물리 메모리 크기.
