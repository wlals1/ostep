## 스레드란 — 주소 공간을 공유하는 실행 흐름

프로세스로 동시성을 하면:
- 주소 공간이 완전 분리 → 데이터 공유가 어려움 (파이프·공유 메모리 필요)
- 생성·문맥 교환이 비쌈 (**CR3 교체 + TLB flush** — Phase 2에서 본 것)

**스레드는 주소 공간을 공유.**

| 스레드마다 **독립** | **공유** |
|--|--|
| **스택** (각자 함수 호출·지역변수) | 코드 |
| **레지스터** (PC, SP 포함) → **TCB**에 저장 | **힙**, 전역변수 |
| | 파일 디스크립터, 페이지 테이블(=주소 공간) |

**주소 공간 그림이 바뀜:**
```
Ch13에서 본 것          스레드 2개
┌────────┐             ┌────────┐
│ 코드    │             │ 코드    │
│ 힙      │             │ 힙      │
│  ↕     │             │  ↕     │
│        │             │ 스택 2  │  ← 주소 공간 한가운데 새로 생김
│  ↕     │             │  ↕     │
│ 스택    │             │ 스택 1  │
└────────┘             └────────┘
```
→ 힙-스택 사이 빈 공간이 스택들로 잘림. **스레드마다 스택 상한이 정해진 이유**(기본 8MB). Ch14에서 "스레드마다 스택이 필요해 한도가 작다"고 한 것.

**문맥 교환 비용:**
```
프로세스 간: 레지스터 저장 + CR3 교체 + TLB flush/ASID   ← 비쌈
스레드 간:   레지스터 저장만. 주소 공간 그대로           ← 쌈
```

## race condition ★

```c
static volatile int counter = 0;
void *worker(void *arg) {
    for (int i = 0; i < 1000000; i++) counter++;
    return NULL;
}
// 스레드 2개 → 기대값 2,000,000. 실제로는 안 나옴.
```

### `counter++`는 명령 3개

```asm
mov  counter, %eax    ; ① 메모리 → 레지스터
add  $1, %eax         ; ② 레지스터에서 +1
mov  %eax, counter    ; ③ 레지스터 → 메모리
```
**"고수준 한 줄 = 기계 명령 하나"는 착각** (내 반복 실수 목록의 그것).

### 최악의 인터리빙

```
counter = 50

A: ① mov counter → eax      eax_A = 50
[문맥 교환 — eax_A=50이 A의 TCB에 저장]

B: ① mov counter → eax      eax_B = 50    ← 아직 50 (A가 아직 안 씀)
B: ② add 1                  eax_B = 51
B: ③ mov eax → counter      counter = 51
[문맥 교환 — eax_A=50 복원]

A: ② add 1                  eax_A = 51    ← 낡은 50에서 더함
A: ③ mov eax → counter      counter = 51  ← B의 결과를 덮어씀!

두 번 증가시켰는데 51. 하나 증발 (lost update).
```

**두 포인트:**
1. **레지스터는 스레드마다 따로.** A의 낡은 eax가 TCB에서 그대로 복원되니, A는 B의 갱신을 **모르고** 낡은 값으로 계속함.
2. **실패가 확률적.** 인터럽트가 하필 ①~③ 사이에 걸려야 터짐 → **재현 불가, 디버깅 지옥.**

## ★ volatile은 race를 막지 못한다 (반복 실수 매듭)

위 코드에 `volatile`이 붙어 있었는데도 틀린 값이 나옴.

**volatile이 하는 일:** "레지스터에 캐싱하지 말고 매번 메모리에서 읽어라" = **컴파일러 최적화 억제.**

**volatile을 붙여도 `counter++`는 여전히 load-add-store 3개.**
읽고 나서 쓰기까지의 **틈이 그대로 열려 있음** → 인터럽트 들어오면 똑같이 깨짐.

| | 대상 | 막는 것 |
|--|--|--|
| **volatile** | **컴파일러** | 최적화(캐싱, 재정렬) |
| **race** | **런타임 스케줄링** | 명령 사이에 끼어드는 문맥 교환 |

→ 컴파일러가 문제를 일으킨 게 아니라 **타이머 인터럽트가 틈에 들어온 것.** 컴파일러에게 하는 부탁으로 스케줄러를 막을 수 없음.

```
가시성(visibility): 내가 쓴 값을 남이 볼 수 있나        → volatile이 도움
원자성(atomicity):  여러 명령이 쪼개지지 않고 실행되나   → volatile 무력  ★ 이게 필요
```

**실무 규칙: C/C++에서 멀티스레드 동기화에 volatile을 쓰면 틀린 코드.** 락이나 `_Atomic`/`std::atomic`을 쓸 것.
(volatile의 진짜 용도: 메모리 맵드 I/O 레지스터, 시그널 핸들러가 건드리는 변수.)
※ **자바의 volatile은 의미가 다름**(가시성 + 재정렬 금지까지 보장). C와 헷갈리지 말 것.

## 용어

| 용어 | 뜻 |
|--|--|
| **critical section** | 공유 자원을 건드리는 코드 조각 (`counter++`) |
| **race condition** | 여러 스레드가 동시에 임계 영역에 들어가 결과가 타이밍에 좌우됨 |
| **indeterminate** | 실행마다 결과가 달라짐 |
| **mutual exclusion** | 임계 영역에 한 번에 하나만 — **우리가 원하는 것** |

## 왜 CPU가 원자적 명령을 잔뜩 안 만드나

**이유 1 (내가 답한 것):** 명령어 집합이 비대해지면 디코더가 복잡해지고 fetch/decode 비용 증가. RISC 철학과 충돌.

**이유 2 (더 근본적): 애초에 불가능.**
```c
n->next = head; head = n;                    // 리스트 삽입
if (a.bal >= amt) { a.bal -= amt; b.bal += amt; }  // 이체
// 해시 리사이즈, 트리 회전, ...
```
**임계 영역은 임의로 길고 임의로 복잡.** 몇 개를 만들든 개발자는 그 조합을 넘어서는 걸 하고 싶어 함.

**그래서 방향 전환:**
```
❌ 모든 작업을 원자적 명령으로              → 불가능
✅ 작은 원자적 원시연산 몇 개만 주고, 그걸로 락을 만든다 → 임의 구간 보호
```
하드웨어가 주는 것: **test-and-set / compare-and-swap(CAS) / fetch-and-add**, 그리고 `xchg`.

> **Phase 2와 같은 패턴:** 하드웨어는 **메커니즘**(base/bounds 검사, TLB, page walk / 원자적 명령)만, **정책**(교체 정책 / 동기화 전략)은 소프트웨어가.

## 숙제 (x86.py) — `threads-intro`

어셈블리 수준에서 **인터리빙을 눈으로** 보는 시뮬레이터.

**옵션:** `-p` 프로그램 / `-t` 스레드 수 / `-i` 인터럽트 간격 / `-r` 랜덤 인터럽트 / `-s` 시드 / `-a` 초기 레지스터 / `-M` 메모리 추적 / `-R` 레지스터 추적 / `-C` 조건 코드 / `-c` 값 계산

`looping-race-nolock.s`:
```asm
.top
mov 2000, %ax     # ┐
add $1, %ax       # ├ 임계 영역 3명령 (공유: memory[2000])
mov %ax, 2000     # ┘
sub $1, %bx       # ┐
test $0, %bx      # ├ 루프 카운터 (%bx는 스레드마다 독립 → 안전)
jgt .top          # ┘
```
**공유 vs 독립 구분:** `memory[2000]` = 공유 → race ⚠ / `%bx` = 레지스터, 스레드별 → 안전 ✅

### 실험 1 — 인터럽트 없으면 정상

```bash
./x86.py -p looping-race-nolock.s -t 2 -a bx=1 -M 2000 -c      # → 2 ✅
```

### 실험 2 — `-i 2`로 race 재현

```bash
./x86.py -p looping-race-nolock.s -t 2 -a bx=1 -M 2000 -R ax -i 2 -c   # → 1 ❌
```
```
    0       1   1001 add $1, %ax           ← T0의 ax=1
    0       0   ------ Interrupt ------    ← ax가 0? T1의 ax로 바뀐 것
    ...
    1       1   1002 mov %ax, 2000         ← T0이 1 씀
    1       1                1002 mov %ax, 2000  ← T1도 1 씀 (덮어씀!)
```
- **`ax` 열은 "현재 실행 중인 스레드의 ax"**. 인터럽트에서 값이 바뀌는 건 TCB 교체 때문. T0의 ax=1은 사라진 게 아니라 저장됨.
- 둘 다 0을 읽어 1을 만들었으니 **둘 다 1을 씀** → 증가 하나 증발.
- 손으로 만든 인터리빙과 정확히 같은 구조.

### 실험 3 — "i≥3이면 안전"은 틀렸다 ★ (내가 잡은 반례)

`bx=1`(1회 반복)에선 i≥3이 전부 통과 → **"임계 영역 3명령보다 크면 안전"**이라는 규칙이 보임.
**의심: 루프가 여러 번 돌면 정렬이 어긋나지 않나?**

루프 한 바퀴 = 6명령(1000~1005), 임계 영역 = 앞 3명령. `-i 4`면:
```
1바퀴: 1000,1001,1002,1003 → 인터럽트   (임계 영역 무사)
2바퀴: 1004,1005,1000,1001 → 인터럽트   ← 임계 영역 한복판! ⚠
```

```bash
for i in 3 4 5 6 7; do
  ./x86.py -p looping-race-nolock.s -t 2 -a bx=3 -M 2000 -i $i -c | tail -1
done
```
```
정답은 6 (각 스레드 3회 × 2)

i=3 : 6 ✅   (임계 영역 3과 맞아떨어짐)
i=4 : 5 ❌   ← 예측대로 깨짐
i=5 : 6 ✅
i=6 : 6 ✅   (루프 6명령과 일치)
i=7 : 4 ❌   ← 2개 유실
```
**"i≥3이면 안전"이 실측으로 반증됨.** 인터럽트 위치가 루프 길이 6의 나머지를 따라 돌면서 앞 3명령 구간에 떨어지느냐가 갈림길.

> **교훈은 "어떤 i가 안전한가"가 아님.** i=3이 통과해도 **인터럽트 타이밍이 조금만 달라지면 깨지는 코드**. 실제 인터럽트는 규칙적이지도 예측 가능하지도 않음.

### 실험 4 — 랜덤 인터럽트 (현실)

```bash
for s in 1 2 3 4 5; do
  ./x86.py -p looping-race-nolock.s -t 2 -a bx=3 -M 2000 -i 4 -r -s $s -c | tail -1
done
```
```
seed=1 : 3    seed=2 : 6 ✅    seed=3 : 3
seed=4 : 4    seed=5 : 4
```
**같은 코드, 같은 입력, 결과는 3·6·3·4·4.** seed=2만 보고 "정상"이라 판단하면 재앙.

> **concurrency 버그의 본질:**
> - 테스트 통과가 정상의 증거가 못 됨 — 운 좋은 인터리빙 하나를 봤을 뿐
> - 재현이 안 되니 버그 리포트를 받아도 못 고침
> - 디버거를 붙이면 타이밍이 바뀌어 사라짐 (**Heisenbug**)
>
> → **테스트로 검증하는 게 아니라 설계로 보장해야 함.** "돌려보니 되던데"가 통하지 않는 유일한 영역.

## 실전 포인트

- **스레드 vs 프로세스 차이**(공유·독립 항목, 문맥 교환 비용) — 면접 단골.
- **`counter++`가 3명령**임을 어셈블리로 설명 → race의 근거.
- **volatile ≠ 원자성** — 가시성/원자성 구분해서 말하기. C와 자바의 volatile 차이도.
- **왜 하드웨어가 원자적 명령을 잔뜩 안 만드나** → 임계 영역은 임의로 길고 복잡. 원시연산 + 소프트웨어 조합.
- **race는 테스트로 못 잡는다** — 실측 데이터(seed마다 3·6·3·4·4)로 답하면 강력.
