# OSTEP Ch 32 — Common Concurrency Problems 정리

지금까지 본 버그들을 **분류하고 이름 붙이는** 장. Phase 3 체크포인트.

---

## 실증 데이터 (Lu et al.)

MySQL, Apache, Mozilla, OpenOffice의 실제 동시성 버그 **105개** 분석:

```
비데드락  74개 (70%)
├─ 원자성 위반 51개 (48%)  → 해법: 락
└─ 순서 위반   24개 (23%)  → 해법: 조건 변수 / 세마포어
데드락    32개 (30%)
```

**데드락이 소수인 이유:** 데드락은 **락을 여러 개 겹쳐 잡아야** 생기는데 실무 코드 대부분은 락 하나만 씀. 반면 비데드락 버그는 **락 하나만 써도** 생김.

> **실무 우선순위: 데드락보다 원자성·순서 위반이 2배 이상 흔하다.** "락 순서만 지키면 안전"이 아님.

## ① 원자성 위반 (atomicity violation) — 51개

MySQL 실제 버그:
```c
// 스레드 1
if (thd->proc_info) {              // ① 검사: NULL 아니네
    // ← 여기서 스레드2가 끼어듦
    fputs(thd->proc_info, ...);    // ② 사용: NULL 역참조 → 크래시
}
// 스레드 2
thd->proc_info = NULL;
```

**`fputs` 자체의 원자성이 문제가 아님.** `if(검사)`와 `fputs(사용)`이 **하나로 묶여야** 했던 것.

> **깨진 가정: "검사했을 때 NULL이 아니었으면, 쓸 때까지 NULL이 아닐 것이다."**
> 단일 스레드에선 참, 멀티스레드에선 거짓.

### ★ "확인하고 행동하기(check-then-act)" — 이 책의 반복 패턴

```
Ch26: flag 확인 → flag 설정          (깨진 락)
Ch28: flag 읽기 → 조건 코드 → 판단    (flag.s, 낡은 레지스터)
Ch30: done 확인 → 잠들기             (lost wakeup)
Ch32: NULL 검사 → 사용               (원자성 위반)
```
**전부 같은 병.** "확인"과 "행동" 사이에 틈이 있고 그 사이에 세상이 바뀜.

**해법: 검사와 사용을 같은 락으로 묶는다.**
```c
lock(&m);
if (thd->proc_info) fputs(thd->proc_info, ...);
unlock(&m);

lock(&m); thd->proc_info = NULL; unlock(&m);   // 상대 쪽도 같은 락으로!
```
(Ch28의 "락은 규약" — 그 데이터를 건드리는 **모든 코드**가 같은 락을 잡아야 성립)

## ② 순서 위반 (order violation) — 24개

Mozilla 실제 버그:
```c
// 스레드 1
void init() { mThread = PR_CreateThread(mMain, ...); }
// 스레드 2
void mMain(...) { mState = mThread->State; }   // mThread가 아직 세팅 전일 수 있음
```

> **깨진 가정: "A가 B보다 먼저 실행될 것이다."** 스레드 스케줄링은 그걸 보장하지 않음.

**해법: 조건 변수 / 세마포어로 순서 강제** (Ch30·31)
```c
// 세마포어 초기값 0
init():  mThread = create(...); sem_post(&s);
mMain(): sem_wait(&s); mState = mThread->State;
```

### 두 버그의 차이

| | 원자성 위반 | 순서 위반 |
|--|--|--|
| 깨진 가정 | "이 구간이 안 쪼개진다" | "A가 B보다 먼저다" |
| 해법 | **락** | **조건 변수 / 세마포어** |
| 비율 | 51개 (48%) | 24개 (23%) |

**둘이 비데드락 버그의 전부고, 해법도 이미 배운 도구 두 개뿐.**

## 데드락 — 4조건

**네 조건이 전부 성립해야** 데드락 발생. **하나만 깨면 사라짐.**

1. **상호 배제 (mutual exclusion)** — 자원을 한 번에 하나만
2. **점유 대기 (hold-and-wait)** — 뭔가 쥔 채로 다른 걸 기다림
3. **비선점 (no preemption)** — 남의 자원을 강제로 뺏을 수 없음
4. **순환 대기 (circular wait)** — 대기 그래프에 사이클

### 지금까지 본 해법 매핑 (OSTEP 기준)

| 해법 | 깨는 조건 |
|--|--|
| 락 순서 통일 (전역 순서, 주소 순 등) | **순환 대기** |
| 철학자: 한 명만 반대 순서로 집기 | **순환 대기** |
| 철학자: 4명만 앉히기 | **순환 대기** |
| `main-deadlock-global.c`의 전역 락 `g` | **점유 대기** |
| `trylock` 실패 시 다 놓고 재시도 | **비선점** |
| lock-free (CAS만으로) | **상호 배제** |

**⚠ Ch31 노트 정정:** "철학자 4명 제한 = 점유 대기를 깬다"고 썼는데 **틀렸음.**
4명만 앉혀도 철학자는 여전히 왼쪽을 쥔 채 오른쪽을 기다림 → **점유 대기는 그대로.**
다만 **5명이 다 하나씩 쥐는 상황이 불가능**해져 고리가 안 닫힘 → **순환 대기 차단**이 정확.

**전역 락 `g`가 점유 대기인 이유:** `g`를 잡고 m1·m2를 **모두** 획득한 뒤 `g`를 놓음
→ 결과적으로 **"필요한 락 전부를 원자적으로 한 번에 획득"** → "일부만 쥔 채 나머지를 기다리는" 상태가 없어짐.
```c
lock(&g);            // 획득 시작
lock(&L1); lock(&L2);
unlock(&g);          // 획득 종료
```

**`trylock`이 비선점인 이유:** OSTEP은 "남이 못 뺏는다"는 조건을 **내가 스스로 내놓는 것**으로 우회한다고 봄.
(“점유 대기를 포기하는 것”이라는 해석도 결과적으로 맞음 — **분류 관점의 차이.** 책 기준으론 비선점.)
```c
top:
  lock(&L1);
  if (trylock(&L2) != 0) { unlock(&L1); goto top; }   // 못 잡으면 다 놓고 재시도
```
⚠ **livelock 주의** — 둘이 계속 동시에 잡았다 놓았다 반복할 수 있음. 재시도 전 **랜덤 지연**을 넣어 완화.

**상호 배제를 깨는 법 = lock-free** (Ch28의 CAS 재시도)
```c
do { old = head; n->next = old; } while (CAS(&head, old, n) != old);
```
락 자체를 안 쓰니 상호 배제 조건이 성립하지 않음.

## 예방 외의 두 접근

### 회피 (avoidance)
스케줄링으로 데드락 가능 상태를 피함. **은행원 알고리즘(Dijkstra)**이 대표.
**모든 스레드가 필요로 할 자원을 미리 알아야** 해서 현실성이 낮음 → 실무에선 거의 안 씀.

### 탐지 후 복구 (detect & recover)
데드락을 그냥 두고, 주기적으로 **대기 그래프에 사이클이 있나** 검사 → 발견하면 죽이거나 롤백.
**DB가 이 방식** — 트랜잭션 하나를 abort하고 재시도시키면 되니까.
> **드물게 일어나는 일에 상시 비용을 지불하지 않는 게 합리적일 때가 있다.**
> Tom West: *"고칠 필요 없는 오류는 다루지 마라."*

## 숙제 (`threads-bugs`) — 4조건 해법을 실제 코드로 ★

**파일 하나가 조건 하나에 대응한다.** 위의 표를 그대로 구현한 숙제.

```
vector-deadlock.c             → 문제 (dst→src 고정 순서인데 인자가 뒤바뀜)
vector-global-order.c         → 순환 대기 차단 (벡터 주소 순으로 정렬)
vector-avoid-hold-and-wait.c  → 점유 대기 차단 (전역 락으로 획득 구간을 감쌈)
vector-try-wait.c             → 비선점 (trylock 실패 시 다 놓고 재시도)
vector-nolock.c               → 상호 배제 차단 (fetch-and-add, lock-free)
```

`vector_add(v_dst, v_src)`는 항상 `dst → src` 순으로 락을 잡음.
**`-d` 플래그**: 홀수 스레드의 인자를 뒤바꿈 → `vector_add(v2, v1)` → **실제 락 순서가 반대**가 되어 데드락 유발.

### 데드락 재현

```bash
timeout 3 ./vector-deadlock -n 2 -l 100000 -t;    echo $?   # → Time: 0.02, exit 0  ✅
timeout 3 ./vector-deadlock -n 2 -l 100000 -d -t; echo $?   # → 출력 없음, exit 124 ❌ 데드락
```
`-d` 없으면 **모든 스레드가 같은 순서**라 데드락 없음 → **순서 자체가 아니라 "서로 다른 순서"가 문제**임을 실증.
(exit 124 = timeout이 죽임. Ch27에서 쓴 판정법)

### 실측 결과

```
                          -d(2스레드)   일반(4스레드)
vector-deadlock            데드락 ❌      0.06초
vector-global-order        0.02초        0.05초   ★ 가장 빠름
vector-avoid-hold-and-wait 0.03초        0.06초
vector-try-wait            0.08초        0.18초   (재시도 530,500 / 5,486)
vector-nolock              0.19초        0.38초   ★ 가장 느림
```

### ★ 반전 ① — lock-free가 제일 느리다 (7배)

```c
// global-order : 원자적 명령 4번 (lock 2 + unlock 2) + 일반 덧셈 100번
lock(v_dst); lock(v_src);
for (i = 0; i < VECTOR_SIZE; i++) v_dst->values[i] += v_src->values[i];
unlock; unlock;

// nolock : 원자적 명령 100번 (VECTOR_SIZE = 100)
for (i = 0; i < VECTOR_SIZE; i++) fetch_and_add(&v_dst->values[i], ...);
```
```
원자적 명령 수 25배 차이 × (20~50사이클 vs 1사이클) → 실측 7배와 일치
```

> **Ch29의 그 교훈 그대로: 락당 작업량이 커야 락 비용이 묻힌다.**
> ```
> hand-over-hand : 노드당 lock/unlock → 락 비용이 작업을 압도 ❌
> nolock 벡터    : 원소당 원자적 명령 → 똑같은 구조 ❌
> global-order   : 벡터 전체에 락 1쌍 → 락 비용이 100번 덧셈에 묻힘 ✅
> ```
> **"락을 없앴다" ≠ "원자적 명령을 없앴다".** 세분도가 잘못되면 오히려 더 많이 쓰게 됨.

### ★ 반전 ② — nolock은 보장도 약하다 (README의 "slightly different semantics")

```
락 버전  : 벡터 덧셈 전체가 원자적 → 다른 스레드는 "덧셈 전" 또는 "덧셈 후"만 봄
nolock  : 원소 하나씩만 원자적   → 앞 절반은 더해지고 뒤 절반은 안 된 상태가 보임
```
(멀티코어에선 인터럽트 없이도 진짜 동시에 발생)

**왜 문제인가 — 원소들이 서로 관계가 있을 때:**
- 3D 좌표 `(x,y,z)`에서 x만 갱신 → **말이 안 되는 위치**
- 합이 항상 100이어야 하는 배열 → **불변식이 깨진 상태**가 노출

더 미묘한 것: `vector_add(v1,v2)`와 `vector_add(v2,v1)`이 동시에 돌면 원소별로 뒤섞여 **어떤 순차 실행으로도 만들 수 없는 결과**가 나옴 → **직렬화 가능(serializable)하지 않음.**

> **lock-free의 대가는 성능만이 아니라 보장의 약화.** "원자적"의 단위가 벡터 전체 → 원소 하나로 축소.
> **문제가 원소 단위 원자성으로 충분할 때만** 쓸 수 있음.

### ★ 반전 ③ — 재시도 53만 번 = livelock 실물

```c
top:
    if (trylock(&v_dst->lock) != 0) goto top;
    if (trylock(&v_src->lock) != 0) {
        retry++;                    // ★ dst는 잡았는데 src 실패 → dst도 놓고 처음부터
        unlock(&v_dst->lock);
        goto top;
    }
```
```
-d 있음 (2스레드) : Retries 530,500   ← 20만 연산당 2.65번씩 헛돎
-d 없음 (4스레드) : Retries   5,486   ← 스레드가 더 많은데 100배 적음
```
**`-d`가 만든 것:**
```
T0: v1 잡음 → v2 실패(T1 보유) → v1 놓고 재시도
T1: v2 잡음 → v1 실패(T0 보유) → v2 놓고 재시도
→ 동시에 잡았다 놓았다 반복. 멈추진 않는데 진전이 없음 = livelock
```
`-d` 없으면 모두 같은 순서라 dst를 잡았으면 src를 반대로 쥔 놈이 없음 → 대부분 성공.

**해결: 재시도 전 랜덤 지연(random backoff).** 같은 리듬으로 부딪히는 걸 깨뜨림.
(네트워크 CSMA/CD, TCP 재전송도 같은 기법)

## ★ 명백히 우월한 방법이 있나

**global-order가 기본 선택. 다만 "항상 쓸 수 있는 게 아니라서" 나머지가 존재한다.**

**global-order의 전제: 필요한 락을 미리 알고 전역 순서를 매길 수 있어야 함.**
이 예제는 벡터 주소로 비교하면 되니 쉬웠지만, 안 되는 경우:

1. **어떤 락이 필요한지 미리 모를 때** — 콜백·플러그인·가상 함수를 거치면 런타임에 정해짐
   ```c
   lock(&node->lock);
   process(node);      // 이 안에서 어느 락을 잡는지 실행해봐야 앎
   ```
2. **계층 구조가 순서를 강요할 때** — 트리에서 어떤 연산은 부모→자식, 다른 연산은 자식→부모. 주소 순으로 강제하면 알고리즘이 안 돌아감
3. **남의 라이브러리를 부를 때** — 그 안에서 무슨 락을 잡는지 모름

| 방법 | 쓸 수 있는 조건 | 대가 |
|--|--|--|
| **global-order** ★ | 필요한 락을 **미리 알고 순서를 매길 수 있을 때** | 없음 (가능하면 최선) |
| **avoid-hold-and-wait** | 순서는 못 매기지만 **락 목록은 아는** 경우 | 전역 락이 병목 → 확장성 ↓ |
| **try-wait** | 락을 **동적으로 발견**할 때. 위 둘이 불가능 | livelock 위험, **연산이 재시작 가능해야** 함 |
| **nolock** | 갱신이 진짜 **단일 워드 원자 연산**이고 그 단위 원자성으로 충분할 때 | 다중 워드 불변식 보장 불가 |

**`try-wait`의 숨은 제약:** 락을 다 못 잡으면 처음부터 다시 하므로, **락 획득 전에 부작용(파일 쓰기, 네트워크 전송)이 있으면 안 됨.** 재시작 가능한 연산에만.

### 진짜 우월한 답

> **"애초에 락 여러 개를 동시에 잡지 않는 설계."**
> Ch10 재방문의 결론과 동일 — **동기화를 잘하는 것보다 동기화가 필요 없게 만드는 게 근본 해결.**
> - 데이터를 나눠 소유해서 락이 하나만 필요하게
> - 메시지 전달(Go 채널)로 공유 자체를 없애기
> - DB는 **트랜잭션 + 데드락 탐지 후 롤백**으로 문제를 다른 층으로 이동
>
> **락을 둘 이상 잡아야 하는 상황이면 global-order가 최선. 하지만 그 상황 자체를 피하는 게 더 낫다.**

## 실전 포인트

- **비데드락이 70%** — 실증 데이터로 답하면 강력. 그리고 그 이유(락 하나만 써도 남).
- **원자성 위반의 본질 = check-then-act** — Ch26·28·30에서 본 그 패턴의 반복.
- **원자성 위반 vs 순서 위반** — 깨진 가정과 해법 도구가 다름.
- **데드락 4조건 + 각 조건을 깨는 실제 기법**을 매핑해서 말할 수 있어야. 면접 단골.
- **순서 통일이 가장 실용적인 예방책** — 병렬성을 안 죽이니까. **실측으로 확인됨**(global-order가 가장 빠름).
- **trylock의 livelock 위험**과 랜덤 백오프 — 재시도 530,500회로 실물 확인.
- **lock-free가 항상 빠른 게 아니다** — 세분도가 틀리면 원자적 명령을 더 많이 씀(7배 느림). 게다가 **보장도 약해짐**(직렬화 불가).
- **각 해법이 쓸 수 있는 조건**을 말할 수 있어야 — global-order는 락을 미리 알 때만.
- **탐지+복구가 합리적인 상황**(DB) — "모든 문제를 예방할 필요는 없다".
