# OSTEP Ch 13 — The Abstraction: Address Spaces 정리

Phase 2(메모리 가상화) 시작. CPU 가상화가 "CPU를 독점하는 환상"이었다면,
메모리 가상화는 **"메모리를 독점하는 환상" = 주소 공간(address space)**.

---

## 왜 필요한가

여러 프로그램을 물리 메모리에 동시에 올리면 두 문제:
1. **보호**: A가 B(또는 OS)의 메모리를 읽고/쓰면 → 데이터 유출·손상.
2. **재배치**: A는 "0번지부터"라고 컴파일됐는데 실제론 물리 512KB에 로드됨. 그대로 0번지 접근하면 OS를 덮어씀.

**두 해결 방식:**
| | (a) 소프트웨어 재배치 | (b) 하드웨어 주소 변환 ⭐ |
|--|------|------|
| 누가 | **로더**가 로드 시 주소 전부 수정 | **MMU(하드웨어)**가 실행 중 매 접근마다 |
| 언제 | 로드 때 한 번 | 메모리 접근마다 |
| 이동 시 | 전부 다시 계산 (비유연) | **base 레지스터 값만 변경** (유연) ⭐ |

→ (b) 채택. **로드 때 주소를 안 고치고**, 실행 중 하드웨어가 "가상 주소 + base = 물리 주소"를 실시간 계산.

## 주소 공간의 구조

```
낮은 주소
  ┌──────────┐
  │  코드     │  고정 크기 (실행 중 안 늘어남). 로딩은 lazy(demand paging).
  ├──────────┤
  │  힙       │  malloc/brk → 주소 증가 방향으로 자람
  ├──────────┤
  │   ↕      │
  │ (빈 공간) │  ← 둘이 여기를 향해 마주봄
  │   ↕      │
  ├──────────┤
  │  스택     │  함수 호출/지역변수 → 주소 감소 방향 (rsp를 sub)
  └──────────┘
높은 주소
```

- **왜 마주보게?** 둘 다 실행 중 크기가 변하는데, 마주보면 **가운데 빈 공간을 유동적으로 나눠 씀.** 같은 방향이면 한쪽 최대치를 미리 못 박아야 해 낭비/부족.
- 둘이 만나면 → 스택 오버플로우 / 할당 실패.
- **빈 공간은 물리 메모리를 안 먹음** (매핑 없음) → 큰 주소 공간을 주되 실제 사용분만 소비.

## 가상 vs 물리 (핵심)

- **가상 주소 공간** = 프로세스가 믿는 뷰. 깔끔한 연속 구조(코드→힙→빈→스택).
- **물리 메모리** = 실제. **페이지 단위로 잘려 여기저기 흩어짐**, 연속일 필요 없음. 여러 프로세스 것이 뒤섞임.
- **페이지 테이블**이 그 매핑("가상 페이지 N → 물리 프레임 M"), **CR3**가 그 테이블을 가리키고, **MMU**가 매 접근 번역.
- mem.c에서 두 프로세스가 같은 가상 주소를 찍고도 값이 안 섞인 이유가 이것.

## 메모리 가상화의 세 목표

| 목표 | 의미 | 어떻게 |
|------|------|--------|
| **Transparency(투명성)** | 프로세스가 가상화를 **눈치 못 챔** ("없는 듯") | 가상 주소로 프로그래밍, OS가 뒤에서 번역 |
| **Efficiency(효율성)** | 느려지거나 메모리 낭비 없이 | **하드웨어 MMU + TLB 캐시** |
| **Protection(보호)** | 서로의 메모리 못 건드림 → 격리 | 하드웨어 경계 검사, 위반 시 트랩(→ segfault) |

- segfault는 목표가 아니라 **보호가 작동한 결과**.
- 이 셋이 Ch15~20(base/bounds → 세그멘테이션 → 페이징 → TLB → 멀티레벨)을 관통하는 발전 동기.

## 숙제 — 내 리눅스에서 실측

도구: `free`(시스템 메모리), `ps`/`top`(프로세스별 VSZ/RSS), `pmap`(주소 공간 상세).

### 핵심 실험: touch 함 vs 안 함

**memory-user.c** (malloc + 무한 루프로 **계속 건드림**):
```
VSZ 105088K(≈102MB)  RSS 103552K(≈101MB)   → RSS ≈ VSZ
```
→ 모든 페이지를 touch하니 전부 물리 메모리에 올라옴.

**memory-user2.c** (malloc만 하고 **안 건드림**, `while(1) sleep(1)`로 유지):
```
VSZ 514688K(≈502MB)  RSS 1280K(≈1.25MB)    → RSS ≪ VSZ !!
```
→ **500MB 할당했는데 물리 메모리는 1.25MB.** `free -m`도 거의 안 변함.

**결론 = lazy allocation(요구 페이징):**
- `malloc`은 **가상 주소 공간을 예약**할 뿐. 실제 물리 프레임은 **처음 접근할 때(page fault)** 붙음.
- 안 건드린 페이지 = 매핑 없음 = 물리 메모리 0 소비.
- 함의: malloc 성공 ≠ 물리 메모리 확보. 나중에 실제 쓸 때 부족하면 OOM (리눅스 overcommit).
- **주의**: 관찰하려면 프로세스가 살아있어야 함(`sleep` 루프). 그냥 return하면 즉시 종료돼 `ps`에 안 잡힘.

### pmap으로 본 실제 주소 공간
```
0x558c42366000    4K r-x--  memory-user2   ← 코드 (r-x = 읽기+실행)
0x558c42369000    4K rw---  memory-user2   ← 데이터
0x558c48ae9000  132K rw---  [anon]         ← 힙
0x7bd23bfff000 512004K rw-- [anon]         ★ 500MB malloc (매핑만, 물리 X)
0x7bd25b428000 1568K r-x--  libc.so.6      ← 공유 라이브러리 (여러 프로세스가 물리 공유)
0x7fff3ab7d000  136K rw---  [stack]        ★ 스택 = 아주 높은 주소!
```
확인된 것:
- **배치 실물**: 코드(0x558c…낮음) → 힙 → … → **스택(0x7fff…높음)**. 마주보는 구조.
- **페이지 단위 권한**: `r-x`(코드), `rw-`(데이터/힙/스택), `r--`(읽기전용) → **보호가 페이지별로.** 코드에 쓰면 segfault 나는 이유.
- **500MB 영역이 가상엔 있는데 RSS엔 없음** → lazy 증명.
- **libc 매핑** = strace에서 본 라이브러리 로딩의 결과.
- 주소가 매번 다름 → **ASLR**.
