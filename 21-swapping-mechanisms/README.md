# OSTEP Ch 21 — Swapping: Mechanisms 정리

Ch13의 **"메모리를 독점하는 환상"의 완성.**
핵심: **물리 메모리를 "전부 담는 곳"이 아니라 "자주 쓰는 것만 담는 캐시"로 본다.**

---

## 문제 — 워킹셋 합 > 물리 메모리

Ch18~20까지의 전제는 이랬음:
```
valid=1 → 물리 프레임에 있음
valid=0 → 없음 = 잘못된 접근(segfault)
```
그런데 프로세스들이 실제로 쓰는 페이지 총합이 물리 메모리를 넘으면?

**관찰:** 모든 페이지를 항상 쓰는 건 아님 (지역성, Ch19의 워킹셋).
→ **자주 쓰는 것만 메모리에, 나머지는 디스크(스왑)에.**

```
가상 주소 공간 (프로세스가 믿는 것)   ← 물리보다 클 수 있음
        ↓
물리 메모리  [자주 쓰는 페이지]        ← 작음, 캐시 역할
        ↕ swap out / swap in
디스크(스왑) [나머지]                  ← 큼, 느림
```

---

## 메커니즘

### present 비트 — valid=0이 두 가지 뜻으로 갈림

| valid | present | 뜻 | 접근하면 |
|--|--|--|--|
| 0 | — | 주소 공간에 없음 | **segfault** |
| 1 | 1 | 메모리에 있음 | 정상 번역 |
| 1 | 0 | **디스크에 있음** | **page fault → swap in** |

(x86은 present 비트로 처리하고 "valid하지만 부재"와 "아예 없음"은 OS가 자기 자료구조로 구분.)

### PFN 자리 겸용 ★

present=0이면 PFN 값이 무의미 → **그 비트를 디스크 주소로 재활용.**
```
present=1 → [ ... PFN ... ]              물리 프레임 번호
present=0 → [ ... 디스크 블록 번호 ... ]   스왑 공간 위치
```
- 하드웨어는 present=1일 때만 그 비트를 PFN으로 봄. present=0이면 **안 보고 trap** → OS가 디스크 주소로 해석.
- **별도 포인터 불필요, 공간 추가 0.** 같은 비트를 상황에 따라 다르게 해석.

### page fault 처리 흐름

```
① 프로세스가 가상주소 접근
② MMU가 PTE 확인 → present=0 → trap
③ OS의 page fault 핸들러 실행
④ PTE에서 디스크 주소 읽음
⑤ 디스크에서 그 페이지를 빈 프레임에 읽어옴
⑥ PTE 갱신: present=1, PFN=새 프레임
⑦ ★ 그 명령을 처음부터 다시 실행(retry) → 이번엔 present=1이라 정상 진행
```

**⑦이 중요** — 실패한 명령을 재실행. 프로세스는 아무 일도 없었던 것처럼 진행(투명성).

### 빈 프레임이 없으면 → 축출

```
⑤' 희생자(victim) 선택
    → dirty면 디스크에 씀 (swap out)
    → 그 페이지 PTE를 present=0으로, 디스크 주소 기록
    → 비워진 프레임에 새 페이지 읽어옴
```
**"누구를 쫓아낼 것인가" = 교체 정책 = Ch22 전체 주제.**

## 비트 두 개 — dirty와 reference

### dirty bit (수정 비트)

```
메모리에 올린 뒤 한 번이라도 썼나?
  안 씀 → dirty=0 (clean) → 디스크 원본과 동일 → 그냥 버림 ✅ 쓰기 생략
  씀    → dirty=1        → 원본과 다름 → 반드시 써야 함
```
**하드웨어가 자동으로 켬** (쓰기 발생 시 MMU가).

**"디스크에 있냐"가 아니라 "고쳤냐"임** (내가 헷갈렸던 것):
코드 페이지도 실행 파일에 있고, swap out된 힙 페이지도 스왑에 있음 — 둘 다 "디스크에 있음". 차이는 **그 사본이 아직 유효하냐**.
```
코드 페이지 (r-x, 절대 안 씀)  → 항상 clean → 버리기만 (실행 파일에서 다시 읽으면 됨)
힙/스택 (rw-)                → dirty → 반드시 저장
읽기만 한 mmap 파일           → clean → 버림
```
→ **clean 축출은 디스크 쓰기가 없어 몇 배 빠름.** 정책이 clean을 우선 희생시키는 이유.

### reference(accessed) bit

```
OS: 주기적으로 모든 페이지의 reference를 0으로 밀어둠
HW: 접근(읽기·쓰기)이 일어나면 1로 켬
OS: 나중에 확인 → 아직 0 = 그동안 안 쓰임 → 좋은 희생자 ✅
```
**왜 하드웨어가 하나:** OS는 매 접근을 감시할 수 없음(Ch15 — 사용자 코드 실행 중엔 OS가 CPU에 없음). HW가 표시만 해두고 OS가 나중에 읽음.

| 비트 | 누가 켜나 | OS가 판단하는 것 |
|--|--|--|
| **dirty** | HW (쓰기 시) | 축출 시 **디스크에 써야 하나** |
| **reference** | HW (읽기·쓰기 시) | **누구를 쫓아낼까** |

### PTE 전체 모습

```
PTE = [ valid │ present │ dirty │ reference │ 권한(rwx) │ PFN or 디스크주소 ]
```

## swap daemon — 미리 비워두기

"빈 프레임 없으면 그때 축출"은 느림 — fault마다 **디스크 쓰기를 기다려야** 함.

**해법: 꽉 차기 전에 백그라운드로 미리 축출** (리눅스 `kswapd`)
```
여유 프레임 < LW(low watermark)  → 데몬 깨어남, 페이지 축출
여유 프레임 > HW(high watermark) → 데몬 잠듦
```
**이득 셋:**
1. fault 시 **이미 빈 프레임이 있음** → 쓰기 대기 없이 바로 swap in
2. 백그라운드라 **프로세스 정지 시간 감소**
3. **여러 페이지를 모아서 한 번에 씀** → 디스크는 큰 덩어리 쓰기가 훨씬 효율적(Ch37)

→ **"작업을 모아서 하면 이득"**은 시스템 전반의 패턴.

## thrashing (한계)

워킹셋 합이 물리 메모리를 크게 넘으면: 올리자마자 쫓겨나고 또 올리고 반복
→ **디스크 I/O만 하느라 실제 일을 못 함.** CPU 사용률 바닥, 디스크 100%.

**교체 정책으로는 못 막음** — 정책은 "주어진 프레임 안에서 누굴 버릴까"만 정하는데, thrashing은 **프레임 자체가 절대적으로 부족한 상황**. 최적 정책조차 무력.

**해법 = 부하를 줄이기 (프로세스 수 감소):**
- **admission control / 워킹셋 모델**: 일부 프로세스를 **통째로 중단(suspend)**시켜 메모리에서 내림. 남은 것들의 워킹셋 합이 들어가면 정상 속도 회복, 나중에 교대 실행.
- **리눅스 OOM killer**: 메모리를 많이 쓰는 프로세스를 죽임. 우아하진 않지만 시스템 마비보단 나음.

> **thrashing은 교체 문제가 아니라 부하 문제.** 해결도 "더 잘 고르기"가 아니라 "일감 줄이기".
> (큐가 터지면 처리 순서를 바꿀 게 아니라 유입을 막아야 하는 것과 같은 구조.)

## SSD를 메모리로 쓰는 것 (물어본 것)

**① 스왑** = 이 장의 그것. 리눅스 swap 파티션/파일, 윈도우 `pagefile.sys`, 맥 `swapfile`.
```bash
swapon --show ;  free -h
```
"메모리로 활용"이라기보다 **밀려난 것의 대피소**. CPU는 SSD를 직접 실행 못 하므로 반드시 메모리로 데려와야(swap in) 사용 가능.
- SSD 덕에 스왑이 실용화됨(HDD 수 ms → SSD 수십 µs, 100배). 그래도 **DRAM보다 1000배 느려** 여전히 최후 수단.

**② ReadyBoost / Optane** = 느린 HDD의 **디스크 캐시**. 메모리 확장이 아니라 디스크 가속 — 방향이 반대. SSD 보편화로 거의 사라짐.

**왜 SSD가 진짜 메모리가 못 되나:**
```
DRAM      : ~50ns,  바이트 단위 랜덤 접근, 무한 쓰기
SSD(NVMe) : ~50µs,  블록(4KB) 단위,        쓰기 수명 제한
              ↑ 1000배
```
속도 / 접근 단위 / 수명 — 셋 다 부적합. 중간을 메우려는 게 **CXL 메모리**(PCIe 연결 메모리 확장, 데이터센터에서 부상 중).

```
레지스터 → 캐시 → DRAM → [CXL] → SSD 스왑 → HDD
  빠르고 작음 ←──────────────────→ 느리고 큼
```
**계층마다 "아래층은 위층의 백업, 위층은 아래층의 캐시"** — TLB가 페이지 테이블의 캐시였듯, 물리 메모리는 스왑의 캐시.

## 실전 포인트

- **page fault ≠ TLB 미스** (Ch19와 구별): TLB 미스는 PTE가 메모리에 있음(가벼움), page fault는 페이지가 메모리에 없음(디스크 I/O, 무거움).
- **PFN 자리 겸용**이 왜 가능한가 → present=0이면 HW가 그 비트를 안 봄. 설계 감각 보여주는 답.
- **dirty의 의미는 "고쳤냐"** — clean 축출이 왜 싼지 설명하기.
- **reference를 왜 HW가 켜나** → OS는 매 접근을 못 봄(Ch15 논리).
- **thrashing 해법은 정책이 아니라 부하 제어.**
