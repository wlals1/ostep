# OSTEP Ch 15 — Mechanism: Address Translation 정리

가상 주소 → 물리 주소 **변환의 실제 메커니즘**. 첫 방식: **Dynamic Relocation (Base and Bounds)**.

---

## 핵심 메커니즘

CPU(MMU) 안에 레지스터 두 개:
- **base**: 이 프로세스 주소 공간이 물리 메모리 **어디서 시작하는지**
- **bounds(limit)**: 주소 공간 **크기**

매 메모리 접근마다 하드웨어가:
```
if (가상주소 < bounds)  물리주소 = 가상주소 + base    ← 변환
else                    예외 발생 (segmentation violation)  ← 보호
```

예) base=32KB, bounds=16KB → VA 1000 → PA 33768. VA 20000 → 예외.

## "동적(dynamic)"의 의미 ★

**base가 자주 바뀐다는 뜻이 아니라, 번역이 "실행 시점"에 일어난다는 뜻.**

| | 정적 재배치 | **동적 재배치** |
|--|------|------|
| 언제 번역 | **로드 시** 명령어의 주소를 물리 주소로 영구 수정 | **매 접근마다** 하드웨어가 계산 |
| 명령어 | 물리 주소를 들고 다님 | **가상 주소 그대로 유지** |
| 실행 중 이동 | 불가 (다 다시 고쳐야) | **base만 바꾸면 끝** ⭐ |
| 보호 | 없음 (검사 안 함) | **bounds 검사로 가능** ⭐ |
| 스와핑 | 어려움 | 가능 |

→ 번역을 실행 시점으로 미뤘기 때문에 **이동·보호·스와핑**이 가능해짐. base 값이 안 변해도 여전히 "동적".

## OS의 역할 (하드웨어만으론 부족)

1. **프로세스 생성 시**: **free list**로 빈 물리 공간 찾아 할당, base/bounds 결정.
2. **종료 시**: 메모리 회수 → free list 반환.
3. **문맥 교환 시**: A의 base/bounds를 **PCB에 저장**, B의 것을 **PCB에서 복원**. (Ch6 레지스터 문맥에 포함)
4. **예외 핸들러 등록·처리**: 경계 위반 시 프로세스 종료 등.
5. **설정의 정당성 보장**: `base + limit ≤ 물리 메모리 크기`, 다른 프로세스와 **겹치지 않게**. ← 하드웨어는 이걸 안 따짐, **OS 책임**.

## 필요한 하드웨어 지원

| 요구사항 | 이유 |
|----------|------|
| 특권 모드(user/kernel) | 특권 연산 구분 |
| base/bounds 레지스터 | 변환·검사용 |
| 변환+경계 검사 회로 | 매 접근마다 빠르게 |
| **base/bounds 변경 = 특권 명령** | OS만 설정 가능 |
| 예외 발생 능력 | 경계·특권 위반 시 |
| 예외 핸들러 등록(특권) | OS가 트랩 테이블 세팅 |

## 하드웨어 vs OS 책임 경계 ★

**"CPU는 명령을 실행만 하는 게 아니라, 디코드하며 합법성을 함께 검사한다."**
```
Fetch → Decode(★ 특권 명령인가? 현재 모드는? ) → Execute(통과 시에만)
```

**왜 OS가 매 명령을 검사할 수 없나:**
1. **사용자 코드 실행 중엔 OS가 CPU에서 돌고 있지 않음.** (Ch6의 그것)
2. 매 명령마다 OS가 개입하면 → 시스템콜 172ns × 명령 수 → **수천 배 느려짐.** "Direct Execution"의 포기.
→ 그래서 **검사를 하드웨어 회로에 박아** 추가 시간 없이(공짜) 수행.

**분담:**
| 시점 | 누가 | 무엇을 |
|------|------|--------|
| 부팅/문맥교환 | **OS** | 규칙 설정(트랩 테이블, base/bounds) |
| 매 명령·매 접근 | **하드웨어** | 모드·경계 확인, 위반 시 **즉시 차단 + 예외** |
| 위반 후 | **OS** | 예외 핸들러에서 판단·처리 |

비유: OS = **입법부**(규칙 제정), 하드웨어 = **현장 경비원**(즉시 제지), 위반 시 경비원이 입법부 호출(트랩).

**사용자가 커널에 임의 진입 가능한가? → 불가.**
- 모드 비트 직접 변경 = 특권 명령 → 하드웨어가 거부.
- 커널 진입은 **트랩으로만**, 진입 지점은 **OS가 트랩 테이블로 지정**. 사용자는 시스템콜 번호만 넘김.
- **단, 커널은 사용자가 넘긴 데이터를 절대 신뢰하지 않음** — 번호·포인터·크기 전부 검증(`copy_from_user` 등). 검증 실수 = 권한 상승 취약점.
- **신뢰 경계(trust boundary)** 개념: 경계를 넘어오는 모든 것을 의심.

## base/bounds의 한계

주소 공간 16KB인데 실제로는 코드+힙+스택 3KB만 사용 → **나머지 13KB도 물리 메모리를 통째로 점유.**

- **내부 단편화(internal fragmentation)**: 할당 영역 **내부**의 낭비.
- (외부 단편화: 할당 블록들 **사이**의 빈틈 — 총 여유는 있는데 연속 공간이 없음.)
- 원인: 주소 공간을 **하나의 연속 덩어리**로 배치하기 때문.
- **해결 방향**: 주소 공간을 **논리적 조각(코드/힙/스택)으로 나눠 따로 배치** → 안 쓰는 가운데 공간은 아예 안 잡음 → **세그멘테이션(Ch16)**.

## 숙제 (relocation.py)

내가 MMU가 되어 손으로 변환. `VA < limit ? VA + base : violation`

```bash
./relocation.py -s 1              # 문제 생성
./relocation.py -s 1 -c           # 정답 확인
./relocation.py -a 1k -p 16k -b 1000 -l 500 -c   # 파라미터 지정
```

**실측 예** (base=13884, limit=290):
- VA 261 → 261 < 290 → **VALID: 14145**
- VA 782, 507, 460, 667 → 전부 290 이상 → **SEGMENTATION VIOLATION**

**관찰**: 주소 공간이 1KB인데 limit이 290이면 VA 290~1023은 전부 위반. 랜덤 주소 대부분이 밖이라 violation이 많음.

**생각해본 것**: `base + limit > 물리 메모리`면? → 존재하지 않는 물리 주소로 번역됨. **하드웨어는 안 따짐**(시키는 대로 계산만) → **OS가 배치 시 검증할 책임**(free list로 충분한 빈 공간 찾기, 겹침 방지).
