# OSTEP Ch 29 — Lock-based Concurrent Data Structures 정리

Ch28이 "락을 어떻게 만드나"였다면, 이 장은 **"락을 어디에 어떻게 거느냐"**.
핵심 교훈: **더 병렬적인 설계가 더 빠른 설계는 아니다.**

---

## 동시성 카운터

가장 단순한 동시성 자료구조 — **공유 정수 하나를 여러 스레드가 증가/감소.**
자료구조가 자명해서(정수 하나) **락 설계 자체에만 집중**할 수 있어 첫 예제로 쓰임.

**실제 용도:** 참조 카운팅(`shared_ptr`, 커널 refcount), 통계 지표(패킷 수, 캐시 히트, 할당 바이트), 세마포어 내부 카운터(Ch31), 조회수·요청 수.

### ① 정확한 카운터 (precise counter)

```c
typedef struct { int value; pthread_mutex_t lock; } counter_t;

void increment(counter_t *c) {
    pthread_mutex_lock(&c->lock);
    c->value++;
    pthread_mutex_unlock(&c->lock);
}
```
**정확성 완벽** — Ch27의 race.c가 이걸로 고쳐짐.

**그런데 확장성이 없음(not scalable):**
```
이상적: 락으로 직렬화되니 시간은 스레드 수에 "비례"해서 증가 (처리량 유지)
실제  : 그보다 더 나쁨 — 초선형 증가
```
원인 둘:
1. **락 경합(contention)** — 대기 스레드가 늘수록 스핀/문맥 교환 오버헤드 증가
2. **캐시 라인 핑퐁** — 여러 코어가 같은 락·같은 `value`를 계속 무효화 (Ch10)

> **완벽한 확장성(perfect scaling)** = 스레드 수에 비례해 성능이 느는 것.

### ② 근사 카운터 (approximate / sloppy counter)

**CPU마다 지역 카운터를 두고, 가끔씩만 전역에 합친다.**

```c
typedef struct {
    int global;  pthread_mutex_t glock;
    int local[NUMCPUS];  pthread_mutex_t llock[NUMCPUS];
    int threshold;                      // S
} counter_t;

void update(counter_t *c, int tid, int amt) {
    int cpu = tid % NUMCPUS;
    lock(&c->llock[cpu]);
    c->local[cpu] += amt;
    if (c->local[cpu] >= c->threshold) {
        lock(&c->glock);
        c->global += c->local[cpu];
        unlock(&c->glock);
        c->local[cpu] = 0;
    }
    unlock(&c->llock[cpu]);
}
```

**왜 빠른가 (2가지):**
- **락이 쪼개져 경합이 거의 없음** — CPU마다 다른 지역 락
- **캐시 라인 분리** — 각 코어가 자기 `local[cpu]`만 건드림

> ⚠ 실제 구현에선 `local[]` 원소를 **캐시 라인 크기(64B)로 패딩**해야 함.
> 안 그러면 `local[0]`과 `local[1]`이 같은 라인에 있어 **거짓 공유(false sharing)** 발생 —
> 논리적으론 안 겹치는데 하드웨어가 같은 라인이라 무효화를 주고받음. Ch10의 함정.

**왜 "sloppy"인가 — 읽기가 부정확:**
```c
int get(counter_t *c) { lock(&c->glock); int v = c->global; unlock(...); return v; }
// 아직 전역에 반영 안 된 지역 값들이 누락됨
```
**최대 오차 = NUMCPUS × S.** (CPU 4개, S=1024면 최대 4096 작게 나옴)

**트레이드오프:**
```
S 크게 → 전역 락 접근 ↓ → 빠름 / 부정확
S 작게 → 정확 / 느림  (S=1이면 원래 카운터와 동일)
```

> **핵심 원리: 정확성을 조금 포기하고 확장성을 얻는다.**
> 리눅스 커널의 **per-CPU counter**(패킷 수, 메모리 통계)가 이 방식.
> **"이 값이 정확해야 하나?"를 먼저 묻는 게 설계의 시작** — 은행 잔고는 안 되지만 조회수는 4096 차이가 무의미.

## 동시성 연결 리스트

### 락 범위 줄이기

```c
void insert(list_t *L, int key) {
    node_t *new = malloc(sizeof(node_t));   // 락 밖
    new->key = key;                          // 락 밖
    lock(&L->lock);
    new->next = L->head;                     // ★ 여기부터 공유 데이터
    L->head = new;
    unlock(&L->lock);
}
```

**판단 기준: "이 시점에 다른 스레드가 이 메모리를 볼 수 있나?"**
`malloc`이 갓 반환한 노드는 **아직 아무도 그 주소를 모름** → 리스트에 연결되기 전까진 사실상 지역 변수.

**`malloc`을 밖으로 뺀 게 특히 중요:** malloc은 내부적으로 자기 락을 쓰고 시간도 걸림. 락 안에서 부르면 그 시간만큼 모두 정지.
→ **"락 잡고 있는 동안 오래 걸리는 일 하지 마라"**의 대표 사례.
(부수 효과: malloc 실패 시 unlock 빼먹는 버그도 사라짐)

### hand-over-hand locking (lock coupling)

리스트 전체에 락 하나면 **한 번에 한 스레드만 순회** → 노드마다 락을 두면?

```
lock(next->lock)      ← 다음을 먼저 잡고
unlock(current->lock) ← 그다음 현재를 놓는다
```

**개념 확인:** "노드 접근이 곧 락"이 아님. **여전히 코드 구간에 대한 락**이고, 바뀐 건 **보호 대상의 세분도** — "리스트 전체" → "노드 하나".

**왜 "다음을 먼저 잡아야" 하나:**
```c
unlock(&current->lock);
// ← 이 틈에 다른 스레드가 current를 삭제하고 free()
lock(&current->next->lock);   // ★ 해제된 메모리 역참조 = use-after-free
```
`current->next`를 읽으려면 `current`가 살아있어야 하는데 락을 놓으면 보장이 없음.
**항상 최소 하나는 쥐고 있어야 발판이 무너지지 않음** (사다리 비유 — 한 손이 다음 칸을 잡은 뒤 다른 손을 뗌).
Ch14의 dangling pointer 문제가 동시성 맥락에서 재등장.

### ★ 그런데 실제로는 단일 락보다 느리다

**노드 1000개 순회 = lock/unlock 1000쌍 = 원자적 연산 2000번.**

```
일반 mov (L1 히트)     : ~1 사이클
원자적 명령 (경합 없음) : ~20~50 사이클      ← 20~50배
원자적 명령 (경합 있음) : 수백 사이클 + 캐시 라인 이동
```
**원자적 명령이 비싼 이유:** 캐시 라인을 **독점(exclusive)** 상태로 가져와야 하고(다른 코어에 있으면 뺏어옴), 메모리 배리어로 **파이프라인도 멈춤.** Ch10 캐시 일관성이 매번 돎.

```
단일 락        : 원자적 연산 2번 + 노드 1000개 순회
hand-over-hand : 원자적 연산 2000번 + 노드 1000개 순회
```
**노드 검사는 몇 사이클인데 락은 그 20~50배** → 락 오버헤드가 실제 작업을 압도.

> ## 이 장의 핵심 교훈
> **"더 병렬적인 설계"가 "더 빠른 설계"는 아니다.**
> 락을 잘게 쪼개면 이론상 동시성은 오르지만 — 락 연산 비용 누적, 코드 복잡도·데드락 위험 증가, 캐시 지역성 악화.
>
> **OSTEP의 조언: 단순한 방식이 충분히 빠르면 그냥 써라.** 먼저 단순하게 만들고, **측정해서** 병목이 확인되면 그때 정교하게. (성급한 최적화 경계)
>
> Ch22와 같은 구조 — "정책이 의미 있는 건 지역성이 있고 메모리가 부족할 때뿐". **병목이 아닌 곳을 최적화하면 이득이 없다.**

## 동시성 큐 (Michael-Scott)

**락을 head용 / tail용 두 개로 분리.**
- enqueue는 tail만, dequeue는 head만 건드림 → **동시에 가능**
- **더미 노드(dummy node)**를 하나 둠 → 큐가 비었을 때 head와 tail이 겹쳐 두 락이 충돌하는 걸 방지

## 동시성 해시 테이블

**버킷마다 락 하나.** 서로 다른 버킷을 건드리는 스레드끼리는 완전히 병렬.
**이 장에서 확장성이 가장 좋은 예.**

### ★ 왜 해시 테이블은 확장되고 리스트는 안 되나

**"락 하나를 잡고 몇 번의 작업을 하느냐"가 핵심.**

```
연결 리스트 (hand-over-hand):
  노드 1000개 순회에 lock/unlock 1000쌍
  → 락 1개당 작업 = 노드 1개 검사(몇 사이클)
  → 락 비용 ≫ 작업 비용  ❌

해시 테이블 (버킷당 락):
  삽입/조회에 lock/unlock 딱 1쌍
  → 락 1개당 작업 = 그 버킷 전체 처리
  → 락 비용을 한 번만 지불  ✅
```
해시 테이블은 **`hash(key) % NBUCKETS`로 어느 버킷인지 바로 계산** → 순회 불필요.
연결 리스트는 **처음부터 훑어야** 하므로 지나는 모든 노드의 락을 거쳐야 함.

**세분화가 이득이 되는 조건:**

| | 좋은 세분화 | 나쁜 세분화 |
|--|--|--|
| 락당 작업량 | 큼 (락 비용이 묻힘) | 작음 (락 비용이 지배) |
| 접근 패턴 | **독립적** (버킷끼리 무관) | **순차적** (앞을 거쳐야 뒤로) |
| 예 | 해시 테이블 버킷, per-CPU 카운터 | 연결 리스트 노드 |

> **"자원이 자연스럽게 독립적으로 나뉘는가"가 핵심.**
> sloppy counter도 같은 원리 — CPU별 지역 카운터는 완전히 독립이라 잘 쪼개짐.
> **병렬 프로그래밍의 일반 원리: 먼저 "독립적으로 나눌 수 있는 축"을 찾아라.** 억지로 쪼개면 오버헤드만 늘어남.

## 실전 포인트

- **동시성 카운터의 확장성 문제 → sloppy counter**로 푸는 흐름. 오차 상한 `NUMCPUS × S`까지 말할 수 있어야.
- **거짓 공유(false sharing)와 캐시 라인 패딩** — 성능 면접 단골.
- **락 범위 최소화** — malloc/초기화를 밖으로. 판단 기준은 "다른 스레드가 이 메모리를 볼 수 있나".
- **hand-over-hand의 순서**(다음 먼저 잡고 현재 놓기)와 그 이유(use-after-free).
- **"더 병렬적 ≠ 더 빠름"** — 원자적 명령 비용(20~50 사이클)을 근거로.
- **해시 테이블 vs 리스트의 확장성 차이** = 락당 작업량 + 접근 패턴의 독립성.
- 설계 순서: **단순하게 → 측정 → 병목이면 세분화.**
