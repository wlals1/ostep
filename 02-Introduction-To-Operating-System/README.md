# OSTEP Ch 2 — Introduction 정리

OS가 무슨 문제를 푸는지의 **큰 그림**. 네 개의 작은 프로그램(mem, cpu, threads, io)으로
운영체제가 제공하는 **네 가지 조각**을 맛본다.

---

## OS가 갖추는 것 (네 조각)

| 조각 | 핵심 질문 | 예제 |
|------|-----------|------|
| **CPU 가상화** | CPU 몇 개로 어떻게 프로세스 여럿을 동시에 돌리나 | cpu.c |
| **메모리 가상화** | 프로그램마다 어떻게 자기만의 메모리를 갖는 듯 보이나 | mem.c |
| **동시성** | 여러 실행 흐름이 공유 자원을 어떻게 안전하게 다루나 | threads.c |
| **영속성** | 전원이 꺼져도 데이터를 어떻게 보존하나 | io.c |

**OS = 환상(illusion)을 만드는 자 + 자원 관리자.**
- 각 프로그램에 "CPU·메모리를 혼자 다 쓰는 것 같은 환상"을 준다.
- 실제로는 제한된 자원(CPU 코어, 물리 메모리)을 여러 프로세스에 나눠주고 보호·격리한다.

---

## cpu.c — CPU 가상화

무한 루프로 인자를 1초마다 출력. 여러 개 동시에 돌리면?

- **CPU는 1개라도 프로세스 여럿이 "동시에" 도는 듯 보임** = 시간분할(time-sharing). 실제론 매우 빠르게 번갈아 실행(context switch).
- **누가 프로세스를 강제로 멈추나?** → **타이머 인터럽트.** OS가 미리 타이머를 세팅 → 시간 되면 하드웨어가 강제로 제어권을 OS로. Spin(busy-wait)으로 CPU를 안 놓는 프로세스도 뺏김.
- 실행 흐름은 항상 **A → OS → B → OS → ...** (OS를 경유해 전환).

**나눈 고민:**
- **트랩 vs 인터럽트**: 트랩=프로세스가 자발적/동기(시스템콜, 0으로 나누기, page fault). 인터럽트=외부 하드웨어가 비자발적/비동기(타이머, 디스크, 키보드). "명령이 유발했나 vs 바깥에서 왔나"가 갈림길.
- **벽시계 시간 ≠ CPU 시간**: Spin(1)은 벽시계 1초를 재지, CPU를 1초 쓴 게 아님. 프로세스 많으면 격차 벌어짐.
- **"OS가 잘못하는 것 아냐?"** → 아니. OS는 논리적 "연산"의 경계를 모름(기계는 명령 3개일 뿐). 언제든 선점할 수 있어야 통제권을 보장. 원자성은 프로그래머 몫.
- Ctrl+C = SIGINT, 백그라운드(`&`)엔 안 닿음 → 포그라운드 프로세스 그룹 개념.

## mem.c — 메모리 가상화

`malloc`한 주소를 출력하고 값을 1씩 증가. 두 개 동시에 돌리면?

- **각 프로세스는 자기만의 사적 주소 공간**을 가짐. 같은 코드라도 값이 안 섞임(격리).
- **같은 가상 주소라도 다른 물리 메모리**로 매핑됨 → 값 충돌 없음. (ASLR로 요즘은 주소도 무작위화.)
- 번역은 **페이지 테이블**(프로세스마다 하나) + **MMU**(하드웨어)가 담당. context switch 때 **PCB에서 페이지 테이블 주소를 CR3에 로드**.

**나눈 고민:**
- **`(unsigned)p`의 버그**: 포인터(8바이트)를 4바이트 정수로 → truncation. `%p`엔 `void*`를 줘야(포인터→포인터, 잘림 없음).
- **`void*` vs `uintptr_t`**: void*는 포인터(주소), uintptr_t는 정수. 이름에 낚이지 말 것.
- **타입은 컴파일 타임 개념**: CPU는 런타임에 바이트만 봄. 타입은 컴파일러가 코드 뽑는 데 쓰는 정보.
- **self-contained 헤더**: `NULL` 못 찾음 → `<stddef.h>` 누락. 헤더는 자기가 필요한 걸 include해야.
- **친구의 공유 메모리 오해 반박**: "같은 가상 주소니 한쪽 수정이 다른 쪽에 영향" → 틀림. 페이지 테이블이 각자 다른 물리 프레임을 가리킴. (단, `mmap(MAP_SHARED)` 등 명시적 공유는 예외.)

## threads.c — 동시성

두 스레드가 공유 변수 `counter`를 각각 loops번 증가. 최종값이 2×loops?

- **작은 loops면 2000 정상, 큰 값이면 매번 다른 값(<2×loops)** → **race condition.**
- 원인: **`counter++`는 원자적이지 않음** = load → add → store 3단계. 그 중간에 타이머 인터럽트로 다른 스레드가 끼어들면 **lost update**(갱신 손실).
- 해결: 그 3단계를 쪼갤 수 없는 단위로 묶어야 → **락(mutex)**. (Ch 28~)

**나눈 고민:**
- **volatile은 race를 못 막는다**: volatile = **visibility(매번 메모리 접근)** 보장일 뿐, **atomicity(load-add-store 묶기)**는 아님. 그래서 코드에 volatile이 있는데도 깨짐.
- **동시성(concurrency) vs 병렬성(parallelism)**: 1코어=번갈아(논리적 동시), 멀티코어=진짜 동시(물리적). 내 노트북 8코어라 진짜 병렬 → race 더 명백.
- **컴파일 에러 vs 링크 에러**: `pthread_t` 못 찾음=헤더(`pthread.h`) 문제(컴파일). `undefined reference to pthread_create`=라이브러리 연결 문제(`-pthread`, 링크).
- include guard(`#ifndef ...`), `Pthread_*` 대문자 = 에러 체크 assert 래퍼.

## io.c — 영속성

파일을 열어 "hello world"를 씀. 화면엔 아무것도 안 나옴 → 파일에 남음.

- **메모리(DRAM)는 휘발성** → 전원 꺼지면 사라짐. 영속 저장엔 **SSD/HDD** + **파일 시스템**(OS 구성요소) 필요.
- `open`/`write`/`close` = **시스템콜(트랩)**로 파일 시스템에 요청.
- **파일은 사적이 아니라 공유**됨 (CPU·메모리와 다름!). 파일은 프로세스보다 오래 살아남아야 하니(=영속성) 사적일 수 없음.
- **왜 영속성이 어렵나:** ① 디스크가 느려 성능 최적화(캐싱/버퍼링) 필요 ② write 도중 크래시 시 자료구조 **불일치** → crash consistency(**journaling**) 필요. (Ch 36~)

**나눈 고민:**
- **`assert(rc = 13)` 버그**: `=`(대입) vs `==`(비교). 대입이라 항상 참 → 검사 무력화. `-Wall`이 경고.
- **13바이트 write**: "hello world\n"(12) + 널 문자('\0') = 13. `xxd`로 널 바이트 확인.
- **`unistd.h`**: UNIX 표준 시스템콜(getpid, write, close, fork...) 선언. write/close 못 찾으면 이거 누락.

---

## 반복 확인한 패턴 (누적 복습)

- **시스템 함수 반환값 항상 체크** (fopen NULL, write 실패 등).
- **헤더 누락 = "이 이름 모른다" 컴파일 에러** (stddef.h, pthread.h, unistd.h).
- **타입/논리적 연산은 컴파일 타임, CPU는 바이트/명령만** — 원자성·트랩 이해의 뿌리.
- **가상 주소 ≠ 물리 주소** — 격리의 핵심, 뒤 챕터에서 계속.
