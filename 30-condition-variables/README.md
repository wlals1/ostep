# OSTEP Ch 30 — Condition Variables 정리

Ch28에서 남긴 **lost wakeup 문제**의 정식 해답.
조건 변수 = **어떤 조건이 만족될 때까지 잠들어 있는 대기실.** 그게 전부다.

---

## ★ 결론부터 — 외울 건 관용구 하나

```c
// 기다리는 쪽
pthread_mutex_lock(&m);
while (조건이_아직_아님)
    pthread_cond_wait(&cv, &m);
... 일 ...
pthread_mutex_unlock(&m);

// 알리는 쪽
pthread_mutex_lock(&m);
상태를_바꿈;
pthread_cond_signal(&cv);
pthread_mutex_unlock(&m);
```

**아래의 세 규칙은 전부 이 틀 안에 이미 들어있음:**
- 락과 함께 쓴다 → 틀에 `lock`이 있음
- 상태 변수를 둔다 → 틀에 `조건`이 있음
- `while`로 감싼다 → 틀이 `while`임

**"왜"를 몰라도 이 틀을 쓰면 안전하다.** 왜를 파는 건 나중에 이상한 버그를 진단하기 위한 것.

---

## 왜 필요한가

Ch27에서 본 두 가지 기다리는 법:
```c
while (done == 0) ;              // 스핀. CPU 100% 태움
pthread_cond_wait(&c, &m);       // 잠듦. CPU 0
```
조건 변수는 **"잠들어서 기다리기"를 제공하는 도구.**

```c
pthread_cond_wait(&c, &m);      // "이 대기실에서 잘게"
pthread_cond_signal(&c);        // "대기실에 있는 놈 하나 깨워"
pthread_cond_broadcast(&c);     // "전부 깨워"
```

### 전체 그림

```
[부모]                          [자식]
lock(m)
done == 0 이네
cond_wait(c, m) ─┐
   락을 놓고     │
   대기실에서 잠 │
                 │              lock(m)      ← 부모가 락을 놓았으니 잡을 수 있음
                 │              done = 1
                 │              signal(c) ──┐
   깨어남 ←──────┴─────────────────────────┘
   락을 다시 잡음
   done == 1 → 진행
unlock(m)
```

---

## 규칙 ① 락과 함께 쓴다

### cond_wait이 뮤텍스를 받는 이유

`cond_wait`을 부를 때 **이미 락을 쥔 상태**임. 락을 쥔 채 잠들면 → 자식이 `done=1`을 하려 `lock(&m)`을 시도 → **아무도 못 들어옴 → 데드락.**

**`cond_wait`이 하는 일:**
```
① 뮤텍스를 놓는다 (unlock)
② 잠든다 (Blocked)
   ... signal 받으면 ...
③ 깨어나서 뮤텍스를 다시 잡는다 (lock)
④ 반환
```
**①과 ②가 원자적**이어야 함. 그래서 어느 락인지 알려주려고 인자로 받는 것.
호출자 입장에선 "락을 쥐고 들어가서 락을 쥐고 나온다"라 자연스러워 보이고, 중간에 놓았다 잡는 건 안 보임.

### 락이 없으면 — lost wakeup

```c
if (done == 0)
    cond_wait(&c);      // 락 없이 잠든다고 가정
```
```
부모: done == 0 확인 ✅
      [문맥 교환]
자식: done = 1
자식: signal(&c)        ← 대기실이 비어 있음. 신호가 허공에 날아감
      [부모로 복귀]
부모: cond_wait(&c)     ← 이제야 잠듦 → 깨워줄 사람 없음 → 영원히 잠
```

**Ch26의 깨진 락과 똑같은 구조:**
```c
while (flag == 1) ;   // 확인
flag = 1;             // 설정      ← 사이에 틈
if (done == 0)        // 확인
    cond_wait(&c);    // 잠들기    ← 사이에 틈
```
> **"확인하고 행동하기" 사이에 틈이 있으면 깨진다.** read-modify-write든 check-then-sleep이든.

락이 `done` 확인 구간을 보호하고, **잠드는 것과 동시에 풀리니** 틈이 없음.
→ 그래서 `pthread_cond_wait`의 시그니처에 뮤텍스가 **강제**로 들어감. API가 "락 없이 쓰는 실수"를 원천 차단.

> Ch28에서 `park()` 앞에 `setpark()`이 필요했던 이유가 정확히 이것. **조건 변수는 그 해법을 API 안에 내장**한 것.

---

## 규칙 ② 상태 변수를 둔다

**조건 변수는 기억이 없다.** 대기자가 없을 때 온 signal은 그냥 증발함.

```c
// done 없이 — 자식이 먼저 실행되면
자식: lock; cond_signal(&c);   ← 대기실이 비어 있음. 신호 소멸
      unlock; 종료
부모: lock; cond_wait(&c, &m); ← 이제야 잠듦. 신호 보낼 자식은 이미 죽음
      → 영원히 잠 ★
```

```c
// done이 있으면
자식: lock; done = 1; signal; unlock    ← done에 "일어났다"가 기록됨
부모: lock; while (done == 0) wait;     ← 이미 1이니 아예 안 잠듦 ✅
```

| | 역할 | 성질 |
|--|--|--|
| **상태 변수 (`done`)** | **사실의 기록.** "일이 끝났나?" | **지속적** — 남아 있음 |
| **조건 변수 (`c`)** | **깨우기 신호.** "확인해봐" | **순간적** — 놓치면 사라짐 |

> **조건 변수는 기억이 없으니, 상태는 별도 변수에 기록해야 한다.**

**그래서 셋이 항상 세트:**
```c
pthread_mutex_t m;   // 상태 변수를 보호
int done;            // 실제 상태 (기억)
pthread_cond_t c;    // 대기/깨우기 (신호)
```
Ch27의 `main-signal-cv.c`가 이 셋을 `synchronizer_t` 구조체로 묶은 게 이것 — **"이 셋은 함께 다닌다"를 코드로 드러낸 것.**

## 규칙 ③ while로 감싼다 (Mesa semantics)

### while은 스핀이 아니다 ★ (헷갈렸던 것)

```c
while (done == 0)
    pthread_cond_wait(&c, &m);
```
- `cond_wait`은 **블로킹 호출** — 거기서 스레드가 멈춤. 잠든 동안 **아무 명령도 안 나감. CPU 0%**
- `signal`을 받아 깨어나야 `cond_wait`이 반환 → **그제야** while로 돌아가 재확인
- **즉 while 루프는 "깨어날 때마다" 한 번씩만 돎.** 신호가 없으면 영원히 한 바퀴도 안 돔

```c
while (done == 0) ;                    // 1초에 수억 번. CPU 100%
while (done == 0) cond_wait(&c, &m);   // 깨어날 때만. 보통 1~2번. CPU 0%
```
**같은 while인데 안에 뭐가 있느냐로 완전히 다름.** (`read()`가 데이터 올 때까지 반환 안 하는 것과 같음)

### 왜 if면 안 되나

**단순한 예제(자식 1, 부모 1, done이 한 번만 1)에선 `if`도 거의 동작함. 그런데:**

**⓵ spurious wakeup** — POSIX가 "아무도 signal 안 했는데 반환할 수 있다"고 **허용함**. 확률은 낮아도 표준이 허용하는 이상 언젠가 일어남.

**⓶ 진짜 문제 — 대기자가 둘 이상이면**
```
버퍼 비어있음(count=0)
소비자1: lock → count==0 → wait (잠듦)
생산자 : lock → 항목 넣음(count=1) → signal → unlock
         signal이 소비자1을 깨움. 그런데 소비자1은 아직 "깨어나는 중"
         (락을 다시 잡아야 반환되니까)
소비자2: lock 획득 ← 소비자1보다 먼저!
         count==1 → 꺼감 → count=0 → unlock
소비자1: 이제야 락 잡고 wait에서 반환
         if → 확인 없이 진행 → ★ 빈 버퍼에서 꺼냄 → 버그
         while → count==0 재확인 → 다시 잠듦 ✅
```

> **핵심: `signal`은 락을 넘겨주지 않는다.** 깨어난 스레드가 락을 다시 잡기까지 **틈이 있고**, 그 사이 다른 스레드가 끼어들어 조건을 무효화할 수 있음.

**Mesa semantics:**
> signal = **"조건이 바뀌었을 수도 있으니 가서 확인해봐"**라는 힌트
> ≠ "네 차례고 조건은 참이야"라는 보장

(반대인 **Hoare semantics**는 깨워진 스레드가 즉시 실행되고 조건이 참임을 보장하지만, 구현이 비싸서 실제 시스템은 거의 다 Mesa.)

**실무 규칙 한 줄: `pthread_cond_wait`은 항상 `while` 안에서. 예외 없음.**
지금 예제엔 과해 보여도 코드가 자라면 반드시 필요해지고, 그때 고치려면 이미 늦음.

## 생산자-소비자 (bounded buffer)

### 무엇을 보장해야 하나

소비자들은 **서로 교체 가능한 일꾼**. 누가 어느 항목을 가져가든 무관.
```
① 소비자가 빈 버퍼에서 꺼내면 안 됨
② 생산자가 꽉 찬 버퍼에 넣으면 안 됨
③ 한 항목을 두 소비자가 가져가면 안 됨 (중복)
④ 항목이 유실되면 안 됨
```
**순서는 요구사항이 아님.** 순서가 중요하면 그건 다른 문제(파이프라인·시퀀싱).

### 실제 사례 — 가장 흔한 동시성 패턴

```bash
grep foo big.txt | wc -l    # 셸 파이프가 정확히 이것
```
`grep`=생산자, `wc`=소비자, 파이프=버퍼. 버퍼가 꽉 차면 grep이 멈추고, 비면 wc가 멈춤.
- **웹 서버**: 요청 수신 스레드 → 작업 큐 → 워커 스레드들
- **로깅**: 앱 스레드들이 큐에 넣고 전용 스레드가 파일에 씀
- **미디어**: 디코더가 프레임 생산, 렌더러가 소비

**가치: 생산 속도와 소비 속도가 달라도 서로 기다리며 조율됨.** 버퍼가 완충.

**왜 유한(bounded)한가:** 무한이면 생산자가 소비자보다 빠를 때 메모리를 다 먹음. 버퍼가 차면 생산자를 멈추는 **역압(backpressure)**이 필요.
→ **양쪽 다 기다릴 수 있어야** 하고, 그래서 조건 변수가 둘 필요.

### 코드 — 대칭 구조

```c
cond_t empty, fill;
mutex_t m;
int count = 0;

void *producer(void *arg) {
    lock(&m);
    while (count == N)          // 꽉 찼으면 기다림
        cond_wait(&empty, &m);  // "빈 자리 생겼다"를 기다림
    put(i);
    cond_signal(&fill);         // "채웠다"고 소비자에게
    unlock(&m);
}

void *consumer(void *arg) {
    lock(&m);
    while (count == 0)          // 비었으면 기다림
        cond_wait(&fill, &m);   // "채워졌다"를 기다림
    int v = get();
    cond_signal(&empty);        // "자리 났다"고 생산자에게
    unlock(&m);
}
```
```
생산자: 꽉 참(count==N) 을 피해 대기 → 넣고  → "채웠다"(fill) 신호
소비자: 빔(count==0)    을 피해 대기 → 꺼내고 → "비웠다"(empty) 신호
```

### ★ 왜 조건 변수가 두 개여야 하나

**하나(`cond`)만 쓰면 데드락.** 버퍼 크기 1, 소비자 2(C1,C2), 생산자 1(P):
```
C1: lock → count==0 → wait(cond)    [대기실: C1]
C2: lock → count==0 → wait(cond)    [대기실: C1,C2]
P : lock → 채움 → signal(cond) → unlock
    → C1이 깨어남                    [대기실: C2]
C1: 락 잡고 → 꺼냄(count=0) → signal(cond) → unlock
    ★ C1이 깨우려는 건 "생산자"인데 대기실엔 C2뿐 → C2가 깨어남
C2: 락 잡고 → count==0 → 다시 wait   [대기실: C2]
→ P도 버퍼가 차서 자고 있었다면 전원 취침. 데드락.
```

> **대기실이 하나면 "누구를 깨워야 하는지" 구분할 수 없다.**
> 소비자가 꺼낸 뒤 깨워야 할 건 **생산자**인데, signal은 대기실의 **아무나** 깨움.

**해결:**
| | 방법 | 평가 |
|--|--|--|
| **① 조건 변수 분리** ✅ | `empty`(생산자 방) / `fill`(소비자 방) | 정석. 정확히 원하는 놈만 깨움 |
| **② broadcast** | `cond_broadcast(&cond)`로 전부 깨워 각자 while로 확인 | 동작은 함. 불필요한 스레드까지 깨워 **성능 나쁨** |

> **원칙: 기다리는 이유가 다르면 조건 변수를 나눠라.**

여기서 `while`의 가치도 재확인 — C2가 엉뚱하게 깨어났을 때 `if`였다면 **빈 버퍼에서 꺼냈을 것.**

### covering condition

어떤 스레드를 깨워야 할지 **정확히 알 수 없을 때**는 `broadcast`로 전부 깨우고 각자 `while`로 판단하게 함.
(예: 메모리 할당기 — 100바이트 반납 시 10바이트 대기자를 깨울지 200바이트 대기자를 깨울지 모름)
**정확성은 확보되지만 불필요한 깨우기 비용을 지불.** 정확한 조건 분리가 어려울 때의 안전한 선택.

## 왜 이 장이 어려운가 (정직하게)

**단일 스레드는 실행 순서가 하나** — 위에서 아래로. 코드를 읽으면 무슨 일이 일어날지 알 수 있음.
**스레드 2개면 실행 순서가 수백만 가지** — 그중 하나만 깨져도 버그고, 그 하나를 머릿속으로 찾아야 함.
**문제 자체가 어려운 것.** 동시성 버그가 업계에서 제일 악명 높은 이유.

**그런데 실무 부담은 작음:**
- 위의 **관용구 하나**만 지키면 안전
- 실무에선 직접 안 만듦 — Go 채널, Java `BlockingQueue`, C++ `condition_variable`+큐, 파이썬 `queue.Queue`
- **배우는 이유는 "안에서 어떻게 동작하는지" 알기 위해서.** 잘못 썼을 때 왜 멈췄는지 진단하려고.

---

## 실전 포인트

- **`cond_wait`이 뮤텍스를 받는 이유** = 원자적으로 놓고 잠들기 (lost wakeup 방지). 면접 단골.
- **왜 `while`이고 `if`가 아닌가** = Mesa semantics + spurious wakeup. 구체적 시나리오로 답할 것.
- **상태 변수가 왜 필요한가** = 조건 변수는 기억이 없음.
- **조건 변수를 왜 둘로 나누나** = 대기실이 하나면 대상을 구분 못 함 → 데드락.
- **signal vs broadcast** 선택 기준, covering condition.
- **락 / 상태 변수 / 조건 변수 셋은 세트**로 다닌다.
