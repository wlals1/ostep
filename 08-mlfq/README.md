# OSTEP Ch 8 — Multi-Level Feedback Queue (MLFQ) 정리

Ch7의 딜레마 해결: **실행시간을 모르면서도** 반환(짧은 작업 우선)과 응답(인터랙티브 빠른 반응)을 **둘 다** 잘하기.
핵심 통찰: **미래(실행시간)를 예측하지 말고 과거 행동을 관찰**해 추측 = feedback.

---

## 구조

- 여러 개의 **우선순위 큐**. 높은 큐 = 높은 우선순위.
- 각 작업의 우선순위를 **관찰된 행동**으로 조정.
- 큐들은 **커널 메모리의 자료구조**(RUNNABLE PCB들을 우선순위별로 묶은 리스트). 각 PCB에 우선순위·남은 슬라이스·배당 소진량 필드.

## 5개 규칙 (최종)

- **규칙 1:** 우선순위(A) > 우선순위(B) → A 실행.
- **규칙 2:** 우선순위 같으면 → RR.
- **규칙 3:** 새 작업은 **최상위 큐**에서 시작 (낙관적: 일단 짧다고 가정).
- **규칙 4(개정):** 어떤 레벨에서 **CPU 총 사용량이 배당(allotment)을 넘으면 강등** (I/O로 끊었든 상관없이 누적).
- **규칙 5:** 매 S초마다 **모든 작업을 최상위로 부스트**.

**왜 SJF를 흉내내나:**
- 인터랙티브(I/O 자주) → 배당 천천히 참 → 높은 우선순위 유지 → 빠른 응답.
- CPU바운드(슬라이스 꽉 씀) → 배당 소진 → 계단식 강등 → 바닥 → 짧은 애들이 먼저(반환↑).
- 실행시간 몰라도 "I/O 자주 하나 / CPU 계속 쓰나"만 관찰해 자동 분류.

**방향 주의 (내가 처음 반대로 생각했던 것):** I/O 자주(인터랙티브)를 **우대**, CPU 독식을 **강등.** 목표가 인터랙티브 응답성 + 짧은 작업 우선이라서.

---

## 기본 MLFQ의 3 허점과 해결

| 허점 | 문제 | 해결 |
|------|------|------|
| **Starvation** | 인터랙티브 계속 오면 바닥 긴 작업 영영 못 돎 | **규칙5 부스트** (주기적 전원 최상위) |
| **Gaming** | 슬라이스 끝 직전 짧은 I/O로 강등 회피, CPU 독식 | **규칙4 개정** (한 번이 아니라 누적 CPU로 강등) |
| **행동 변화** | CPU→인터랙티브 바뀐 작업이 바닥에 갇힘(승격 없음) | **규칙5 부스트** |

- **starvation ≠ convoy**: convoy는 잠깐 기다림, starvation은 영원히 못 돎.
- 규칙4 개정 = **누적 CPU 시간**이 배당 넘으면 강등 → I/O로 끊어도 리셋 안 됨 → gaming 무력화.

## 튜닝 (voo-doo constants)

- 큐 개수, 큐별 슬라이스, 배당, 부스트 주기 S.
- **높은 큐 = 슬라이스 짧게, 낮은 큐 = 길게** (피라미드):
  - 높은 큐 = 인터랙티브 → 어차피 I/O로 금방 CPU 놓음 → 짧아도 되고, 짧아야 여러 개가 빠릿하게 번갈아.
  - 낮은 큐 = CPU바운드 → 길게 줘서 문맥교환(Ch6 비용) 절약.

## 정책 vs 메커니즘 (중요 원칙)

- **MLFQ(Ch8) = 정책**("다음 누구를 돌릴지").
- **Ch6 = 메커니즘**(타이머 인터럽트 + 문맥교환 = "어떻게 바꾸나").
- 스케줄러 흐름: 타이머 인터럽트 → 커널 진입 → MLFQ 규칙으로 다음 선택(배당/부스트 체크) → swtch로 문맥교환 + CR3 교체.
- 메커니즘 고정, **정책만 갈아끼움** (리눅스 O(1)→CFS→EEVDF).

**곁가지로 정리한 것:**
- 타이머는 **인터럽트**(시스템콜 아님). 핸들러는 매 틱 스케줄러 호출이 아니라 **슬라이스 소진 시에만**.
- **타이머 틱 주기 ≠ 슬라이스**: 틱이 훨씬 촘촘(예 1ms), 슬라이스는 틱 여러 번(예 10ms). 틱마다 카운터 감소, 0이면 재스케줄.
- 스케줄러 호출 계기: 타이머(선점) + I/O·종료·sleep(자발적).
- 슬라이스/우선순위/배당 카운터 = **PCB에 저장**(커널 스택 아님, 지속적 스케줄링 상태라서). mlfq.py의 `PRIORITY/TICKS/ALLOT`이 이 필드.

## 숙제 (mlfq.py) — 실험으로 확인한 것

작업 정의: `-l 시작,실행,ioFreq` (ioFreq=0이면 I/O 없음). `-c`로 검증.

- **기본 강등**: `-l 0,20,0 -n 3 -q 10 -a 1` → 0~10 Q[2], 10~20 Q[1], 반환 20. 배당 소진하며 계단식 강등.
- **인터랙티브 우대 + overlap**: `-l 0,200,0:0,20,2` → 인터랙티브 Job1이 높은 우선순위 유지하며 빠릿 반응, **Job1이 I/O로 빠진 틈에 CPU바운드 Job0이 실행(overlap, CPU 안 놀림)**. Job1 끝나면 Job0이 바닥에서 마저.
- **gaming 재현**: `-S` (옛 규칙4, I/O 내면 배당 리셋).
- **부스트로 starvation 해결**: `-B N`.

**직접 찾은 반례 (중요):**
- **MLFQ를 RR로 만들려면? → `-n 1`(큐 1개)** 이 정답. 강등할 아래 큐가 없어 단일 레벨 RR.
- **부스트로 RR 만들기는 안 됨.** 부스트 주기 < 슬라이스로 하면 → 강등 무력화 + **부스트는 실행 중 프로세스를 안 바꿈**(승격 도구지 선점 도구 아님) → 현재 프로세스가 계속 돌아 **FIFO**가 됨 (RR 아님!).
- 교훈: **부스트는 승격(starvation 방지)용이지 실행 순서를 RR로 만드는 도구가 아니다.** 시뮬레이터로 돌려 "어? FIFO네" 반례를 직접 확인.
