# OSTEP Ch 5 숙제 — fork / exec / wait 정리

프로세스 API 8문제를 직접 코딩하며 익힌 것. `q1.c`~`q8.c` 참고.

## Q1 — fork와 변수

fork 전에 `x=100` 설정 후 fork → 자식·부모가 각각 x를 바꾸면?

- **자식은 x=100을 봄**(복사본), 이후 각자 바꿔도 **서로 안 보임.**
- fork는 **주소 공간을 복사** → 부모·자식 독립(격리).
- 실험: `&x`가 부모·자식에서 **같은 가상 주소**인데 값은 다름(200 vs 100). → **같은 가상 주소, 다른 물리 프레임** (mem.c 그대로).
- 실제 메커니즘 = **copy-on-write(COW)**: fork 시 페이지 공유(읽기 전용) → **쓰는 순간 그 페이지(4KB)만** 복사. 전체 아님, lazy.

## Q2 — fork와 파일 fd

open 후 fork → 부모·자식이 fd 공유?

- **fd 번호는 복사**되지만, 그 fd가 가리키는 **"열린 파일 서술자"(offset 담김)는 공유.**
- 그래서 동시에 쓰면 **덮어쓰기 없이 offset이 같이 전진**해 둘 다 보존 (실험: "parent child" 둘 다 남음).
- 변수(복사)와 대비: 변수는 독립, fd offset은 공유.

## Q3 — wait 없이 자식 먼저 출력 보장

- **sleep()** = "1초면 끝나겠지" **타이밍 도박** → 보장 아님(스케줄러가 부모를 먼저 깨울 수 있음).
- **pipe** = 진짜 보장. 부모가 `read(p[0])`로 **blocked** → 자식이 "hello" 출력 후 `write(p[1])` → 부모 깨어남 → "goodbye". **데이터 의존성**이 순서를 강제.
- 교훈: **순서 보장 = 동기화(pipe/wait), 타이밍 트릭 아님.**

## Q4 — exec 변종 (execl/execlp/execle/execv/execvp/execvpe)

- 이름의 글자가 차이: **`l`(list) vs `v`(vector)** = 인자 전달 방식 / **`p`** = PATH 검색 / **`e`** = 환경변수 직접 지정.
- **진짜 시스템콜은 `execve()` 하나**, 나머지는 libc 편의 래퍼.
- 왜 많나: **상황별 편의**(인자 개수·PATH 필요·환경 제어).

## Q5 — wait() 반환값

- 성공 = **종료된 자식의 pid**, 실패(**자식 없음**) = **-1** (0 아님).
- **좀비(zombie)**: 종료됐지만 부모가 아직 안 거둔 자식. `wait()`가 **거둬야(reap)** OS가 흔적 정리.
- 자식이 부모보다 먼저 끝나도 좀비로 남아 나중에 reap 가능.
- (내부: 자식 종료 시 부모에게 **SIGCHLD** 시그널.)

## Q6 — waitpid()

- `waitpid(pid, &status, options)`: **특정 자식** 지정 + `WNOHANG`(논블로킹).
- **wait() 한 번 = 자식 하나만 reap.** 여럿이면 여러 번 호출.
- **주의:** waitpid는 **거두는 대상**을 통제할 뿐, **자식의 실행 순서는 통제 못 함**(스케줄러 몫).
- 유용: 자식 여럿 중 특정 자식 대기, 또는 막히지 않고 상태만 확인.

## Q7 — close(STDOUT_FILENO) 후 printf

- fd 1(stdout) 닫음 → printf의 write가 **실패(EBADF)** → 출력 **사라짐**(에러도 조용).
- **자식이 close해도 부모 출력은 나옴** → `close`는 **그 프로세스의 fd 테이블에만** 적용(프로세스별).

## Q8 — pipe로 두 자식 잇기 = `ls | wc`

```c
pipe(p);
// 자식1(ls): dup2(p[1], STDOUT_FILENO)  → stdout을 파이프 쓰기 끝으로
// 자식2(wc): dup2(p[0], STDIN_FILENO)   → stdin을 파이프 읽기 끝으로
// 각 자식: 안 쓰는 파이프 끝 close
// 부모: p[0], p[1] 둘 다 close + waitpid 둘
```
- `|` = **한 프로세스의 stdout을 다음 프로세스의 stdin에 연결.** 셸이 pipe+dup2로 구현.
- **안 쓰는 끝 close 필수:** 읽기 쪽(wc)은 **모든 쓰기 끝(p[1])이 닫혀야 EOF**를 봄. 하나라도 열려있으면 **영원히 hang.**

## 이번에 잡은 핵심 개념

### fd 3층 모델
```
① fd 테이블 (프로세스별, fork 때 복사)  →  ② 열린 파일 서술자 (공유, offset)  →  ③ 실제 파일
```
- **①은 프로세스마다 따로** (open/close after fork는 자기 테이블만)
- **②는 fork 전에 연 fd가 상속되면 공유** (Q2 offset 공유의 정체)
- 공유 여부의 기준 = **fork 시점**: fork 전에 연 것 = 상속(공유), fork 후 조작 = 각자.

### dup2(oldfd, newfd)
- **newfd를 oldfd와 같은 대상을 가리키게** (바뀌는 건 newfd). 이미 열려있으면 먼저 닫음.
- `dup2(p[1], 1)` = fd 1(stdout)이 파이프 쓰기 끝을 가리키게 → 리다이렉션/파이프의 실제 도구.
- 셸의 `>`도 close+open 대신 dup2로 구현.

### fork: 복사 vs 공유 요약
| 대상 | fork 시 | 결과 |
|------|---------|------|
| 변수(주소 공간) | 복사(COW) | 독립 |
| fd 번호(fd 테이블) | 복사 | 프로세스별 |
| 열린 파일 서술자(offset) | 공유 | offset 같이 전진 |

### zombie / reaping
- 종료된 자식은 부모가 wait로 거둘 때까지 좀비. wait/waitpid가 reap.

## 오늘 헷갈렸다 푼 것

- **가상 주소 같은데 값 다름** → 같은 가상, 다른 물리(COW). mem.c 재확인.
- **wait는 "먼저 시작"이 아니라 "먼저 종료"된 자식을 거둠.**
- **waitpid는 실행 순서 통제 아님** — 거두는 대상만 지정.
- **close는 프로세스별(fd 테이블)**, offset은 공유(서술자). "공유"의 정확한 층위.
- **fork 전 close/open은 상속, fork 후는 각자.**
- **pipe 안 쓰는 끝 안 닫으면** 읽는 쪽이 EOF 못 봐 hang.
