# OSTEP Ch 5 — Process API (fork / exec / wait) 정리

프로세스를 **코드 안에서** 생성·교체·대기하는 UNIX API. 셸의 심장이자, OS 프로세스 트리를 짓는 벽돌.

---

## 세 시스템콜 한눈에

| 콜 | 하는 일 | 핵심 |
|----|---------|------|
| `fork()` | 호출 프로세스를 복제 (자식 생성) | **두 번 반환** (부모/자식) |
| `exec()` | 현재 프로세스를 다른 프로그램으로 교체 | **성공하면 반환 안 함** |
| `wait()` | 부모가 자식 종료를 대기 | 순서를 **확정적**으로 만듦 |

---

## fork()

- 호출한 프로세스를 **거의 그대로 복제**: 주소 공간, 열린 파일, 실행 위치(PC)까지 복사한 자식 생성.
- fork 이후 **두 프로세스**가 fork **다음 줄부터** 똑같이 실행됨.
- **반환값으로 부모/자식 구분:**
  - 부모: **자식의 pid** (양수)
  - 자식: **0**
  - 실패: **-1**
- **순서는 비결정적(non-deterministic).** 부모·자식 둘 다 Ready라 스케줄러가 누구 먼저 돌릴지 정함. fork는 "fork 후 코드가 두 번 실행됨"은 보장하지만 **순서는 보장 안 함** → 의존 금지.
  - fork 자체는 부모를 쫓아내지 않지만, ① fork(시스템콜) 반환 시 스케줄러 개입 ② 타이머 인터럽트 ③ 멀티코어 때문에 순서가 unspecified.

## wait()

- 부모가 **자식이 끝날 때까지 Blocked** → 자식 종료 시 Ready.
- 반환값 = **종료된 자식의 pid**.
- **순서 확정:** 부모가 먼저 스케줄돼도 wait()에서 막혀 자식이 먼저 완료됨 → "자식 먼저, 부모 나중"이 보장됨. 비결정성 제거.
- 헤더: `<sys/wait.h>`.

## exec() (execvp)

- 현재 프로세스의 **메모리 이미지(코드·데이터)를 새 프로그램으로 통째 교체.** "새 프로세스 생성"이 아니라 **현재 프로세스가 다른 프로그램이 되는 것.**
- **성공하면 절대 반환 안 함** (다음 줄 실행 X — 코드가 덮여 사라짐). 실패 시 -1 반환 → exec 뒤엔 에러 처리를 둠.
- `execvp(프로그램명, argv배열)`:
  - `v` = 인자를 **배열(vector)**로 전달
  - `p` = **PATH에서** 프로그램을 찾음 (전체 경로 불필요)
  - 넘긴 배열이 **새 프로그램의 `argv`가 됨.** 예: `["wc","p3.c",NULL]` → wc의 `main(argc,argv)`가 argc=2, argv=이 배열로 시작.
  - `argv[0]`=프로그램 이름은 **관례** (실행 대상은 execvp 첫 인자가 결정; argv[0]은 프로그램이 "자기 이름"으로 참고). 배열 끝은 **NULL**로 표시.
- **exec는 열린 fd를 유지한다** (메모리만 교체) ← 리다이렉션의 핵심.

## 왜 fork와 exec를 나눴나 (UNIX 설계의 백미)

- 한 방의 "프로그램 X 실행" 콜이었다면 **생성과 로딩 사이에 끼어들 틈**이 없음.
- fork/exec를 나누면, 그 **틈(fork 후 ~ exec 전)**에 자식이 아직 셸 복사본일 때 **환경을 세팅**할 수 있음 → 리다이렉션(`>`), 파이프(`|`).

---

## 파일 디스크립터 (fd)

- **열린 파일을 가리키는 작은 정수.** OS의 프로세스별 "열린 파일 테이블" 인덱스.
- 모든 프로세스는 시작 시 **fd 3개**가 열림:
  - **fd 0 = stdin**, **fd 1 = stdout**, **fd 2 = stderr**
- **`open()`은 사용 가능한 가장 낮은 fd**를 배정.
- 멘탈 모델: fd = "번호 붙은 호스". 프로그램은 번호(예: 1번)에만 출력하고, **그 번호가 뭐에 연결됐는지는 OS가 정함.**

## 리다이렉션 `>`의 구현

```
close(1)                                  // fd 1(화면) 닫음 → 1번이 빔
open("file", O_CREAT|O_WRONLY|O_TRUNC)    // 가장 낮은 빈 fd=1 → fd 1이 파일로
execvp("wc", ...)                         // wc가 fd 1(=파일)에 출력
```

- 프로그램(wc)은 자기가 파일에 쓰는지도 모름 — 그냥 fd 1에 쓸 뿐.
- **위치 규칙:** fork **후**(부모 fd 안 건드리려고), exec **전**(세팅이 유지되게), **자식 안**에서.
- **exec가 fd를 유지**하므로 exec 전 세팅이 새 프로그램까지 이어짐.

### `wc p3.c > newfile.txt`의 실행 순서

```
1. 셸이 명령 파싱 (프로그램=wc, 인자=[p3.c], stdout→newfile.txt)
2. 셸: fork()
   ├ 자식: close(1) → open("newfile.txt") [fd1=파일] → execvp("wc",["wc","p3.c",NULL]) → wc가 파일에 출력 → 종료
   └ 부모(셸): wait() [Blocked] → 자식 종료 → 프롬프트
```

- `|`(파이프)도 같은 원리: close/open 대신 `pipe()`의 한쪽 끝을 fd에 연결해 두 프로세스를 이음. (processes-shell 프로젝트에서 구현)

---

## 셸 = 프로세스, 그리고 프로세스 트리

- **셸(bash) 자체가 실행 중인 하나의 프로세스.** 명령마다 **fork + exec + wait** 반복.
- 확인: `echo $$`(셸 pid), `ps`, `pstree`.
- **모든 프로세스엔 부모가 있고 트리를 이룸.** 뿌리 = **PID 1**(`init`/`systemd`), 부팅 시 최초 프로세스.
- 예: `./p3` 실행 시 사슬 → `bash ──fork+exec──▶ p3 ──fork+exec──▶ wc`
- **fork+exec가 근본적인 이유:** 시스템 전체 프로세스 트리가 PID 1에서 fork+exec로 자라난 것.
- `./p3`엔 `./`가 필요하고 `wc`는 안 필요한 이유: `.`(현재 디렉토리)은 보안상 보통 **PATH에 없음** → 현재 폴더 프로그램은 명시적 경로 필요.

## 코드 예제 (오늘 작성)

- **p1.c** — fork로 부모/자식 분기 (반환값 rc로 구분)
- **p2.c** — 부모에 wait() 추가 → 자식이 항상 먼저 완료
- **p3.c** — fork + execvp("wc", ["wc","p3.c",NULL]) + wait → 자식이 wc로 변신
- **p4.c** — 자식에서 close(1)+open(file) 후 exec → 출력이 파일로 (`>` 수동 구현)

## 오늘 헷갈렸다가 푼 것

- **fork 후 순서**: 부모 먼저가 "보장"은 아님(스케줄러). 내 시스템에서 일관돼도 표준 아님. 순서 필요하면 wait().
- **wc에 fork가 있나?** 없음. fork는 **셸**이 함. wc는 단순 일꾼(파일 읽고 세고 출력). 배관공(셸) vs 일꾼(wc) 분리.
- **argv[0] = 프로그램 이름**은 관례. 실행 대상은 execvp 첫 인자가 결정.
- **wc 실행파일은 내가 안 만들었는데?** OS 기본 설치(coreutils), `/usr/bin/wc`. execvp가 PATH에서 찾음.
- **fd 리다이렉션 직관**: 프로그램은 번호에만 쓰고, 번호의 연결은 밖에서 바꿈. close(1)로 1번을 비우면 open이 1번을 가져가 파일에 연결.
