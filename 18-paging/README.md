# OSTEP Ch 18 — Paging: Introduction 정리

세그멘테이션(Ch16)·free space(Ch17)를 죽인 **외부 단편화**를 원천 소멸.
핵심: **주소 공간을 균일한 크기(페이지)로 잘라 물리에 흩어 놓고, 배열 룩업으로 O(1) 번역.**

---

## 왜 페이징인가 — "흩어놓기"가 아니라 "싸게 번역하기"

세그먼트도 임의로 쪼개서 흩어 올릴 수는 있음(2000B를 1000+1000으로). **문제는 배치가 아니라 번역.**
쪼개는 위치·개수가 매번 제각각이면 번역기가 **가변 구간 리스트를 검색**해야 함 → base/bounds의 O(1)이 무너짐.

**페이징의 트릭 = "항상 똑같은 자리에서, 똑같은 크기(2ⁿ)로 쪼갠다".**
→ 하위 n비트는 무조건 페이지 안 위치(offset), 상위는 몇 번째 페이지(VPN)로 딱 떨어짐 → **검색 없이 배열 인덱싱**.

| | 세그먼트 임의 분할 | 페이징(균일 분할) |
|--|--|--|
| 물리 배치 | 흩어놓기 가능 | 흩어놓기 가능 |
| 조각 크기·경계 | 매번 제각각 | **항상 고정(2ⁿ)** |
| 번역 구조 | 가변 구간 리스트 + **검색** | 배열 **인덱싱 O(1)** |
| 오프셋 | 구간마다 base 빼기 | 하위 n비트 **그냥 잘라 쓰기** |

→ 세그멘테이션이 "각 세그먼트 통째로 연속" 정책을 유지한 이유 = 흩어놓으면 번역이 감당 안 돼서.
페이징은 균일 크기라 번역이 싸니 **흩어놓기를 실제로 채택** → 외부 단편화 소멸.

**공짜 아님 — 세 가지 대가:**
| | 세그멘테이션 | 페이징 |
|--|--|--|
| 외부 단편화 | 있음 | **없음** ✅ |
| 내부 단편화 | 적음 | 있음(페이지 끝 낭비) |
| 관리 정보 | 3~4쌍 → 레지스터 | **수십만~백만 PTE → 메모리 테이블** |
| 번역 비용 | 레지스터라 빠름 | 메모리 접근 +1회 → **TLB 필수(Ch19)** |

## 용어 (page 세계 ↔ frame 세계, 대칭)

```
가상 세계          물리 세계
page(페이지)   →   frame(프레임)    ← 둘 다 같은 크기 (그래서 offset 그대로 통과)
VPN            →   PFN
```

| 약어 | 뜻 |
|--|--|
| **VPN** | Virtual Page Number — 가상 주소 상위 비트, 몇 번째 페이지 |
| **offset** | 페이지 안에서 몇 번째 바이트 |
| **PFN** | Physical Frame Number — 물리 몇 번째 프레임 |
| **PTE** | Page Table Entry — 페이지 테이블의 **한 칸** = valid + PFN + 권한비트 등 |

번역 = **VPN을 PFN으로 바꾸는 것**. offset은 안 바뀌고 **복사**됨.

---

## 번역 메커니즘 (계산 전부)

```
가상주소 [ VPN │ offset ]
              │
              ▼   PTE = PageTable[VPN]      ← VPN으로 인덱싱 (PFN으로 X)
            PTE = [ valid │ PFN │ 권한... ]
              │
       valid=0 → trap(segfault). 끝.
       valid=1 → PFN 꺼냄
              ▼
물리주소 = (PFN << offset비트) | offset      ← offset 하위에 그대로 이어붙임
```

**"PFN의 시작 주소"는 저장 안 함 — 계산.** 프레임 크기 고정이라 `시작주소 = PFN × 페이지크기`.
크기가 2ⁿ이라 곱셈도 시프트(`PFN << n`). → 세그먼트의 **base 저장을 없앤 이득**. PFN이 base를 인코딩.

**VPN→PFN은 부호확장/산술 변환 아님 — 그냥 룩업 결과.** VPN 2와 PFN 5는 아무 수치 관계 없음(표의 2번 칸에 5가 적혀 있을 뿐). 그래서 VPN 비트 수 ≠ PFN 비트 수 가능(물리 메모리가 크면 PFN이 더 김). 주소·VPN·PFN은 전부 **unsigned**로 다룸(음수 오해 방지지 확장 아님).

### valid 비트 = base/bounds의 bounds 검사에 대응

- base/bounds: 주소 공간을 **연속 한 덩어리**로 보고 `주소 < bounds` **한 번**으로 보호.
- 페이징: 주소 공간이 페이지로 흩어져 있어 **페이지마다 valid 비트**로 분산 검사.
- valid=0 = "이 페이지는 주소 공간에 없음" → 접근 시 trap. PFN 값이 0이든 뭐든 **무시**.
- 그래서 `[3,7,5,0]`의 마지막 0은 "PFN 0"이 아니라 valid=0이면 **안 보는 쓰레기값**.

| base/bounds | 페이징 대응 |
|--|--|
| **base** (시작 저장) | 저장 안 함 → PFN×크기로 계산 |
| **bounds** (범위 검사) | **valid 비트** (페이지마다) |

## ★ 오늘 크게 헷갈린 것 (다시 볼 것)

### ① 주소 공간 크기 ≠ 물리 사용량 ≠ "할당"

- **주소 공간 16KB = 번지 범위(한도)**. 물리 메모리 소비 **0**. 누가 16KB를 떼준 적 없음.
- **valid 9개 = 9KB = 실제 물리 프레임 붙은 페이지**.
- 나머지 7페이지 = 번지만 있고 빈 곳, 물리 0.
- 비유: 아파트 호수 101~116호(범위)가 있어도 실제 사는 건 9집. 나머지는 번호만 있는 빈 집.
- **Ch13 재확인**: malloc 500MB(범위) vs RSS 1.25MB(실제) — 같은 얘기.

### ② 인과 방향 — 크기가 비트를 정한다 (비트가 크기를 정하는 게 아님)

**"16KB라서 14비트"** (16KB가 먼저). "14비트라서 16KB"로 거꾸로 외우면 계속 헷갈림.
비유: "자물쇠가 4자리다"가 먼저 → "조합 1만 개"가 결과.

### ③ VPN 비트는 페이지 크기가 아니라 **주소 공간 크기**가 정한다

두 입력이 **각자 절반**을 담당 (서로 독립, 둘 다 사람이 정함):
```
주소 공간 크기 ──▶ VPN 비트    ┐
                             ├─▶ 총 주소 비트
페이지 크기    ──▶ offset 비트  ┘
```
페이지 크기만으로 VPN 못 구함. VPN = log₂(주소공간 / 페이지크기) = log₂(페이지 개수).

### ④ 단위 k = 1024 = 2¹⁰ (십진수 아님)

```
1K=2¹⁰   1M=2²⁰   1G=2³⁰
4K = 2²×2¹⁰ = 2¹²    (K 붙으면 지수 +10, 4는 +2)
8K=2¹³  16K=2¹⁴  32K=2¹⁵
```
실수 사례: 4KB의 offset을 14비트로 착각(2¹⁴로 봄). **4K=2¹²라 offset 12비트.**

### 계산 공식 + 검산

```
총 주소 비트 = log₂(주소 공간 크기)
offset 비트  = log₂(페이지 크기)
VPN 비트     = 총 − offset = log₂(페이지 개수)

검산: VPN + offset = log₂(주소 공간).  안 맞으면 어디 틀림.
```

**비트 자릿수 세다 헷갈리면 나눗셈으로:**
```
VPN    = 가상주소 ÷ 페이지크기   (몫)
offset = 가상주소 % 페이지크기   (나머지)
```

## 선형 페이지 테이블은 크다 → Ch20 동기

**칸(PTE)과 프레임을 구별:**
| | 실사용에 비례? |
|--|--|
| 물리 프레임 | ✅ 9개만 (안 쓰면 0) |
| 선형 테이블 칸(PTE) | ❌ **16개 전부 존재** |

**왜 안 쓰는 칸을 못 빼나:** `PageTable[VPN]`을 O(1)에 읽으려면 배열이라 중간 칸도 있어야 함(12번째로 세야 하니까). valid=0으로 "비었다" 표시만, 칸 자체는 유지.

**실제 규모 (32비트, 4KB 페이지, PTE 4B):**
```
offset 12비트, VPN 20비트 → PTE 2²⁰ = 100만 개 → 테이블 4MB
프로세스당 4MB. 100개면 400MB. 대부분 안 쓰는 페이지인데도 칸은 다 존재.
```
→ Ch20 멀티레벨: "안 쓰는 구간은 **테이블 자체를 안 만든다**"로 해결.

**실행 시 페이지는 몇 개 붙나? — 처음엔 거의 0.**
- ELF 헤더로 레이아웃(코드/힙/스택 위치)은 앎 → 주소 공간에 **등록만**, 물리 안 붙임.
- 첫 접근 → **page fault** → 그제야 프레임 붙이고 SSD에서 그 페이지만 읽음(**demand paging**, Ch21).
- 9개 = "지금까지 건드려 붙은 스냅샷"이지 시작 시 정한 수 아님.
- **주소 공간 등록 ≠ 물리 할당** (Ch13 lazy allocation의 연장).

## 숙제 (paging-linear-translate.py)

```bash
./paging-linear-translate.py -P 1k -a 16k -p 32k -v -n 3 -c
```
`-P` 페이지 크기 / `-a` 주소 공간 / `-p` 물리 메모리 / `-v` 테이블 출력 / `-n` 주소 개수 / `-c` 정답.

**PTE 읽는 법:** 최상위 비트 = valid. `0x80000018` → valid=1, 하위 = PFN(0x18=24). `0x00000000` → valid=0.

**실측 (페이지 1KB → offset 10비트, VPN 4비트):**
```
[ 0] 0x80000018  valid=1 PFN=24
[ 8] 0x00000000  valid=0        → VA VPN 8 접근 = Invalid
[12] 0x8000000f  valid=1 PFN=15
```

**손 번역 검증 — VA 0x00003385 (=13189):**
```
VPN    = 13189 ÷ 1024 = 12        → PTE[12]=0x8000000f → valid=1, PFN=15
offset = 13189 % 1024 = 901
물리   = 15 × 1024 + 901 = 16261   ✅ (시뮬레이터 일치)
```

**실수 포인트:**
- offset 비트는 **그 문제의 페이지 크기**가 정함 (1KB→10, 4KB→12). 딴 문제 숫자 가져오지 말 것.
- 이진수 자릿수 세다 틀리면 **÷1024, %1024로 검산**.
- 16진수 폈을 때 상위 잉여 비트 버리기 (14비트 주소면 하위 14비트만).

## 실전 포인트

- 주소 쪼개기(VPN/offset 비트 계산)는 시험·면접 단골. 공식 + 검산 반드시.
- valid 비트 = 보호(bounds의 분산판) + "안 쓰는 페이지 표현", **하나의 메커니즘이 두 역할**.
- "선형 테이블이 왜 크고 왜 낭비인가"를 숫자로 설명 → 멀티레벨(Ch20)의 필요성.
- page(가상) vs frame(물리) 용어 정확히.
