# OSTEP Ch 19 — TLB (Translation Lookaside Buffer) 정리

Ch18 페이징의 대가 — **접근마다 메모리 2번** — 를 갚는 장.
핵심: **MMU 안 번역 캐시(TLB)로, 지역성 덕에 대부분의 번역을 공짜로.**

---

## 문제 — 페이징은 메모리 접근을 2배로

`int x = arr[i];` 한 줄로 데이터 하나 읽을 때:
```
① VPN으로 PageTable[VPN] 읽기   → 메모리 접근 1번 (PTE 가져오기)  ← 번역
② PFN 얻어 물리주소 조립
③ 그 물리주소에서 실제 데이터    → 메모리 접근 1번 (arr[i])
                                  ─────────
                                   총 2번
```
원래(페이징 없으면) ③ 한 번이면 끝인데, **①이 매번 추가**돼 접근이 2배. 메모리 접근은 느려서(수십~수백 사이클) 프로그램이 절반 속도로 김. **①이 낭비** — 진짜 원하는 건 데이터인데 주소 알려고 테이블을 또 읽음.

## 해결 — TLB

**관찰(지역성):** `arr[0..255]`가 한 페이지(1KB=int 256개) 안이면 **VPN이 전부 같음** → `PageTable[VPN]`이 매번 같은 답. 그걸 매번 메모리 가서 읽는 건 순수 낭비.

**TLB = MMU 안의 작은 하드웨어 캐시.** VPN→PFN 번역 결과를 수십~수백 개 저장.
```
① VPN으로 TLB 먼저 확인
    히트 → PFN 즉시. 메모리 안 감 (① 접근 생략)
    미스 → PageTable 읽고, TLB에 채운 뒤 재개
② 데이터 접근
```
첫 접근만 미스, 같은 페이지 이후 접근은 전부 히트.

**왜 잘 되나 = 지역성(locality):**
- **공간 지역성**: 방금 쓴 근처를 곧 씀(배열 순회) → 같은 VPN 반복.
- **시간 지역성**: 방금 쓴 걸 또 씀(루프 변수, 스택) → 같은 번역 재사용.
- 대부분 프로그램이 이래서 **히트율 99%+** → "접근마다 2배"가 "가끔 미스날 때만"으로 줄어듦.

## TLB 미스 처리 — 누가 하나 (trap이냐?)

미스는 인터럽트가 아니라 **trap(예외)** — 실행 명령 때문에 동기적으로 남. 처리 주체는 설계 나름:

| | 하드웨어 관리 (x86) | 소프트웨어 관리 (MIPS) |
|--|--|--|
| 누가 | MMU가 **스스로** page table walk | **OS trap 핸들러** |
| trap? | **안 걸림** | 걸림 |
| 페이지 테이블 | HW 고정 형식 (CR3가 가리킴) | OS 마음대로 (유연) |
| 속도/유연 | 빠름 / 낮음 | 느림 / 높음 |

**TLB 미스 ≠ page fault (헷갈리지 말 것):**
- **TLB 미스**: 번역이 캐시에 없음. PTE는 **메모리에 있음** → 테이블에서 가져다 채우면 끝. 가벼움.
- **page fault**: PTE의 **valid=0** → 페이지가 물리 메모리에 아예 없음(디스크 or 미할당). **무조건 OS trap** → swap-in 또는 segfault. 무거움(디스크 I/O). Ch21 주제.

## 소프트웨어 관리의 무한 재귀 함정

미스 핸들러도 **가상 주소로 접근되는 코드**. 핸들러를 부르려고 그 주소를 번역 → 또 TLB 미스 → 핸들러 부르려고... **무한 재귀.**
**해결(재귀의 바닥 만들기):**
- 핸들러를 **번역 불필요한 물리(unmapped) 주소**에 배치, 또는
- 핸들러 번역을 **wired(고정) TLB 엔트리**로 못 박아 항상 히트.
- 일반 원리: **"X를 처리하는 메커니즘은 X에 의존하면 안 된다."** (락 구현이 락을 필요로 하면 안 되듯.)

## TLB의 한계 — reach와 절벽

**capacity miss:** TLB 용량 n인데 서로 다른 페이지 **n+1개를 루프로 반복** 접근하면:
```
1회차: 0..n-1로 꽉 채움 → 페이지 n 미스 → 가장 오래된 페이지 0 쫓아냄
2회차: 페이지 0 접근 → 방금 쫓겨나 미스 → 페이지 1 쫓아냄 → ...
      = 내가 다음에 쓸 걸 항상 방금 버림 → 히트율 0%
```
- **LRU가 최악으로 작동하는 케이스** (순차 반복 접근).
- **절벽(cliff)**: 워킹셋이 용량을 넘는 순간 **낭떠러지처럼** 급락. 점진적 아님.

**TLB reach = 엔트리 수 × 페이지 크기** = TLB가 커버하는 총 메모리 범위.
워킹셋 ≤ reach → 히트, 넘으면 절벽.

**reach 넓히는 법:**
1. 엔트리 수 ↑ → TLB는 빠른 HW라 크게 못 만듦(비쌈·느려짐). 한계.
2. **페이지 크기 ↑ (huge page, 2MB/1GB)** → 같은 엔트리로 넓은 범위. DB·JVM이 씀.
   - **대가: 내부 단편화** (4KB만 필요한데 2MB 잡으면 낭비). 그래서 기본은 4KB.

## 문맥 교환 함정 (시험 단골)

A가 TLB를 자기 번역으로 채운 뒤 B로 교환. TLB엔 **A의 `0x1000→PFN`이 잔존**.
B가 `0x1000` 접근 → MMU가 "TLB에 있네, 히트!" → **A의 PFN을 줌** → B가 A의 물리 메모리 읽음 → **격리 붕괴.**
(주의: "같은 페이지 테이블 참조"가 아님. B의 CR3는 맞는데 **TLB에 옛 번역이 남은 게** 문제.)

**해결 두 가지:**

| | Flush (전체 비우기) | ASID / PCID (주인 ID 표시) |
|--|--|--|
| 방법 | 교환마다 TLB 싹 비움 (x86은 CR3 재기록 시 자동) | 엔트리에 프로세스 ID 저장, 매칭 조건 `VPN AND ASID` |
| 안전 | ✅ | ✅ (ID 안 맞으면 미스) |
| 대가 | B 초반 **콜드 미스 폭탄** | HW 복잡(ID 비트) |
| 공존 | ❌ A 번역 날아감 | ✅ A·B 공존 → 복귀 시 히트 |

→ 현대 CPU는 **ASID(ARM/리눅스) / PCID(x86)** 채택, flush는 fallback.

**커널 페이지 = global 비트:**
- 주소 공간은 **유저 반 + 커널 반**. 커널 영역은 **모든 프로세스가 같은 물리(하나뿐인 OS)를 공유** 매핑 (시스템콜 시 주소공간 안 바꾸고 커널로 점프하려고). 유저 모드 접근은 금지(트랩).
- 커널 번역은 A든 B든 같음 → 문맥 교환해도 유효. flush/ASID로 막으면 낭비.
- **global 비트**를 켜 "문맥 교환 시 flush·ASID 검사 제외" → 커널 번역은 TLB에 상주.
- (나중에 Meltdown 취약점과 얽힘 — 지금은 "커널 엔트리는 global로 유지"만.)

## 숙제 — measure.c로 TLB 크기 실측 ★

파이썬 시뮬레이터가 아니라 **직접 C로 TLB 절벽을 내 CPU에서 측정.**

### 설계 (핵심 = 측정 오염 막기)

```
1. arr = malloc(NUMPAGES * 1024 * sizeof(int))   // 페이지당 int 1개만 쓸 거라 이만큼
2. 워밍업: for i: arr[i] = i;                     // 모든 페이지 강제 write → 프레임 부착
3. gettimeofday(start)
4. for t in trial:                                // 여러 번 반복(타이머 해상도 확보)
       for p in NUMPAGES:
           sum += arr[p * 1024];                  // ★ stride 접근: 매번 다른 페이지
5. gettimeofday(end)
6. 접근당 시간 = 총 µs / (trial * NUMPAGES) * 1000 ns, sum 출력
```

**stride = 페이지크기 / sizeof(int) = 4096/4 = 1024 인덱스.**
`arr[0], arr[1024], ...` = 매 접근이 다른 페이지 → TLB 미스를 측정 대상으로.
NUMPAGES개 페이지 걸치려면 배열 = `NUMPAGES × 1024` int.

### 측정 3대 함정 (이게 실력)

| 함정 | 틀린 방법 | 올바른 방법 | 이유 |
|--|--|--|--|
| **page fault 오염** | calloc만 | **측정 전 write 워밍업 루프** | calloc은 CoW zero-page라 write 전엔 프레임 미부착 → 첫 접근이 fault(디스크급)로 오염 |
| **컴파일러가 루프 삭제** | `-O0` | **`-O2` + sum을 printf로 출력** | -O0은 잡음 많아 정밀도↓. sum이 쓰이면 컴파일러가 루프 보존 |
| **타이머 해상도** | 1번 측정 | **수백만 번 반복 후 나눔** | gettimeofday=µs, 접근=ns(1000배 작음) → 1번은 양자화 잡음. 총시간 ≫ µs 되게 |

**일감 총량 고정 팁:** `trial = TOTAL / NUMPAGES` (TOTAL 상수). NUMPAGES 커도 총 접근 일정 → 실행 시간 일정, 접근당 비교 공정.

### 코딩에서 걸린 실수 (반복 실수 — ROADMAP 등재)

- **연산자 우선순위 괄호** (또!): `sec*1e6 + usec / (trial*N)` → `*`·`/`가 `+`보다 우선이라 분자가 안 묶임. **분자 전체 괄호** `(sec*1e6 + usec) / (...)`. → 복잡한 수식은 **중간 변수로 쪼개면** 원천 차단.
- **단위 변환 방향**: 초를 µs로 내려야(`tv_sec * 1e6`), µs에 곱하면(`tv_usec * 1e6`) 스케일 폭발. 큰 단위를 잘게 부숴 작은 단위에 합침.
- **결과 타입**: 접근당은 ns급 소수 → `int`/`long`에 담으면 0. `double`로, ×1000해서 ns.
- **오버플로우**: `trial * NUMPAGES`가 `int*int` → 큰 N에서 넘침. `(long)trial * NUMPAGES`.
- **시간 단위**: 초 > ms(10⁻³) > µs(10⁻⁶) > ns(10⁻⁹), 매 단계 ×1000. 1초 = 100만 µs.

### 실측 결과 (내 CPU, 4KB 페이지)

```
    1 ~  256 pages: 1.4~1.7 ns   ← 평평 (TLB 히트 구간)
        1024 pages: 2.1 ns       ← 계단1: L1 TLB 초과
        4096 pages: 5.3 ns       ← ★ 계단2: L2 TLB reach 초과 (진짜 절벽, 2.5배 급등)
       16384 pages: 9.1 ns
       65536 pages: 9.9 ns       ← 고원 (전부 미스, walk 비용 지배)
```

**해석:**
- **계단이 2개 = 2단계 TLB(L1/L2)의 증거.**
- reach 역산: L1 TLB ≈ 수백 엔트리(reach 1~2MB), L2 TLB ≈ 1~2천 엔트리(reach 4~8MB). 4096페이지=16MB에서 L2도 초과 → 매 접근 page table walk.
- **`reach = 엔트리수 × 페이지크기`를 실제 CPU에서 측정으로 확인.**
- 워킹셋에 따라 같은 코드가 **7배**(1.4 → 9.9ns) 갈림 → 지역성이 성능을 지배.

**실전 함의:** cache/TLB 친화 코드(작은 워킹셋, 순차 접근, blocking/tiling)가 빠른 이유 = 이 절벽을 안 넘어서. 면접 "cache-friendly code" → 이 그래프.

## 이 장 뼈대

```
페이징 대가: 접근마다 메모리 2번 (PTE + 데이터)
→ TLB(MMU 캐시) + 지역성 → 히트율 99%+, 평균 ≈ 1번
→ 미스 처리: HW walk(x86, trap 없음) / SW 핸들러(MIPS, trap)  ※ page fault와 구별
→ 한계: 워킹셋 > TLB reach → capacity miss 절벽 (n+1 반복 = LRU 최악)
→ reach 확장: huge page (대가: 내부 단편화)
→ 문맥 교환 함정: 옛 번역 잔존 → flush / ASID·PCID (+ 커널은 global)
```
