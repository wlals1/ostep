## 최종 설계

```
블록 구조:  [헤더 4B][payload][푸터 4B]
            헤더/푸터 = size | alloc   (8정렬이라 하위 3비트가 남아 alloc 비트 겸용)

free 블록:  [헤더][prev 4B][next 4B][남는 공간][푸터]
            payload 자리에 링크를 심음 (임베디드 free list)

힙 구조:    [패딩][프롤로그 8/1][ ... 블록들 ... ][에필로그 0/1]
            프롤로그·에필로그 = sentinel. 경계 특수처리 제거

free list:  이중 연결, LIFO 삽입
배치 정책:  best fit (+ exact fit 조기 종료)
병합:       즉시 병합 (4가지 경우)
분할:       남는 게 최소 블록(16B) 이상이면 split
realloc:    ① 이미 충분 → 제자리
            ② 다음이 free이고 합치면 충분 → 흡수 (복사 없음)
            ③ 다음이 에필로그 → 힙 확장 후 흡수 (복사 없음)
            ④ 그 외 → malloc + memcpy + free
CHUNKSIZE:  64
```

## binary-bal — 55%가 구조적 한계임을 계산으로 확인

트레이스 분석:
```bash
awk '/^a/{print $3}' traces/binary-bal.rep | sort -n | uniq -c
#  2000 64,  2000 448,  2000 512
head -20 traces/binary-bal.rep   # 64와 448을 번갈아 할당
```

**패턴:** 64와 448을 번갈아 2000개씩 → 448을 전부 free → 512를 2000개 할당

```
1단계: 힙 = 2000 × (72 + 456) = 1,056,000
       (64+8=72,  448+8=456)

2단계: 456바이트 구멍 2000개
       ★ 사이사이에 64짜리가 살아 있어 병합 불가

3단계: 512 블록 = 520바이트.  520 > 456  →  구멍에 안 들어감
       힙을 2000 × 520 = 1,040,000 더 늘려야 함

최종 힙 = 2,096,000
최대 payload = 2000×64 + 2000×512 = 1,152,000
util = 1,152,000 / 2,096,000 = 55.0%   ← 실측과 정확히 일치
```

> **어떤 배치 정책으로도 못 고친다.** 구멍(456)이 요청(520)보다 작은 건 물리적 사실.
> 병합도 불가 — Ch17의 *"coalescing은 살아 있는 블록이 가로막으면 못 한다"*가 정확히 이 상황.

**근본 해법은 배치 자체를 바꾸는 것 (segregated storage):**
```
현재:       [64][448][64][448]...   → 448을 free하면 구멍이 흩어짐
크기별 분리: [64][64]...[448][448]... → 448을 free하면 912,000바이트가 통째로 연속
                                       → 512를 거기 다 넣을 수 있음
```
free list만 나누는 게 아니라 **힙 영역 자체를 크기 클래스별로 분리**해야 함.
실제 할당기(tcmalloc, jemalloc)가 하는 방식. **구조 변경이 커서 이번엔 보류.**

## 배운 것

### 개념 — Ch17이 코드가 됨

| Ch17 개념 | 구현에서 만난 곳 |
|--|--|
| 헤더에 크기 저장 | `free(p)`가 `p-4`에서 크기를 읽음 |
| 임베디드 free list | free 블록의 payload에 prev/next를 심음 |
| splitting | `place()`에서 남는 게 16 이상이면 쪼갬 |
| coalescing | 4가지 경우. 즉시 병합 |
| best/first fit | 실측으로 비교 (best fit이 util +2점) |
| 탐색 vs 병합 트레이드오프 | 푸터가 그 딜레마를 푸는 장치 |
| compaction 불가 | 사용자가 raw 포인터를 들고 있어서 |

### 설계 원리

**① 안 쓰는 비트를 겸용한다**
크기가 항상 8의 배수 → 하위 3비트가 놀고 있음 → alloc 비트로 사용. **공간 추가 0.**
(Ch21에서 `present=0`일 때 PFN 자리를 디스크 주소로 재활용한 것과 같은 발상)

**② sentinel — 특수 케이스를 일반 케이스처럼 보이게**
프롤로그·에필로그를 `alloc=1`로 심어두면 `coalesce`의 경계 검사가 **통째로 사라짐.**
`if (첫 블록인가?)` 같은 분기 없음. 16바이트 한 번에 평생의 분기를 삼.
(Ch29의 Michael-Scott 큐 더미 노드, 연결 리스트 dummy head와 같은 트릭)

**③ 연산의 비대칭이 구조의 비대칭을 낳는다**
```
에필로그 : NEXT 방향으로만 읽힘 → 헤더 4바이트면 충분
프롤로그 : PREV는 푸터→헤더 2단계 → 온전한 블록(8바이트) 필요
```

**④ 헤더 먼저, 푸터 나중**
`FTRP(bp)`가 **헤더에서 크기를 읽어** 위치를 계산하므로, 헤더를 먼저 갱신해야 푸터가 올바른 자리를 가리킴. **이 lab에서 가장 흔한 버그.**

**⑤ 리스트 조작 먼저, 물리 조작 나중**
`remove_free`는 헤더를 바꾸기 전에. 헤더가 바뀌면 `NEXT_BLKP`가 다른 곳을 가리킴.

**⑥ 물리적 인접 ≠ 리스트상 인접**
```
prev/next : free list에서의 논리적 순서
헤더/푸터 : 메모리상의 물리적 인접성
```
**병합은 물리적으로 인접한 것끼리만.** 그래서 푸터가 필요하고, 리스트는 자유롭게 정렬 가능.
(Ch17의 *"주소순은 병합이 쉽고 크기순은 탐색이 빠르다"* 딜레마를 푸터가 해소)

**⑦ 할당된 블록은 free list에 없다**
`mm_free(bp)`는 `remove_free`가 아니라 `insert_free`를 해야 함. 처음에 헷갈린 지점.

### 디버깅

**`mm_check` — 불변식 검사기**
```
[블록]     헤더==푸터 / bp가 8정렬 / 크기>=16이고 8의 배수 / 힙 범위 안
[인접]     연속된 free 블록이 없음 (즉시 병합 불변식)
[힙]       프롤로그 8/1, 에필로그 0/1이 힙 맨 끝
[리스트]   모든 노드가 alloc=0 / 링크 일관성 / ★ 힙의 free 개수 == 리스트 노드 수
```
**개수 대조가 가장 강력** — 누락·중복을 한 번에 잡음.
`#ifdef DEBUG`로 켜고 끔. 켜면 O(n²)라 느리지만 정확성 검증용.

**잡아낸 실제 버그: 8바이트 블록이 힙을 파괴**
```
mm_realloc ③에서 asize - oldsize == 8 → extend_heap(2) → 8바이트 블록
8바이트 블록: 헤더4 + 푸터4, payload 0
insert_free가 bp+0(푸터), bp+4(에필로그 헤더)를 덮어씀
→ 에필로그에 포인터 값이 들어감 → GET_SIZE가 쓰레기 → 순회가 힙 밖으로
```
**이 버그는 implicit 버전에도 있었지만 증상이 없었음** — payload에 아무것도 안 썼으니까.
**explicit으로 바꾸며 잠복 버그(latent bug)가 드러난 것.**
→ 수정: `extend_heap`이 최소 블록 크기(16) 미만을 만들지 않도록 방어.

**검사기도 디버깅이 필요하다**
첫 실행에서 "bad size 8 at ..."이 떴는데 **프롤로그(의도적으로 8바이트)를 잡은 거짓 양성**이었음.
불변식이 "모든 블록"이 아니라 "모든 **실제** 블록"이었던 것. → 루프를 `NEXT_BLKP(heap_listp)`부터 시작.
(Ch27·32의 helgrind 거짓 양성과 같은 교훈 — **경고를 보면 "진짜 버그인가, 검사기가 틀렸나"부터 묻기**)

### 측정 규율

**① 처리량은 잡음을 탄다**
```
5회 실행: 77, 75, 65, 75, 75  →  65는 이상치. 대표값 75
util은 매번 정확히 동일 (할당 결정은 결정적)
```
**한 번 측정으로 결론 내리면 안 됨.**

**② 점수판이 전략을 바꾼다**
처리량이 만점(40/40)에 도달한 뒤로는 **처리량을 희생해서라도 이용률을 올리는 게 이득**.
best fit(느리지만 알뜰)과 작은 CHUNKSIZE를 택한 근거.

**③ 튜닝은 과적합일 수 있다**
```
CHUNKSIZE 64  : 이 11개 트레이스에 최적
CHUNKSIZE 4096: 페이지 크기와 맞음. 범용적으로 안전
```
`mem_sbrk`가 진짜 시스템콜이었다면 64는 재앙. **여기선 처리량 여유가 있어 안 드러날 뿐.**
CHUNKSIZE 스윕 결과가 **비단조적**(1<<9에서 골짜기)인 것도 워크로드 의존의 증거.
→ **채점 기준을 위한 튜닝과 좋은 설계는 다를 수 있다.**

**④ 구조적 한계를 계산으로 확인하고 멈추기**
binary-bal 55%가 "덜 노력해서"가 아니라 **워크로드 구조상 한계**임을 산술로 검증.
더 짜내려면 설계를 바꿔야 하고, 그 비용을 판단해서 중단.

### C 관련

- **`void*`는 포인터 산술 불가** (`sizeof(void)` 미정의) → `(char *)` 캐스팅
- **`(long)(bp = mem_sbrk(size)) == -1`** — 대입을 괄호로. `==`가 `=`보다 우선 (반복 실수 4번째)
- **`a == b == 0`은 "둘 다 0"이 아님** — `(a==b)==0`으로 결합. `&&`로 명시 (반복 실수 5번째)
- **매크로 오타는 링크 에러로 나타남** — `PACk`가 함수 호출로 해석 → 컴파일은 경고, 링크에서 `undefined reference`
- **`-Wall`이 실제 버그를 잡음** — `heap_free_count;` (증가 연산자 누락) → "statement with no effect"
- **struct 없이 메모리를 해석** — 관리 정보를 힙 안에 직접 배치. 타입 시스템의 도움이 전혀 없음
