# OSTEP Ch 22 — Swapping: Policies 정리

Ch21이 "어떻게 내보내나"(메커니즘)였다면, 이 장은 **"누구를 내보내나"(정책).**
목표: **page fault 최소화.** 잘못 고르면 방금 쫓아낸 걸 바로 다시 불러옴.

---

## 기준선 — Optimal (Belady's MIN)

**가장 먼 미래에 쓰일 페이지를 축출.** 이론상 fault 최소.

**구현 불가** — 미래를 모름.

### 그럼 왜 배우나 ★ (헷갈렸던 것)

**가상화와 무관. 비교하려고 배움.**

내 정책이 fault율 5%가 나왔을 때, 비교 대상이 없으면 좋은지 나쁜지 판단 불가.
- 최적이 3% → 내 정책 꽤 좋음
- 최적이 0.5% → 형편없음

→ **"여기까지가 이론상 한계"라는 upper bound = 실제 정책을 재는 자.**

**같은 패턴이 Ch7에도:** SJF가 평균 반환시간의 이론적 최적이지만 작업 길이를 몰라 구현 불가. 그래도 "MLFQ가 SJF에 얼마나 근접하나"의 기준이 됐음. 동일한 구조.

---

## 실제 정책들

미래를 모르니 **과거로 미래를 추측**.

### FIFO — 먼저 들어온 것 축출

- 큐 하나면 됨, 구현 초간단.
- **결함: "오래 있었다"와 "안 쓴다"를 혼동.**
  프로그램 시작 때 올라온 페이지(메인 루프 코드, 전역 변수, 자주 부르는 함수)가 오히려 **가장 자주 쓰이는데** FIFO는 얘들을 먼저 쫓아냄.

### RAND — 아무거나 축출

- **가치는 "운"이 아니라 "패턴에 안 당하는 것".**
- LRU/FIFO는 특정 패턴에서 **체계적으로** 최악(0%)이 되는데, RAND는 규칙성이 없어 우연히 몇 개가 살아남아 **바닥이 덜 무너짐.**
- 평균은 낮지만 **최악의 경우가 없음.**

### LRU — 가장 오래 안 쓴 것 축출

근거: **지역성** — 최근에 안 썼으면 앞으로도 안 쓸 것.

**FIFO와의 차이 ★**
```
FIFO: 언제 들어왔나 (입장 시각)    ← 그 뒤로 얼마나 썼든 무관
LRU : 마지막으로 언제 썼나 (사용 시각) ← 계속 쓰면 계속 살아남음
```
→ 메인 루프 코드는 매번 접근되니 LRU에선 **절대 안 쫓겨남.** FIFO는 못 하는 일.

**그런데 완벽한 LRU는 구현 불가에 가까움:**
```
① 매 메모리 접근마다 타임스탬프 갱신 또는 리스트에서 빼서 맨 앞으로
   → 메모리 접근은 초당 수십억 번. OS는 매 접근을 가로챌 수 없고(Ch15),
     HW라 해도 매 접근 리스트 조작은 회로로 감당 불가
② 축출 시 전체를 뒤져 가장 오래된 것 찾기 → O(n)
```
→ **①이 재앙.** LRU도 사실상 이론상의 물건.

### CLOCK ★ — LRU 근사, 실제 채택

HW가 할 수 있는 최소한의 일 = **접근 시 reference 비트를 1로 켜기. 끝.** (회로로 공짜)

페이지들을 **원형**으로 늘어놓고 시계바늘 하나:
```
바늘이 가리키는 페이지 검사:
  reference == 1 → 0으로 끄고 다음으로 (second chance, 이번엔 봐줌)
  reference == 0 → 이놈이 희생자. 끝.
```
- **1을 만나면 축출이 아니라 0으로 끄고 넘어감.** 한 바퀴 돌아 다시 왔을 때도 0이면 그때 축출.
- **자주 쓰는 페이지는 바늘이 오기 전에 HW가 다시 1로 켜줌** → 영원히 안 쫓겨남 = LRU와 같은 효과.
- **다 1이면?** 한 바퀴 돌며 전부 0으로 꺼짐 → 출발점 돌아오면 첫 놈이 희생자. **최악 2바퀴, 무한 루프 없음.**
- 비용: **바늘 하나 + 비트 하나.** 리스트 조작·타임스탬프·전체 스캔 전부 없음.
- `-b` 옵션(clockbits): 비트를 여러 개 쓰면 더 세밀 → LRU에 더 근접, 대신 비용 증가.

### Enhanced Clock — dirty까지 조합

```
(ref=0, dirty=0)  최고 희생자 — 안 쓰였고 쓰기도 불필요
(ref=0, dirty=1)  안 쓰였지만 디스크에 써야 함
(ref=1, dirty=0)  최근 쓰였음
(ref=1, dirty=1)  최악 희생자
```
낮은 등급부터 축출 → **clean 우선**이라 디스크 쓰기 절약.

## 숙제 (paging-policy.py) — `vm-beyondphys-policy`

```bash
./paging-policy.py -C 3 -a 0,1,2,3,... -p LRU -c
```
`-C` 캐시 크기 / `-a` 접근 순서 / `-p` 정책(FIFO,LRU,LFU,OPT,UNOPT,RAND,CLOCK) / `-b` clockbits / `-n`+`-s` 랜덤 생성 / `-m` 최대 페이지 번호 / `-N` trace 생략 / `-c` 정답

### 실험 1 — 순환 워크로드 (LRU 저격)

캐시 3칸, 접근 `0,1,2,3` 반복:
```
LRU    0 히트 (0%)      ← 최악. 다음에 쓸 것을 정확히 골라 버림
FIFO   0 히트 (0%)      ← 순차 접근이라 "입장순 = 사용순" → LRU와 동일
RAND   5 히트 (41.7%)   ← 규칙성이 없어 우연히 살아남음
OPT    6 히트 (50%)     ← 이론상 최대
```
**OPT가 이기는 방식:** `[0,1,2]`에 3이 들어올 때 앞으로 가장 먼 **2**를 축출 → `[0,1,3]`.
0과 1을 최대한 오래 붙잡아 히트를 만듦. (내가 처음에 가장 **가까운** 0을 축출한다고 답했는데, 그건 UNOPT = 최악 정책.)

**교훈:** RAND가 LRU를 이기는 건 운이 아니라 구조 — **최악을 없애는 게 평균을 높이는 것보다 중요할 때가 있음.**

### 실험 2 — Belady's Anomaly ★

같은 접근 `1,2,3,4,1,2,5,1,2,3,4,5`:
```
FIFO:  캐시 3 → 3 히트  /  캐시 4 → 2 히트   ❌ 늘렸는데 나빠짐!
LRU :  캐시 3 → 2 히트  /  캐시 4 → 4 히트   ✅ 정상
```

**원인 = stack property:**
> 캐시 크기 N일 때 담긴 집합이, N+1일 때 집합의 **부분집합**인가?

```
LRU 유지 집합:  {최근 3개} ⊂ {최근 4개}       ← 포함 보장 → 절대 나빠질 수 없음
FIFO 유지 집합: {늦게 온 3개} ⊄ {늦게 온 4개}  ← 보장 없음 → 역전 가능
```
LRU는 "최근 N개"라 크기를 늘리면 항상 기존 집합을 포함. FIFO는 "늦게 들어온 것"이라 크기가 바뀌면 축출 타이밍이 어긋나 **집합 자체가 달라짐.**

- **OPT, LRU, LFU 계열은 안전.** FIFO와 clock 일부 변형이 취약.
- 실무 의미: "메모리를 늘렸는데 느려졌다"가 이론적으로 가능. **FIFO를 안 쓰는 또 하나의 이유.**

### 실험 3 — 워크로드가 순위를 뒤집는다 ★★

```bash
# 균등 랜덤 (지역성 0)
./paging-policy.py -s 42 -n 100 -C 10 -m 20 -p $p -c -N | grep FINALSTATS

# 80-20 지역성 (80%는 페이지 0~4, 20%는 5~19)
python3 -c "
import random; random.seed(42)
a=[random.randint(0,4) if random.random()<0.8 else random.randint(5,19) for _ in range(200)]
print(','.join(map(str,a)))" > trace.txt
./paging-policy.py -a $(cat trace.txt) -C 5 -p $p -c -N | grep FINALSTATS
```

| 정책 | 순환(LRU 저격) | 균등 랜덤(지역성 0) | 80-20(지역성 있음) |
|--|--|--|--|
| OPT | 50% | **67%** | **72.5%** |
| CLOCK | — | 50% | **55.0%** |
| LRU | **0%** | 45% | 54.5% |
| FIFO | 0% | 49% | 52.5% |
| RAND | 41.7% | 45% | **50%** (꼴찌) |
| UNOPT | — | 6% | — |

**세 가지 결론:**

1. **"어느 정책이 최고냐"는 질문 자체가 틀림. 워크로드를 먼저 물어야 함.**
   - 지역성 있음 → LRU/CLOCK 승
   - 지역성 없음 → 실용 정책 전부 45~50%에 뭉침, **차이가 노이즈**
   - LRU 저격 패턴 → LRU 꼴찌, RAND가 오히려 나음

2. **균등 랜덤에서 LRU가 FIFO보다 못한 이유:** LRU의 근거는 "최근에 안 썼으면 앞으로도 안 쓴다" = **지역성 가정**. 그 가정이 깨진 워크로드에선 추측이 무의미해져 FIFO·RAND와 구별 불가.
   → **정책이 의미 있는 조건 = 지역성 있음 + 메모리 부족. 둘 중 하나라도 없으면 선택이 무의미.**
   (성능 튜닝의 일반 원리 — 병목이 아닌 곳을 최적화하면 차이가 없음.)

3. **CLOCK ≈ LRU (55 vs 54.5).** 비트 하나 + 바늘로, 구현 불가능한 LRU와 같은 성능.
   → **"완벽하지만 못 만드는 것"보다 "근사인데 공짜인 것"이 이긴다.** 실제 OS가 CLOCK을 쓰는 이유.

4. **OPT와의 격차(72.5 vs 55)** = 미래를 모르는 대가. 최선을 다해도 17%p가 남음.
   → 최적 정책을 "구현하려고"가 아니라 "**재려고**" 배우는 이유.

## 워크로드를 미리 알 수 있나 (물어본 것)

**범용 OS는 못 앎.** 무슨 프로그램이 돌지 모름 → **어떤 워크로드에서도 크게 안 망하는** 정책(CLOCK)을 선택. "최고"가 아니라 **"최악이 없는"** 것을 고름.

**세 가지 우회로:**

**① 앱이 힌트를 준다**
```c
madvise(ptr, len, MADV_SEQUENTIAL);  // "순차로 읽을 것" → 읽고 나면 버려도 됨
madvise(ptr, len, MADV_WILLNEED);    // "곧 쓸 것" → 미리 올려둬
posix_fadvise(fd, ..., POSIX_FADV_DONTNEED);
```
OS가 못 아는 걸 앱이 알려줌. DB·대용량 처리 프로그램이 실제로 사용.

**② 적응형 정책** — 실행 중 관찰해 조정. 대표: **ARC**(최근성 LRU + 빈도 LFU를 둘 다 추적하다 워크로드에 따라 비중 이동, ZFS 채택). 리눅스도 active/inactive 두 리스트로 유사하게.

**③ 앱이 직접 관리** — DB(PostgreSQL, MySQL)는 OS 캐시를 우회하고 **자기 버퍼 풀**을 운영. 자기가 무슨 쿼리를 실행 중인지 아니까 "이 테이블 풀스캔이니 캐시 오염시키지 말고 바로 버려라" 같은 판단이 가능. `O_DIRECT`로 OS 캐시 우회.

> **정보가 있는 층이 결정하는 게 낫다.** OS는 정보가 없어 보수적 정책, 앱은 정보가 있으니 직접 관리하거나 힌트 제공.
> (Ch17에서 malloc이 압축을 못 한 것도 "정보(포인터 소유)가 다른 층에 있어서"였음 — 같은 패턴.)

## 실전 포인트

- **OPT는 구현용이 아니라 측정용**(upper bound). Ch7 SJF와 같은 역할.
- **FIFO vs LRU 차이 = 입장 시각 vs 사용 시각.** 한 문장으로 말할 수 있어야.
- **LRU를 왜 그대로 못 쓰나** → 매 접근마다 자료구조 갱신 불가. → CLOCK이 답.
- **CLOCK의 second chance 동작**을 설명할 수 있어야 (1이면 끄고 넘어감, 무한 루프 없음).
- **Belady's anomaly + stack property** — FIFO만 취약한 이유.
- **정책 순위는 워크로드가 결정** — 실측 표로 답하면 강력.
