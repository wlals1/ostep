# OSTEP Ch 10 — Multiprocessor Scheduling 정리

CPU 여러 개(멀티코어)에서 스케줄링. 단일 CPU와 뭐가 달라지나.
(락·캐시 일관성 세부는 **예고편** — Phase 3 Concurrency에서 회수하고 이 챕터 재방문 권장.)

---

## 새 문제 두 개

### 1. 캐시 친화성 (cache affinity)
- 각 코어엔 자기 **캐시**(자주 쓰는 데이터). 프로세스가 한 코어에서 돌면 그 데이터가 그 코어 캐시에 **warm(데워짐)** → 빨라짐.
- 코어를 옮기면 새 코어 캐시는 **cold** → 다시 채워야 해 느림.
- **원칙: 같은 프로세스는 되도록 같은 코어에서** (캐시 친화성 유지).

### 2. 공유 자료구조 + 락 (동시성 예고편)
- 스케줄러 큐를 여러 코어가 동시에 건드리면 race condition → **락** 필요.
- 락은 **경합(contention)** — 코어 많을수록 서로 기다려 느려짐.

---

## SQMS vs MQMS

| | SQMS (중앙 큐 1개) | MQMS (코어당 큐) |
|--|----|----|
| 구조 | 모든 코어가 큐 하나 공유 | 코어마다 큐, 작업을 배정 |
| 장점 | 부하 균형 자동, 단순 | **확장성↑**(락 경합↓), **캐시 친화성↑** |
| 단점 | **락 경합(확장성↓)**, 캐시 친화성↓ | **부하 불균형** → 마이그레이션 필요 |

- **핵심**: SQMS = 확장성 문제, MQMS = 부하 불균형 문제.
- 실제 리눅스 = **MQMS 계열 + 주기적 부하균형(마이그레이션)**.
- **MLFQ를 멀티코어로** = 코어당 MLFQ(각자 피라미드) + 코어 간 부하균형. (MLFQ=세로축 "누가 먼저", MQMS=가로축 "어느 코어" → 직교, 곱해 씀.)

## 부하 불균형 해결: work stealing
- 유휴 코어가 다른 바쁜 코어 큐를 **peek**해서 작업을 훔쳐옴 (`-P` 간격).
- **트레이드오프**: 훔치면 부하균형↑ 이지만 캐시 친화성↓(옮긴 작업 cold) + peek 오버헤드.
- 너무 자주 훔침 → MQMS 장점 사라짐(SQMS로 회귀). 너무 드물게 → 불균형 오래.

---

## 숙제 (multi.py) — 실측으로 발견한 것

모델: CPU마다 캐시(`-M`), 작업 = 실행시간 + working set. 캐시 cold=느림(1x), warm=빠름(`-r`배, 기본 2x), warm되는 시간 `-w`(기본 10). 정책: 기본 SQMS / `-p` MQMS / `-P` peek 간격.

**직접 확인한 것들:**
1. **캐시 효과**: `a:100:100`, warmup 10, 2x → cold 10틱(10 진행) + warm 45틱(90 진행) = **55틱.**
2. **퀀텀 vs warmup**: 퀀텀(10) ≤ warmup(10)이면 **캐시가 절대 안 데워짐**(warm되기 직전 쫓겨남) → warm 0%. 퀀텀(30) > warmup(10)이어야 데워질 틈이 생김.
3. **대칭 워크로드면 SQMS=MQMS**: 작업 4·CPU 4 또는 완전 대칭이면 SQMS도 안정 배정돼 차이 없음. **차이는 비대칭/경쟁 시** 드러남.
4. **캐시 크기 vs working set 합** (직접 발견): 같은 코어 작업들 working set 합 ≤ 캐시면 교체돼도 **안 밀려 warm 유지**(최적). 초과하면 서로 밀어내 **cache thrashing**(계속 cold).
5. **work stealing 반례** (핵심 발견): `a:100:100,b:100:100,c:30:100`, `-p`
   - `-P 30`(훔침): b 끝난 뒤 CPU1이 a를 훔침 → a가 **cold부터** → **85틱.**
   - `-P 0`(안 훔침): a가 CPU0에 warm 유지 → **80틱.** → **안 훔친 게 빠름!**
   - 이유: **작업 하나(a)만 남아 병렬 이득 없음** → 옮기면 cold 페널티만. work stealing은 공짜 아님.

---

## 핵심 통찰 (스스로 발견)

- **작업 하나(스레드 1개)는 옮겨도 병렬 아님** — 한 번에 한 코어에서만 실행. work stealing의 병렬 이득은 **여러 작업이 남아 각 코어가 다른 걸 동시 실행할 때**만.
- **work stealing 이득 조건**: 병렬 이득(노는 코어 활용) > cold 페널티. 병렬 안 되면 cache-hot 작업은 **안 옮기는 게 나음.**
- 그래서 실제 스케줄러는 **cache-hot 태스크 마이그레이션을 꺼림**(migration cost 계산) — 무작정 안 훔침.
- 멀티코어 스케줄링 = **부하 균형 ↔ 캐시 친화성/오버헤드**의 저울질.

## 심화 Q&A (질문하며 정리)

- **peak 연산량(코어수×성능) ≠ 실제 속도**: 병렬성이 그 상한을 얼마나 채우냐 + 메모리 대역폭·락·전력이 정함. 직렬 작업엔 소수 고성능 코어, 병렬엔 다수 코어. → 현대 CPU는 **이종 코어**(P/E core)로 둘 다.
- **스케줄러가 병렬성을 재나?**: 아니. 병렬성은 **프로그램(스레드 수)**이 정함. 스케줄러는 스레드를 배치할 뿐(관찰 가능한 CPU/IO/우선순위로). 역할 분담 = "병렬화는 프로그램, 배치는 스케줄러."
- **공유 많으면 코어 적게 vs 병렬 이득**: 암달의 법칙 + 락/캐시 오버헤드. 공유 적으면 코어↑ 이득, 많으면 오버헤드가 이득 잡아먹음(sweet spot 존재).

## ① "락 경합" — 정확히 무엇이 비싼가

그때의 답: *"코어가 많아지면 락이 걸리는 동안 다른 프로세스는 그 큐에 접근을 못 하니 오버헤드 발생."* → 맞지만 거칠다.

**락 획득 비용 = 원자적 명령(`xchg`/`cmpxchg`)의 비용** (Ch28):
```
일반 mov (L1 히트)      : ~1 사이클
원자적 명령 (경합 없음)  : ~20~50 사이클
원자적 명령 (경합 있음)  : 수백 사이클 + 캐시 라인 이동
```

**왜 비싼가 — 캐시 일관성:** 원자성을 보장하려면 그 캐시 라인을 **독점(Exclusive)으로 확보**해야 함. 다른 코어가 갖고 있으면 **뺏어와야** 하고, 그게 코어 간 상호연결을 타는 트랜잭션.
```
코어0이 xchg → 코어1~7의 라인 무효화(Invalidate 브로드캐스트)
코어1이 xchg → 코어0의 라인 무효화, 라인이 코어1로 이동
코어2가 xchg → 또 이동
... 락 캐시 라인이 코어들 사이를 계속 튕겨다님 (cache line ping-pong)
```

### 왜 "단순 비례"가 아니라 초선형인가

`(m-1) × 락 점유 시간` = **대기 시간**이고 이건 선형. 그런데 두 가지가 더 있음:

**⓵ 획득 1회의 비용 자체가 커진다.** 코어가 많을수록 캐시 라인이 더 자주·더 멀리 이동 → 20사이클이던 게 수백 사이클로. **선형 항에 곱해지는 계수가 커짐 → 초선형.**

**⓶ 락을 안 잡고 있는 코어도 시스템을 느리게 한다** ★
```asm
xchg %ax, mutex     ; 스핀 대기 루프 — 실패해도 매번 "쓴다"
```
- 기다리는 코어들의 쓰기가 계속 캐시 라인을 무효화
- **락을 쥐고 실제로 일하는 코어까지 느려짐** (자기 캐시가 계속 무효화됨)
- 대기 코어가 많을수록 상호연결이 무효화 트래픽으로 포화
- → **기다리는 놈들이 일하는 놈을 방해하는 구조.** 코어를 늘리면 처리량이 늘다가 **어느 지점부터 오히려 감소.**

> 그래서 실제 스핀락은 **test-and-test-and-set** — 먼저 일반 load로 읽어보고(공유 상태 캐시 가능, 조용함) 자유로울 때만 `xchg`. 무효화 트래픽을 크게 줄임.

### 헷갈렸던 것: 캐시 라인 독점 ≠ 락

| | 무엇 | 지속 시간 | 누가 |
|--|--|--|--|
| **캐시 라인 독점** | 하드웨어 수준 | **명령 하나 (~수십 사이클)** | CPU가 자동 |
| **락(mutex)** | 소프트웨어 수준 | **lock()~unlock() (임의로 김)** | 개발자가 배치 |

**락이 "잠겼다"는 건 `flag` 값이 1이라는 뜻**이지 하드웨어가 그 메모리를 봉인한 게 아님. 다른 코어는 그 라인을 자유롭게 읽고 씀 — `xchg` 해봐야 1을 받아 물러날 뿐.
**매 `xchg`마다 라인을 확보했다 놓으므로** 핑퐁이 발생. (Ch28의 "락은 규약"과 같은 얘기)

## ② SQMS/MQMS = Ch29 자료구조와 같은 구조 ★

```
SQMS : 공유 큐 하나 + 락 하나        ↔  정확한 카운터 (공유 변수 + 락 하나)
MQMS : CPU마다 큐 + 각자의 락        ↔  sloppy counter (CPU별 지역 카운터)
```

**대가까지 대응된다:**
| | 얻은 것 | 포기한 것 |
|--|--|--|
| **sloppy counter** | 확장성 | **전역 값의 정확성** (오차 ≤ NUMCPUS × S) |
| **MQMS** | 확장성 | **부하 균형** (한 CPU는 놀고 한 CPU는 밀림) |

**둘 다 "전역적으로 옳은 상태"를 포기하고 확장성을 얻음.**

**보정 방법까지 대응:**
```
sloppy counter : S번마다 전역 카운터에 합침       ← 가끔 경계를 넘어 동기화
MQMS           : 가끔 work stealing으로 재분배     ← 가끔 경계를 넘어 동기화
```
**그 빈도가 트레이드오프의 손잡이:**

| | 자주 동기화 | 드물게 동기화 |
|--|--|--|
| sloppy counter (S 작게↔크게) | 정확 / 느림 | 부정확 / 빠름 |
| MQMS (steal 자주↔드물게) | 균형 좋음 / 오버헤드 큼 | 불균형 / 오버헤드 작음 |

**Ch29의 확장성 조건으로 정리:**
```
① 락당 작업량이 커야 (락 비용이 묻히게)
② 접근 패턴이 독립적이어야
MQMS: CPU마다 자기 큐만 → ② 만족 ✅
SQMS: 모두가 한 큐를    → ② 위반 ❌
```
**"독립적으로 나눌 수 있는 축"이 여기선 CPU.** 해시 테이블의 버킷, sloppy counter의 CPU와 같은 발상.

## ③ work stealing 반례가 이제 완전히 설명된다

그때 실측으로 발견한 것:
```
-P 0  (안 훔침) : 80 ticks
-P 30 (훔침)    : 85 ticks   ← 훔치는 게 오히려 손해
```
그때는 "오버헤드 때문"으로 끝났는데, **그 오버헤드의 정체:**

1. **남의 큐 락을 잡아야 함** → 원자적 명령 + 캐시 라인 이동
2. **작업을 옮기면 캐시/TLB 친화성이 깨짐** → 아래 ④ 참고
3. **훔치기가 실패해도 비용은 지불** — 남의 큐를 봤는데 훔칠 게 없으면 순수 낭비

> **work stealing = "독립성 경계를 넘는 행위"이고, 경계를 넘는 데는 항상 비용이 든다.**
> 부하 불균형으로 잃는 것 < 경계를 넘는 비용이면 **안 훔치는 게 낫다.** (실측으로 확인한 것)

## ④ 마이그레이션 시 정확히 무엇을 잃는가

그때의 답: *"같은 프로세스는 같은 코어에서 실행되는 게 캐시를 효율적으로 활용할 수 있어."* → 맞지만 무엇을 잃는지 불명확했음.

**옮겨지는 것 vs 옮길 수 없는 것:**
```
레지스터   : TCB에 저장 → 새 코어에서 복원. 명시적으로 이동 ✅
캐시/TLB   : 코어 전용 하드웨어. 복사 불가 ❌ → 콜드 스타트
```

| 잃는 것 | 왜 못 옮기나 | 비용 (Ch19 실측) |
|--|--|--|
| **L1/L2 캐시** (데이터+명령어) | 코어 전용 하드웨어 | L1 히트 ~1ns → 메모리 ~100ns (100배) |
| **TLB** ★ | **코어마다 자기 TLB** | 히트 1.4ns → 미스 9.9ns (7배) |
| **분기 예측기** | 코어 전용, 학습 상태 소실 | 예측 실패마다 파이프라인 플러시 10~20사이클 |

**TLB를 놓쳤던 것이 포인트.** 코어0에서 채워둔 VPN→PFN 번역이 코어1엔 없음 → **전부 미스 → page table walk 4번씩.**

```
마이그레이션 직후: 워킹셋을 다시 채울 때까지 수십~수백 μs 느려짐
```
→ 그래서 스케줄러가 **cache-hot 태스크의 마이그레이션을 꺼림**(migration cost 계산).
→ 성능이 중요한 서버는 **CPU pinning**으로 워커를 코어에 고정 (`taskset` — Ch27 실험에서 쓴 그것).

## ⑤ 근본 원리 — 동기화를 빠르게 vs 필요 없게

**"락과 원자적 명령을 안 쓰면?"**을 따져보면:

| | 가능? | 특징 |
|--|--|--|
| **원자적 명령만 (lock-free)** | 가능 — 단일 변수 갱신이면 CAS로 | 재시도 비용, **캐시 핑퐁은 그대로**, ABA·메모리 회수 문제로 설계 난이도↑ |
| **락만, 원자적 명령 없이** | **불가능** | 락 자체가 원자적 명령으로 만들어짐 (Ch28 부트스트랩) |
| **둘 다 안 쓰기** | **가능 — 공유를 없애면** ★ | CPU마다 자기 데이터만 → 락도 CAS도 불필요, 핑퐁 0 |

```
MQMS에서 CPU가 자기 큐만 건드리면 → 접근 스레드가 하나 → 동기화 불필요 ✅
work stealing 할 때만 남의 큐 → 그때만 락 필요
```

> ### 핵심 원리
> **진짜 확장성은 동기화를 빠르게 만드는 게 아니라, 동기화가 필요 없게 데이터를 나눠 소유하는 데서 나온다.**
> ```
> 동기화를 빠르게 → 락 최적화, lock-free   (한계 있음)
> 동기화를 없애기 → 데이터를 나눠 소유       ★ 근본 해결
> ```
> 리눅스 per-CPU 변수, sloppy counter, MQMS, Go의 채널 철학이 전부 이것.
> *"메모리를 공유해서 통신하지 말고, 통신해서 메모리를 공유하라."*

## 재방문 요약 — 그때 vs 지금

```
그때: "락 때문에 느리다"

그때: "MQMS는 부하 불균형"
지금: sloppy counter와 같은 구조 — 독립성을 얻고 전역 정확성을 포기.
      work stealing = 가끔 경계를 넘는 보정. 그 빈도가 트레이드오프 손잡이

그때: "-P 0이 -P 30보다 빨랐다" (반례만 발견)
지금: 경계를 넘는 비용 = 남의 큐 락 + 캐시/TLB 콜드 + 실패해도 지불
      → 불균형 손실 < 경계 비용이면 안 훔치는 게 낫다
