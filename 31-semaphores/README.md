# OSTEP Ch 31 — Semaphores 정리

락과 조건 변수를 **하나의 도구로 통합.** Ch30보다 쉽다 — 신경 쓸 게 줄어들기 때문.
핵심: **초기값이 용도를 결정한다.**

---

## 정의 — 이게 전부

```c
sem_t s;
sem_init(&s, 0, X);    // X로 초기화 (두 번째 인자 0 = "이 프로세스 내에서만")

sem_wait(&s);          // 값-- 하고, 값이 음수면 잠듦
sem_post(&s);          // 값++ 하고, 대기자가 있으면 하나 깨움
```

**불변식:**
```
값 = 초기값 − (wait 호출 수) + (post 호출 수)
값이 음수일 때 |값| = 잠들어 있는 스레드 수
임계 영역에 있는 스레드 수 ≤ 초기값
```

### ★ 오해 교정: "값이 음수면 아무도 못 들어간다" — 틀림

**`sem_post`는 값의 부호와 무관하게 대기자 하나를 깨운다.**
"값이 0 이상이 되면 깨운다"가 아니라 **"대기자가 있으면 깨운다".**

**왜 그래도 되나 — 잠든 스레드는 이미 자기 몫을 감소시켰기 때문.**
```c
sem_wait: 값--  → 음수면 잠듦
//        ↑ 감소는 이미 끝남. 잠든 건 그 다음
```
깨어난 스레드는 "내 감소가 이제 유효해졌다"는 뜻이라 바로 진입. 값이 여전히 음수인 건 **나 말고 다른 사람들이 아직 기다린다**는 뜻일 뿐.

**추적 (초기값 2, 스레드 5개):**
```
T1 wait: 2→1, 통과        실행 중 1
T2 wait: 1→0, 통과        실행 중 2
T3 wait: 0→-1, 잠듦       대기 1
T4 wait: -1→-2, 잠듦      대기 2
T5 wait: -2→-3, 잠듦      대기 3

T1 post: -3→-2, T3 깨움   실행 중 2 (T2,T3)  ★ 값이 -2인데도 T3 실행
T2 post: -2→-1, T4 깨움   실행 중 2 (T3,T4)
T3 post: -1→0,  T5 깨움   실행 중 2 (T4,T5)
T4 post: 0→1              실행 중 1
T5 post: 1→2              실행 중 0. 초기값 복귀 ✅
```
**항상 "실행 중 ≤ 초기값"이 유지됨.**

## ★ 초기값이 용도를 결정한다

| 초기값 | 의미 | 용도 |
|--|--|--|
| **1** | "자원 1개, 아무도 안 씀" | **락** (이진 세마포어) |
| **0** | "아직 아무 일도 안 일어남" | **순서 보장 / 신호** (join 등) |
| **N** | "자원 N개" | **동시 접근 수 제한** (throttling) |

### 초기값 1 = 락

```c
sem_init(&m, 0, 1);
sem_wait(&m);    // = lock()
... 임계 영역 ...
sem_post(&m);    // = unlock()
```
```
 1 : 자유
 0 : 한 명 사용 중
-1 : 사용 중 + 한 명 대기
-2 : 사용 중 + 두 명 대기
```

### 초기값 0 = 순서 보장

```c
sem_init(&s, 0, 0);
// 부모                    // 자식
sem_wait(&s);              printf("child\n");
printf("parent: end\n");   sem_post(&s);
```

**부모가 먼저:**
```
부모: wait → 0-1 = -1 → 잠듦
자식: "child" 출력 → post → -1+1 = 0 → 부모를 깨움
부모: "parent: end"
```
**자식이 먼저:**
```
자식: "child" 출력 → post → 0+1 = 1 (대기자 없음, 값만 남음)
부모: wait → 1-1 = 0 → 음수 아니니 안 잠듦. 바로 통과
```
**두 경우 다 순서가 보장됨.**

> ### 왜 조건 변수보다 간단한가 ★
> ```
> 조건 변수: 신호가 유실될 수 있음 → 별도 상태 변수(done) 필요 + while 필요
> 세마포어 : 값 자체가 신호를 카운트해서 보관 → 별도 변수 불필요
> ```
> **세마포어는 값 자체가 기억이다.** 자식이 먼저 post하면 값이 1로 남아 있다가 나중에 온 부모가 소비.
> 락 + 조건 변수 + 상태 변수 **셋이 세마포어 하나로** 줄어듦.

### 초기값 N = 동시 접근 제한

```c
sem_init(&s, 0, 10);   // 스레드 100개가 wait/post로 감싸도
                        // 동시 실행은 항상 10개 이하
```
```
100개 wait → 10개 통과, 90개 대기, 값 = -90
1개 post   → 값 -89, 대기자 1명 깨움 → 여전히 10개 실행 중
```
**용도:** 커넥션 풀(DB 연결 10개), 동시 다운로드 제한, 워커 풀에서 특정 자원만 N개 제한.

## 생산자-소비자

**세마포어 값 = 그 자원의 현재 개수.** 이 대응만 잡으면 나머지는 자동.

```c
sem_init(&empty, 0, N);    // 빈 칸 N개 (처음엔 다 비었으니)
sem_init(&fill,  0, 0);    // 채워진 항목 0개
sem_init(&mutex, 0, 1);    // 락

void *producer(void *arg) {
    sem_wait(&empty);      // 빈 칸 하나 소비 (없으면 대기)
    sem_wait(&mutex);      // ★ 락은 가장 안쪽
    put(i);
    sem_post(&mutex);
    sem_post(&fill);       // 채워진 항목 하나 증가
}

void *consumer(void *arg) {
    sem_wait(&fill);       // 항목 하나 소비 (없으면 대기)
    sem_wait(&mutex);
    int v = get();
    sem_post(&mutex);
    sem_post(&empty);      // 빈 칸 하나 증가
}
```
**대칭:** 생산자는 `empty`를 쓰고 `fill`을 만들고, 소비자는 정반대.

**Ch30 조건 변수 버전과 비교:**
```c
// 조건 변수                          // 세마포어
lock(&m);                             sem_wait(&empty);
while (count == N) cond_wait(&empty,&m);  sem_wait(&mutex);
put(i);                               put(i);
cond_signal(&fill);                   sem_post(&mutex);
unlock(&m);                           sem_post(&fill);
```
**락도, while도, count 변수도 사라짐.** 세마포어 값이 count 역할을 하고 대기 조건도 값에 내장됨.

### ★ mutex는 반드시 가장 안쪽에 — 순서를 바꾸면 데드락

```c
// ❌ 잘못된 순서
sem_wait(&mutex);      // 락 먼저
sem_wait(&empty);      // 그다음 빈 칸 대기
```
```
버퍼가 꽉 참 (empty = 0)
P: wait(&mutex) 통과 → 락 획득
P: wait(&empty) → -1 → 잠듦  ★ 락을 쥔 채로!
C: wait(&mutex) → 락은 P가 쥐고 있음 → 잠듦
   → 소비자가 꺼내야 empty가 느는데 락 때문에 못 들어감
   → P는 empty를, C는 mutex를 기다림 → 영원히 멈춤
```
> **"락을 쥔 채로 잠들면 안 된다."** Ch30에서 `cond_wait`이 락을 놓고 자야 했던 것과 같은 이유.
> **규칙: 대기용 세마포어를 먼저 통과한 다음 락을 잡는다.**

### 세 층의 역할 구분 (헷갈렸던 것)

| | 담당 | 값의 의미 |
|--|--|--|
| **포인터** (fill_ptr, use_ptr) | **위치** — 어디를 건드릴까 | 배열의 몇 번째 칸 |
| **세마포어** (empty, fill) | **개수 + 통행 허가** — 들어가도 되나 | 남은 자원 수 |
| **mutex** | **상호 배제** — 포인터/배열 보호 | 1 = 자유 |

**생산자가 1명뿐이면 mutex 불필요** — fill_ptr를 건드리는 스레드가 하나뿐이니까. mutex는 **같은 쪽에 여러 명일 때** 필요.

### `empty = N − fill` 아닌가? (좋은 관찰이지만)

**평형 상태에서만 성립.** 대기자가 있으면 어긋남:
```
N=5, 버퍼 꽉 참, 생산자 3명 대기
empty = -3 (빈 칸 0 + 대기자 3),  fill = 5,  합 = 2 ≠ 5
```

**하나로 합칠 수 없는 이유 (더 중요):**
- `sem_wait`은 "값을 읽고 판단"이 아니라 **"감소시키고, 안 되면 잠든다"는 하나의 원자적 동작**
- POSIX엔 값을 읽는 쓸모 있는 방법이 사실상 없음 (`sem_getvalue`는 읽는 순간 낡은 값)
- **본질은 값이 둘이 아니라 대기 큐가 둘이라는 것** — 생산자용 대기실과 소비자용 대기실
  → Ch30에서 조건 변수를 둘로 나눈 것과 같은 이유: **대기실이 하나면 누구를 깨울지 구분 못 함**

> 이런 관계는 **불변식(invariant)** — "대기자가 없을 때 empty+fill이 N이 아니면 버그"처럼 검증에 씀.

## 리더-라이터 락

**동기:** 읽기 99%, 쓰기 1%인 자료구조(설정, 해시 테이블)에서 일반 락은 **읽기끼리도 직렬화**시켜 낭비.

```
읽기 ↔ 읽기 : 동시 가능 ✅  (아무도 안 바꾸니 서로 영향 없음)
읽기 ↔ 쓰기 : 불가 ❌
쓰기 ↔ 쓰기 : 불가 ❌
```

```c
typedef struct {
    sem_t lock;        // readers 카운터 보호 (초기값 1)
    sem_t writelock;   // 쓰기 권한 (초기값 1)
    int readers;
} rwlock_t;

void acquire_readlock(rwlock_t *rw) {
    sem_wait(&rw->lock);
    rw->readers++;
    if (rw->readers == 1) sem_wait(&rw->writelock);   // ★ 첫 독자가 작가를 막음
    sem_post(&rw->lock);
}
void release_readlock(rwlock_t *rw) {
    sem_wait(&rw->lock);
    rw->readers--;
    if (rw->readers == 0) sem_post(&rw->writelock);   // ★ 마지막 독자가 풀어줌
    sem_post(&rw->lock);
}
void acquire_writelock(rwlock_t *rw) { sem_wait(&rw->writelock); }
void release_writelock(rwlock_t *rw) { sem_post(&rw->writelock); }
```
**트릭: 첫 독자가 문을 잠그고 마지막 독자가 연다.** 그 사이 독자들은 자유롭게 드나듦.

### 문제 — 작가 굶주림(writer starvation)

```
독자1 진입 → readers=1 → writelock 획득
작가: 대기...
독자2 진입 → readers=2   (writelock은 이미 독자들이 쥐고 있어 그냥 들어옴)
독자1 퇴장 → readers=1   (0이 아니니 writelock 안 놓음)
독자3 진입 → readers=2
→ 독자가 끊이지 않으면 readers가 절대 0이 안 됨 → 작가 영원히 대기
```
**읽기가 많은 워크로드에서 정확히 최악** — 이 락을 쓰는 이유가 바로 그 상황인데.

**해결:** **작가 우선(writer-preference)** — 작가가 대기 중이면 새 독자를 막음. 그럼 독자가 굶을 수 있어 보통 번갈아 우선권을 주는 절충.
(리눅스 `pthread_rwlock`은 기본 독자 우선, `PTHREAD_RWLOCK_PREFER_WRITER_NONRECURSIVE_NP`로 변경 가능)

### ★ 실무 조언 — rwlock은 생각보다 안 좋다

```
일반 mutex  : 원자적 연산 2번 (lock/unlock)
reader lock : lock(&lock), readers++, 조건부 writelock, post(&lock)
              = 원자적 연산 4~6번
```
**읽기 하나 하려고 락을 여러 번 잡음.** Ch29의 교훈 재등장 — **더 정교한 게 더 빠른 게 아니다.**
임계 영역이 짧으면(해시 조회 몇 십 사이클) **rwlock 오버헤드가 실제 작업보다 커서 일반 mutex보다 느림.**

**원칙:** 일단 일반 mutex로 짜고, **측정해서** 읽기 경합이 진짜 병목이면 그때 고려.
요즘은 **RCU(Read-Copy-Update)**나 lock-free 자료구조가 더 많이 쓰임 — 읽기 쪽이 락을 아예 안 잡음.

## 식사하는 철학자

철학자 5명, 각자 양옆 포크 2개를 잡아야 식사. 포크는 5개.

```c
void philosopher(int p) {
    sem_wait(&fork[left(p)]);
    sem_wait(&fork[right(p)]);
    eat();
    sem_post(&fork[left(p)]);
    sem_post(&fork[right(p)]);
}
```

**5명이 동시에 왼쪽 포크를 집으면:**
```
철학자0: 포크0 획득, 포크1 대기
철학자1: 포크1 획득, 포크2 대기
철학자2: 포크2 획득, 포크3 대기
철학자3: 포크3 획득, 포크4 대기
철학자4: 포크4 획득, 포크0 대기 → 철학자0이 쥐고 있음
→ 원을 그리며 서로를 기다림. 전원 아사.
```
**데드락 4조건 중 순환 대기(circular wait).**
Ch27 `main-deadlock.c`(m1→m2 vs m2→m1)와 **완전히 같은 구조**, 사이클이 5개짜리로 커졌을 뿐.

**해법 — 4조건 중 하나만 깨면 됨:**
```c
// ① 한 명만 반대 순서로 → 순환 대기를 깸
if (p == 4) { sem_wait(&fork[right(p)]); sem_wait(&fork[left(p)]); }
else        { sem_wait(&fork[left(p)]);  sem_wait(&fork[right(p)]); }
```
**한 명만 역방향이어도 고리가 안 닫힘.**
- **② 동시에 앉는 인원을 4명으로 제한** (세마포어 초기값 4) → 최소 한 명은 반드시 양쪽을 얻음 = **점유 대기**를 깸
- **③ 두 포크를 원자적으로 집기** (둘 다 가능할 때만) = **점유 대기**를 깸

## ★ 개념 교정: "문맥 교환이 모든 문제의 원인"이 아니다

멀티코어에선 문맥 교환 없이도 진짜 동시에 돌아 같은 문제가 발생(Ch27 `race 1000000`에서 절반 손실).
문맥 교환은 단일 코어에서 동시성을 **흉내내는 수단**일 뿐.

**진짜 원인:**
> 여러 실행 흐름이 공유 자원을 건드리는데, 그 흐름들의 **순서가 보장되지 않는다.**

그리고 이건 **버그가 아니라 동시성의 정의**라 없앨 수 없음.
→ 우리가 하는 일은 원인 제거가 아니라 **"어떤 순서로 섞여도 결과가 옳도록" 설계하는 것.**

## 실전 포인트

- **세마포어 2개 규칙**(`wait`: 값-- 후 음수면 대기 / `post`: 값++ 후 대기자 깨움)과 **초기값 3용도**(1=락, 0=순서, N=제한). 면접 단골.
- **음수 값 = 대기자 수**, `post`는 부호와 무관하게 하나 깨움.
- **생산자-소비자를 세마포어로** 쓸 수 있어야 — `empty=N, fill=0, mutex=1`.
- **mutex를 가장 안쪽에** 두는 이유(락 쥔 채 잠들면 데드락).
- **rwlock의 작가 굶주림**과 "실무에선 일반 mutex가 나을 수 있다".
- **철학자 = 순환 대기**, 한 명만 순서를 뒤집으면 해결.
- **조건 변수 대비 세마포어의 장점**: 값이 신호를 기억 → 상태 변수·while 불필요.
