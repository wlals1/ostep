# OSTEP Ch 20 — Advanced Page Tables (멀티레벨) 정리

Ch18에서 걸어둔 빚 — **선형 페이지 테이블 4MB/프로세스** — 을 갚는 장.
핵심: **페이지 테이블도 페이지에 담는다.** 안 쓰는 조각은 아예 안 만듦.
★ Ch2에서 무너졌던 **CR3가 가리키는 구조**의 정식 답.

---

## 문제 — 선형 테이블은 왜 통째로 커야 하나

32비트 / 4KB 페이지 / PTE 4B → VPN 20비트 → PTE **2²⁰ = 100만 개** → **4MB, 프로세스마다.**

**O(1) 인덱싱의 대가:**
```
PageTable[999999] 의 주소 = base + 999999 × 4 = base + 3,999,996
```
곱셈 한 번으로 바로 점프하려면 **앞 칸들이 실제로 자리를 차지**해야 함. 중간을 비우면 위치 계산이 깨짐.
→ **안 쓰는 칸(valid=0)도 존재해야 하고, 그게 4MB의 정체.**

**칸 vs 프레임 (Ch18에서 잡은 것 재확인):**
| | 안 쓰는 VPN |
|--|--|
| 물리 프레임 | 안 붙음 |
| **PTE 칸** | **존재함, valid=0** ← 낭비 |

### 낭비가 뭉쳐 있다는 관찰 ★

```
VPN 0 ~ 15          : 코드/힙   valid=1
VPN 16 ~ 999,980    : 텅 빈 중간 valid=0   ← 99.99%가 여기 연속 덩어리로
VPN 999,981~999,999 : 스택     valid=1
```
- **흩어져 있으면 못 걷어냄** (뺀 만큼 뒤가 밀려 인덱싱 붕괴).
- **연속 덩어리면** "이 구간 전체 없음"을 한 마디로 표현 가능 → 실마리.

### 왜 "쓰는 VPN만 압축"은 안 되나 (내가 물어본 것)

**VPN은 우리가 붙이는 순번이 아니라 가상 주소를 자른 결과값.** 선택권 없음.
```
가상주소 0x3f8c04 → VPN = 상위비트 = 1016   (컴파일러·SP가 정한 주소에서 나옴)
```
쓰는 페이지에 0,1,2로 재번호하면 → CPU는 주소에서 나온 **1016**을 들고 오는데 "1016 → 2번 칸"을 알려줄 변환표가 필요 → **그 표가 다시 VPN 전체 범위(100만 칸)** → 원점.

> **하드웨어는 "주소에서 자른 VPN"으로 O(1)에 찾아야 하고, VPN 값은 못 고친다.**
> 그래서 "VPN을 인덱스로 쓰는 배열"이 강제됨.

**멀티레벨은 재번호를 안 함 — VPN을 그대로 두고 두 토막으로 쪼개 쓸 뿐.**

## 해결 — 테이블을 페이지 크기로 조각내기

### ★ 왜 하필 조각 = 4KB (페이지 크기)인가

**페이지 테이블도 메모리에 저장되고, 메모리는 페이지 단위로 관리되니까.**
- 조각 하나 = 프레임 하나에 딱 → OS가 빈 프레임 하나 잡아 조각 하나 생성.
- 조각들을 **물리 어디에나 흩어 놔도 됨** → PDE가 **PFN 하나**로 위치 지정 가능.
- 어중간한 크기(7KB 등)면 연속 2페이지 필요 → **외부 단편화 부활**(Ch17). 페이지 크기에 맞추는 게 원천 차단.

**나머지는 자동으로 따라 나옴:**
```
조각 4KB, PTE 4B → 조각당 PTE 1024개 → PTI 10비트
VPN 20 − PTI 10  → PDI 10비트 → 디렉터리 1024칸
디렉터리 1024 × 4B = 4KB → 디렉터리도 딱 한 페이지 ✅
```
전부 4KB에 맞아떨어짐 — 우연이 아니라 **"모든 걸 페이지 크기에 맞춘다"**는 설계 원칙의 결과.

### 도입 순서 (논리 흐름)

```
1. 안 쓰는 구간의 PTE를 통째로 걷어내고 싶다        (동기)
2. 그러려면 테이블을 조각내야 한다                  (수단)
3. 조각 크기 = 페이지 크기(4KB)                    ★ 프레임 하나에 딱, 단편화 없음
4. → 조각당 PTE 1024, 조각 1024개, 디렉터리도 4KB   (자동)
5. 조각 위치를 기록할 상위 표(디렉터리)가 필요 → 2단계
```

### 두 층 분리 (헷갈렸던 것)

```
층1 (상위) = 페이지 디렉터리 — "조각 k가 물리 어디 있냐"   각 칸 = PDE
층2 (하위) = 조각들 — 그 안에 PTE(VPN→PFN)              각 칸 = PTE
```
조각 안의 PTE는 여전히 VPN→PFN. 하지만 **조각 자체의 위치는 조각 안에 안 적혀 있음** → 밖(층1)에서 관리.

### 절약 계산

```
필요한 조각 3개 × 4KB      =  12KB
디렉터리                   =   4KB
─────────────────────────────────
합계                       =  16KB     (선형 4MB → 250배 절약)
안 만든 조각 1021개 × 4KB  ≈   4MB 절약
```

**낭비가 사라진 게 아니라 1000배 작은 층으로 밀려남:** 디렉터리도 1021칸이 valid=0이지만 그건 `1021 × 4B = 4KB`. 층2에서 같은 구간이 `1021 × 4KB = 4MB`였던 것 대비 1000배 압축. **층1의 한 칸(4B)이 층2의 한 조각(4KB, PTE 1024개)을 대표.**

## 번역 흐름

```
32비트 가상주소
[ PDI 10 ][ PTI 10 ][ offset 12 ]
└──── VPN 20비트 ────┘

① CR3 → 페이지 디렉터리 물리 위치
② PDE = Directory[PDI]
     valid=0 → 그 구간 조각 자체가 없음 → fault
     valid=1 → 조각의 PFN
③ PTE = 조각[PTI]                      ← 메모리 접근 2번째
     valid 검사 → 데이터 페이지의 PFN
④ 물리주소 = (PFN << 12) | offset       ← 메모리 접근 3번째(실제 데이터)
```

**CR3 = 페이지 디렉터리의 물리 주소를 담은 레지스터.**
문맥 교환 시 **CR3 하나만 교체**하면 주소 공간 전체가 갈아끼워짐 (프로세스마다 디렉터리가 따로).
→ **Ch2의 "두 프로세스가 같은 가상주소를 찍는데 왜 안 섞이나"의 최종 답.**

## 대가 — 공간 vs 시간

| | 선형 | 2단계 | 4단계(x86-64) |
|--|--|--|--|
| 공간 | 4MB | **16KB** ✅ | 더 절약 |
| 번역 메모리 접근 | 1번 | **2번** ❌ | **4번** ❌ |
| 데이터 포함 총 | 2번 | 3번 | 5번 |

**공간 250배를 아낀 대가로 번역이 2배(64비트는 4배) 느려짐.** Ch17부터 반복된 공간↔시간 트레이드오프.

### TLB가 이 대가를 갚는다 ★

**TLB에 저장되는 건 최종 결과 하나 — `VPN → PFN`.** 중간 단계(디렉터리, 조각)는 저장 안 함.
몇 단계를 거쳤든 결론은 "이 VPN은 저 PFN" 한 줄이니까.

```
TLB 엔트리: [ VPN │ PFN │ valid │ ASID │ 권한 ]
                   ↑ walk의 최종 결과만
```

| | TLB 히트 | TLB 미스 |
|--|--|--|
| 2단계 | 번역 0 + 데이터 1 = **1번** | 2 + 1 = 3번 |
| 4단계 | 번역 0 + 데이터 1 = **1번** | 4 + 1 = 5번 |

**히트하면 단계 수와 무관하게 1번.** 히트율 99%면:
```
평균 = 0.99 × 1 + 0.01 × 5 ≈ 1.04번   ← 페이징 없을 때(1번)와 거의 같음
```

> **멀티레벨이 성립하는 건 TLB가 있어서다.** TLB 없이 4단계 walk를 매번 하면 5배 느려 못 씀.

## walk에 무한 재귀가 없는 이유 ★

TLB 미스 시 walk는 메모리를 2~4번 읽는데 — 그 주소들도 번역이 필요하지 않나?

**아니다. walk에 쓰이는 모든 포인터가 물리 주소.**
```
CR3 (물리)              → 번역 불필요, 바로 읽음
PDE의 조각 위치 (물리)   → 번역 불필요
PTE의 PFN (물리)        → 번역 불필요
```
번역이 필요한 건 처음 들어온 **가상 주소 하나뿐**이고, walk는 물리 주소 세계에서만 움직임.

**Ch19 미스 핸들러 재귀와 같은 해법:**
> **번역 메커니즘 자체는 번역에 의존하면 안 된다.** 바닥을 물리 주소로 깔아 재귀를 끊는다.
> (락 구현이 락을 필요로 하면 안 되고, 페이지 폴트 핸들러가 폴트를 내면 안 되듯.)

**부수 효과:** 커널도 가상 주소로 동작하는데 페이지 테이블은 물리로 다뤄야 함
→ 리눅스는 **물리 메모리 전체를 커널 가상 주소 공간에 선형 매핑**(`__va()`/`__pa()`는 상수 오프셋 변환). xv6 `vm.c`에서 재확인 예정.

## 실전 포인트

- **CR3 + 멀티레벨 + 문맥 교환**: "두 프로세스가 같은 가상주소를 써도 안 섞이는 이유" → 프로세스마다 디렉터리, CR3 교체. (Ch2 체크포인트 회수)
- **왜 조각 크기 = 페이지 크기인가** → "페이지 테이블도 페이지에 담는다". 면접에서 설계 감각 보여주는 답.
- **TLB에 캐시되는 건 최종 VPN→PFN 하나** → 단계 수가 히트 성능에 영향 없음. 자주 틀리는 포인트.
- **walk는 전부 물리 주소** → 재귀 없음. 시스템 설계의 일반 원리("메커니즘은 자신에 의존 금지").
- 공간↔시간 트레이드오프를 숫자로 말하기 (4MB↔16KB, 접근 1↔2~4번).

### 다른 접근 (비교)

| 방식 | 아이디어 | 특징 |
|--|--|--|
| **선형** | VPN 그대로 인덱싱 | O(1), 공간 낭비 큼 |
| **멀티레벨** ★ | 테이블을 페이지로 쪼개 상위 표로 관리 | 공간↓, 접근 횟수↑, 실전 표준 |
| **inverted/hashed** | 물리 프레임 기준 표 + 해시 | 공간 매우 작음, **검색** 필요 |
