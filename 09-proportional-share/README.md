# OSTEP Ch 9 — Scheduling: Proportional Share (비례 배분) 정리

목표가 달라짐: 반환·응답 최적화(Ch7~8)가 아니라 **각 작업에게 CPU의 정해진 비율을 보장(fair-share).**
예: "A에게 75%, B에게 25%." 클라우드 자원 배분, VM별 몫 나누기 등.

---

## Lottery Scheduling (복권)

**아이디어:** 각 작업에 **티켓(ticket)** = CPU 몫. 매 슬라이스마다:
1. `난수 % 총티켓` = 당첨 티켓번호
2. 리스트를 누적하며 훑어 그 번호 가진 작업 찾기 → 실행

```
winner = random() % total_tickets
counter = 0
for job in list:
    counter += job.tickets
    if counter > winner: return job    # 누적이 winner 넘는 순간 당첨
```

**성질:**
- **장기적·확률적 공정**: 오래 돌리면 티켓 비율로 수렴(대수의 법칙). **한 번엔 보장 X.**
- **단기 불공정**: 짧은 작업은 운의 영향 큼.
- **불공정 지표 U** = 먼저 끝난 작업 완료시각 / 나중 완료시각. 완벽=1. **작업 길수록 U→1**(수렴).

**장점:**
- **단순**: 티켓 + 난수만. 과거 상태 추적 불필요(무작위라 "지금까지 누가 얼마 받았나" 기억 안 함).
- **새 작업 우아**: 티켓 추가 + 총티켓 갱신이면 끝 (O(1), 재조정 없음).

**단점:** 부정확(확률적), 단기 불공정.

## Stride Scheduling (결정론적)

**아이디어:** 무작위 대신 정확히.
- **stride(보폭)** = 큰수 / 티켓수 (티켓 많음 → stride 작음, 고정).
- **pass(누적 진행값)** = 실행할 때마다 stride만큼 증가 (처음 0).
- **매번 pass 최소(제일 뒤처진) 작업 실행** → pass += stride.

**왜 비율대로:** 티켓 많음 → stride 작음 → 실행해도 pass 조금만 늘어 → 금방 다시 최소 → 자주 뽑힘.
- 예: A(티켓100, stride100) vs B(티켓50, stride200) → A가 2배 자주 실행 (정확히 2:1).

**장점:** 결정론적, **단기에도 정확**(운 없음).

**단점:**
- **전역 상태**: 모든 pass 값 추적 필요.
- **새 작업 처리 애매**: pass를 0으로 주면 → 기존 작업들은 pass 잔뜩 쌓여있어 **새 작업이 CPU 독점.** 뭘 줘야 공정한지 어려움.

## Lottery vs Stride

| | Lottery | Stride |
|--|---------|--------|
| 방식 | 무작위 추첨 | pass 최소 실행(결정론) |
| 정확도 | 확률적(단기 불공정) | 정확(단기도 공정) |
| 상태 | 거의 없음 | 전역(모든 pass) |
| 새 작업 | 우아(티켓 추가) | 까다로움(pass 값 애매) |

## CFS (참고 — 심화, 한 줄만 기억)

> **CFS = stride의 리눅스 실전판. stride의 pass ≈ CFS의 vruntime.**

- 리눅스 기본 스케줄러(2007~2023, 이후 EEVDF로 교체).
- **vruntime**(가상 실행시간) 누적 → **vruntime 최소 프로세스 실행** (= stride의 "제일 뒤처진 애 우선").
- 세부(참고만, 지금 몰라도 됨): weight(nice값)로 비례배분, red-black tree로 최소 O(log n) 찾기, 새 작업 vruntime을 현재 최소 근처로(독점 방지 — stride 문제 해결).

**핵심:** Ch9의 알맹이는 **lottery + stride**. CFS는 "stride의 발전형" 정도로 넘어가면 충분.

---

## MLFQ vs 비례배분 (목표 차이)

- **MLFQ**: 반환·응답 최적화 (누가 짧은/인터랙티브인지 추측).
- **Lottery/Stride/CFS**: 각자 몫(비율) 보장 (얼마나 빨리 끝나는지엔 무관심).
- 목표 자체가 다름 — 성능 지표 최적화 vs 공정 배분.

## 숙제 (lottery.py) — 실측

`난수 % 총티켓 = 당첨번호` → 누적 훑어 당첨 작업 실행. 작업 끝나면 총티켓 감소.

- `-l 10:75,10:25` → Job0이 약 3배 자주 실행(티켓 비율대로).
- **긴 작업(100) vs 짧은 작업(3)**, 둘 다 티켓 5:5:
  - **긴 작업**: 비율대로 배분이 눈에 보임(U→1, 공정).
  - **짧은 작업**: 운의 영향 커서 비율이 잘 안 보임(U가 1에서 멂). ← 직접 확인.
  - 시드(`-s`) 바꾸면 짧은 작업은 완료 순서가 매번 달라짐(운의 증거), 긴 작업은 비슷.
- **교훈**: Lottery는 장기·확률적 공정. 단기 불공정이 stride(결정론)와의 결정적 차이.
