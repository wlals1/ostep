# OSTEP Ch 17 — Free Space Management 정리

Ch16에서 남은 숙제: **크기가 제각각인 조각들을 어떻게 관리하나.**
`malloc`/`free`의 내부이자, 이 장의 실패가 곧 **페이징(Ch18)의 동기**.

---

## 문제 설정

관리 대상: **가변 크기** 빈 공간들. (고정 크기면 문제가 안 됨 — 어느 칸이든 똑같으니까.)

**외부 단편화(external fragmentation)**: 총 여유는 충분한데 **연속된** 공간이 없어 실패.
```
[1000 sz16] [ptr1 사용중] [1032 sz16] [1048 sz52]
총 free 84 바이트 → Alloc(60) 실패
```

### 왜 압축(compaction)을 못 하나 ★

살아 있는 블록을 옮겨 빈 공간을 몰면 해결되지만 — **`malloc`은 불가능.**
- 사용자가 **raw 포인터**를 들고 있음 → 옮기면 전부 dangling.
- **중간 번역 계층이 없음.** OS는 페이지 테이블이라는 계층이 있어서 물리 프레임을 옮겨도 투명(Ch13 Transparency)하지만, 할당자에겐 그런 게 없음.

```
크기가 제각각          → 외부 단편화
coalescing으로 완화    → 살아있는 블록에 막히면 한계
compaction은 근본책    → malloc은 번역 계층이 없어 불가
→ OS 층위엔 번역 계층이 있다 + 크기를 균일하게 하자 = 페이징
```

## 메커니즘

### 헤더 (header)

할당 블록 **바로 앞**에 크기·매직값 기록. `free(p)`가 크기를 알 수 있는 이유.
```c
header_t *hptr = (header_t *)p - 1;   // 포인터 산술로 헤더 접근
```
- 실제 소비 = **요청 크기 + 헤더 크기**(+정렬 패딩).
- `malloc(1)`을 100만 번 → 헤더만 8MB. **작은 할당의 오버헤드가 치명적.**
- 매직값은 **무결성 검사**용. 버퍼 오버플로우로 다음 블록 헤더를 덮으면 여기서 걸림(`free(): invalid pointer`).

### 임베디드 free list

노드를 저장할 별도 메모리가 없음 → **빈 공간 안에 노드를 씀.**
```
0x1000 ┌──────────────┐
       │ size: 4088   │  ← 노드 {size, next}가 그 빈 공간의 첫 8바이트에 삽
       │ next: NULL   │
       ├──────────────┤
       │  (가용 영역)  │
```
- 힙이 처음 세팅되는 시점: **첫 `malloc` 때**(exec 시점 아님) → `brk`/`mmap` 시스템콜 → libc가 노드 기록 → 그때 page fault로 물리 프레임 부착.

### 정렬 (alignment)

**정렬** = 주소가 N의 배수여야 한다는 *요구*. **패딩** = 그걸 맞추려 끼우는 빈 바이트(*수단*).

`malloc`은 반환 메모리에 뭐가 담길지 모르므로 **최대 정렬을 항상 보장**(x86-64 glibc = 16).
정렬 위반 시 x86은 느려지고, ARM 일부·SIMD(`movaps`)는 **트랩**.

같은 원리가 세 군데: **구조체 패딩 / 스택 `rsp` 16정렬(ABI) / 힙 `malloc`**.

정렬로 인한 낭비 = **내부 단편화**. (10 요청 → 16 할당, 6 증발)

| | 낭비 위치 |
|--|--|
| **내부** 단편화 | 할당 블록 **안** (정렬 패딩, 헤더) |
| **외부** 단편화 | 블록들 **사이** |

### 분할(splitting)과 병합(coalescing)

- **splitting**: 큰 조각에서 필요한 만큼 잘라 쓰고 나머지를 리스트에 남김.
- **coalescing**: free할 때 **주소상 인접한** free 조각과 합침. 안 하면 붙어 있어도 따로 놈.

**coalescing은 만능이 아님** — 살아 있는 블록이 가로막으면 못 합침.

## 할당 정책 비교

같은 시드(`-s 0`)로 정책만 바꿔 실측한 결과.

| 정책 | 고르는 것 | 탐색 | 남는 조각 | 병리 |
|--|--|--|--|--|
| **BEST** | 맞는 것 중 **최소** | **항상 O(n) 전수** | 티끌(sz1) | 부스러기로 리스트가 길어짐 + 매번 전수 탐색 |
| **WORST** | **최대** | 항상 O(n) 전수 | 중간~큼 | 작은 조각 **영원히 방치** + 큰 조각 소진 |
| **FIRST** | 맞는 **첫 번째** | 조기 종료, 최선 O(1) | 상황따라 | **앞쪽 오염**(부스러기를 매번 헛되이 훑음) |
| **NEXT** | 마지막 위치부터 첫 번째 | 조기 종료 | 상황따라 | 탐색을 분산할 뿐, 조각이 고르게 퍼지면 이점 소멸 |

**BEST가 항상 전수 탐색인 이유**: "가장 작은 것"은 **끝까지 봐야 확정**. 3번째에 딱 맞아도 4번째에 더 작은 게 있을 수 있으니 못 멈춤. (exact fit 조기 종료 최적화는 가능 — 더 작을 수 없으니까.)

### WORST fit의 역설

"큰 데서 자르면 남는 조각도 커서 좋다"가 무너지는 이유 — **두 갈래**:

1. **작은 조각을 후보에조차 안 올림.** `[3][5][8][8][67]`에서 뭘 요청하든 항상 67을 고름. 앞의 넷은 큰 조각이 8 아래로 줄 때까지 **죽은 공간**.
2. **큰 조각을 스스로 파괴.** 큰 요청을 받아낼 유일한 자산을 작은 요청에까지 갖다 씀. → 나중에 `Alloc(70)` 오면 총 여유 91인데 최대 연속 67 → 실패.

실측(`-s 0`)에서 WORST만 최종 리스트 크기 5, BEST/FIRST는 4.
갈림길은 `Alloc(8)` 지점 — BEST/FIRST는 sz8 **정확히 맞는** 조각을 써서 남김 없음, WORST는 sz84를 잘라 **sz8 조각을 하나 더 생성**.

## ★ 리스트 순서(listOrder)가 정책을 바꾼다

**SIZESORT+ (크기 오름차순) + FIRST fit = BEST fit**
리스트가 크기순이면 **처음 맞는 것 = 맞는 것 중 최소**. → BEST 품질을 **조기 종료**로 획득.

직접 만든 반례로 검증 (주소순과 크기순이 어긋나게 설계):
```bash
./malloc.py -S 100 -b 1000 -H 0 -a -1 -A +20,+10,+5,+10,-0,-2,+4 -p FIRST -l ADDRSORT  -c
./malloc.py -S 100 -b 1000 -H 0 -a -1 -A +20,+10,+5,+10,-0,-2,+4 -p FIRST -l SIZESORT+ -c
./malloc.py -S 100 -b 1000 -H 0 -a -1 -A +20,+10,+5,+10,-0,-2,+4 -p BEST  -l ADDRSORT  -c
```
`-0,-2` 후 free list = `[1000 sz20][1030 sz5][1045 sz55]`. 여기서 `Alloc(4)`:

| 설정 | 반환 | searched |
|--|--|--|
| FIRST + ADDRSORT | **1000** (sz20을 깎음 — 나쁜 선택) | 1 |
| FIRST + SIZESORT+ | **1030** (sz5 선택) | **1** ★ |
| BEST + ADDRSORT | **1030** (같은 선택) | **3** |

→ 같은 결과를 1/3 비용에. **정책은 그대로 두고 자료구조만 바꿔 성능을 얻은 사례.**

### 대가: 탐색 vs 병합 트레이드오프 ★

| 정렬 | alloc | free / coalescing |
|--|--|--|
| **ADDRSORT** | 전수 탐색 필요 | **주소 인접 = 리스트 인접** → 병합 쉬움 |
| **SIZESORT+** | 조기 종료 가능 | 주소 이웃이 리스트 어디 있는지 모름 → **병합 어려움** |

**주소순은 병합이 쉽고, 크기순은 탐색이 빠르다. 둘 다는 안 된다.**

실제 할당자는 이 딜레마를 **자료구조로** 푼다:
- **segregated list / bin**: 크기별 리스트를 미리 나눠 요청 크기로 **바로 인덱싱** → 탐색 O(1). (glibc bins, tcmalloc)
- **boundary tag**: 블록 앞뒤에 크기를 기록 → 리스트 순회 없이 **주소 이웃과 즉시 병합**. (CSAPP malloc lab)
- **slab allocator**(커널): 고정 크기 객체 전용 캐시 → 초기화 비용까지 절약.
- **buddy allocation**: 2의 거듭제곱 단위 → 병합이 극도로 단순(짝 하나만 확인). 대신 **내부 단편화** 발생.

`malloc`은 초당 수백만 번 호출 → **O(n) 전수 탐색은 사망 선고.** BEST fit이 "이론상 좋은데 실전에선 못 쓰는" 교과서 정책인 이유.

## 숙제 (malloc.py) 실측

```bash
./malloc.py -n 10 -H 0 -p BEST -s 0        # 문제
./malloc.py -n 10 -H 0 -p BEST -s 0 -c     # 정답
./malloc.py -n 10 -H 0 -p WORST -s 0 -c
./malloc.py -n 10 -H 0 -p FIRST -s 0 -c
./malloc.py -n 10 -H 0 -p BEST -s 0 -c -C  # coalescing
```

**옵션**: `-S` 힙 크기 / `-b` 시작 주소 / `-H` 헤더 크기 / `-a` 정렬(-1=없음) / `-p` 정책 / `-l` 리스트 순서 / `-C` 병합 / `-A +n,-i` 연산 직접 지정(**`-i`는 크기가 아니라 `ptr[]` 인덱스**).

### 탐색 비용 실측
```
BEST  searched: 1, 2, 3, 4, 4, 4   ← 후반 항상 전수
FIRST searched: 1, 2, 3, 3, 1, 3   ← Alloc(2)가 첫 원소 sz3에 맞아 1로 종료
```

### 함정 — 우연의 일치에 속지 말 것 ⚠

`-s 0`에서 BEST와 FIRST 결과가 **동일**하게 나옴. 정책이 같아서가 아니라 **ADDRSORT 순서상 첫 번째로 맞는 조각이 마침 최적 조각이기도 했기 때문**(리스트가 `[3][5][8][84]`).

마찬가지로 `-l SIZESORT+`를 줘도 출력이 안 바뀐 이유: 그 워크로드에서 **주소순과 크기순이 우연히 일치**. → **정렬을 바꿔도 순서가 안 바뀌었으니 아무것도 증명 못 함.**
**결론을 주장하려면 차이가 드러나는 케이스를 직접 설계해야 한다.** (위 `-A +20,+10,+5,+10,-0,-2,+4`)

### coalescing(`-C`) 실측

`-s 0` 워크로드에서는 매 free마다 리스트가 `[1000 sz100]` 하나로 완전 복원됨.
**단, 이 워크로드가 유난히 착해서** — alloc/free가 번갈아 나와 **살아 있는 할당이 항상 최대 1개**.

수명이 겹치면 얘기가 다름:
```
+10,+10,+10,-0,-2  (a=8 정렬)
→ -C 켜도 [1000 sz16]은 고립. 1016에 ptr[1]이 살아 있어서.
   1032+1048만 병합되어 68.
```
**coalescing은 이미 인접한 조각만 붙일 수 있지, 살아 있는 블록이 흩뜨린 걸 모으지 못한다.**

## 실전 포인트

- `free(p)`가 크기를 아는 법 = **헤더** → 면접 단골.
- **double free / 헤더 오버플로우**가 왜 위험한가 = free list와 매직값이 깨짐 (Ch14와 연결).
- 내부 vs 외부 단편화 구분해서 말하기. 한 실행 안에서 **둘 다** 일어남.
- BEST/WORST/FIRST의 트레이드오프를 **탐색 비용 + 남는 조각 크기** 두 축으로.
- "정렬 방식이 정책을 바꾼다"(SIZESORT+ + FIRST = BEST) — 자료구조 설계 감각을 보여주는 답.
